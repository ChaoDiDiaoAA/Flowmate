# Deep Research

Use the trusted task, phase, immutable plan version and frozen source scope. Product permissions and exposed tools are authoritative.

1. During planning, split the user's problem into dimensions, subquestions, evidence needs and explicit stop conditions. Include only relevant authorized local IDs in sourcePolicy; match the task's web setting. Save executable steps: each has id, questionIds, tool:"read_research_local" and input:{artifactId,documentId}, with exactly one selected material ID and the other null. One acquisition can serve several questions. When the trusted task authorizes web access, combine relevant local and web steps in the same plan: search_research_web with input:{query,timeRange?,rank?} and read_research_web with input:{url}. Use specific public queries, a publication window when appropriate, and public HTTP(S) URLs. Tavily receives the query or URL; omit private source text, identifiers, local paths and credentials, including in URL queries and fragments. Each successful web step saves one page. If sourcePolicy.web is false, do not plan or call either web tool. When web is enabled, keep sourcePolicy.web:true and include at least one web step, plus a local read step when local materials are authorized. Use steps:[] only for local-only plans with nothing to acquire. In planning only read selected local materials. Size the shared budget and deadlines for acquisition, synthesis, all review calls and the Assistant response. For a new plan expected to produce a report with citations, suggest `execution.budget.toolTimeoutMs: 120000` (120 seconds per tool) and `execution.timeoutMs: 300000` (300 seconds for the Run). These are planning suggestions only; execution uses the user-confirmed budget and deadlines. Save the plan and finish the Run for confirmation. After a web setting change, generate and confirm a new plan before investigation.
2. During investigation, use the confirmed steps and current request checkpoint. With web off, do not use web evidence, including snapshots or claims from older plans. With web on, use only this plan's acquired web evidence. Pass the exact stepId and planned material parameters to read_research_local. The root Agent uses the two web tools with only {stepId} for the matching confirmed web steps. Issue independent reads together; the application permits two acquisitions at a time across parent and child agents. Reuse succeeded steps through their saved sourceSnapshotId. Attempt pending steps on first confirmation. In a later Run, attempt eligible pending, failed or interrupted steps after the user explicitly continues. When delegating independent local investigations to research-investigator, include their local step IDs, questions and source parameters.
   Confirmed legacy plans without a steps field retain the original local read/query flow: follow their confirmed questions and source policy and omit stepId for local reads.
3. Read authorized source bodies. For web sources, compare the publication or update date where available and the date of acquisition. Keep missing, stale and conflicting information visible. During investigation, copy the complete returned `evidenceRef` into Claim `evidence[].ref`: it already includes the confirmed plan, original source execution and exact UTF-16 locator. During planning this field is null; after confirmation use `query_research_evidence` on the saved source to obtain a usable reference. For a narrower passage, request an excerpt and copy its returned reference.
4. Turn findings into atomic claims using a question ID from the confirmed plan. Dependencies are numeric IDs of Claims saved under the same plan. Put the evidence judgment and specific reasons inside `verification`; compare supporting/refuting passages, entity identity, date, version and conditions. Multi-hop conclusions depend on saved intermediate claims; missing or unverified links remain unresolved.
5. Check every planned subquestion against current findings and retain the checkpoint's failed and unexecuted steps. Save Claims only once no steps remain pending, running or interrupted. Query saved passages to resolve evidence gaps. Use validation feedback within the same remaining budget. As the budget runs low, save a partial report with known findings and explicit gaps after running acquisitions stop. Revise the plan and obtain confirmation before changing acquisition steps or scope.
6. Save the final report under the confirmed plan. Use formatVersion:3 with answer as a sentence array and sections containing title and sentences. Each sentence has text and citations:[{claimId,evidenceIndex}], where evidenceIndex is the exact zero-based evidence entry in the saved Claim. Every fact and qualification needs support, and each selected quote must directly support a fact or supply a necessary premise. For multi-hop claims, cite the passages establishing the necessary links. Full saved context can qualify or contradict a quote. If support is elsewhere, cite the passage that actually supports the sentence. Include one coverage entry per planned question; mark covered only with supported Claims for that question. Full requires all steps to succeed, all questions covered, all referenced Claims and dependencies supported, and no unresolved questions.
   The Host binds Claim evidence entries to saved snapshots, exact UTF-16 spans and quotes, and acquisition receipts. It builds the evidence directory and independently reviews the final text and citations under research-semantic-v2. Submit only the report. Full saved context fits either in one review call or in N segment calls plus one final decision call. Leave enough of the confirmed shared budget and original deadlines for the entire review and reserve one call for the Assistant response. A failed or incomplete review prevents the save. Correct citations or narrow wording, then resubmit the final version for a fresh review within the remaining budget. Use partial when evidence remains insufficient; include gaps, conflicts, limitations and unresolved questions. If there are no citable findings, use empty answer and sections arrays to save the gaps without calling the reviewer. A verdict is a model judgment; a snapshot records what was captured, not whether it is true or still valid. Full/partial is separate from the Run terminal status. Finish after the save receipt and let the user inspect the review and saved citations, export Markdown or PDF, or explicitly continue.

Assemble a Claim from actual returned values (the variables below stand for those values):

```javascript
{
  questionId: confirmedQuestionId,
  text: atomicStatement,
  dependencies: savedDependencyIds,
  evidence: [{ relation: "supports", ref: readResult.evidenceRef }],
  verification: { status: "insufficient", reasons: [specificUnresolvedCondition] }
}
```

Folio informs bounded acquisition and references to real execution; the ICLR research characterization informs Claims and breadth/depth analysis; ACL CaRR informs single-hop support and complete evidence chains; Anthropic informs coordinator/investigator division and synthesis. The workflow and confirmation/budget/storage rules are Flowmate's engineering choices. Product coverage is current evidence, never independent Gold. Do not claim measured research gains from this workflow alone.
