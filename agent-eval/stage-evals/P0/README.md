# P0 阶段评测

P0 评测产品的基础输入、身份、权限、存储、重启和失败恢复，不运行模型或真实 Agent，也不使用 Inspect AI。评测复用现有产品测试、来源审计、故障探针和 [cases.json](cases.json) 中的确定性 Oracle。

当前状态是“评测入口已准备，等待用户执行”。旧 P0 报告已删除，不能沿用旧通过结论。

## 如何运行

在 Windows PowerShell 7 中执行：

```powershell
Set-Location D:/code/Flowmate
# 首次使用且依赖尚未安装时执行
bun install --frozen-lockfile
bun run p0:eval
```

命令直接执行，不读取标准输入，不要求交互终端，也不询问用途依据或记录人。默认使用项目来源与 `development` 用途；缺少必要文件或环境时显示具体原因并退出。

如果旧命令仍停在提问处，先按 `Ctrl+C`，再执行上面的命令。新版创建新的运行目录，不恢复旧进程、不覆盖旧输出。

运行期间不要修改源码、Case、依赖锁或来源清单。需要 Bun ≥1.4、Node ≥24、Python、Pillow、pytest，以及本机 `data/invoices/voxel51/`。Windows 链接边界测试需要开发者模式或相应权限；无法创建测试链接会作为设施问题报告。

## 本地技术判定范围

新 P0 `development` 运行采用 `assessmentPolicy: p0-local-f/v2`，在执行前写入 `expected-binding.json`，其摘要绑定 `execution-freeze.json`、执行记录和 F 报告，复核结果同时标明策略。该策略的本地确定性 F 不再以人工用途声明为技术验收前提，不读取或生成 `source-use.json`，不把来源许可 `not_verified` 改成已授权。通过仅表示本次范围内基础功能与资产技术检查通过，不表示来源许可、业务语义、真实 Agent 或生产用途通过。产品用途白名单、主体权限、Workspace 归属、路径隔离及当前有效性继续执行，明确拒绝使用仍阻断；Case/Oracle、证据完整性及必要覆盖不放宽。

新规则仅适用于策略和 `development` 用途同时匹配的新运行；无策略字段的旧证据沿用原规则，仍要求原有真实用途记录，未知策略、用途不匹配或冻结绑定被改动不能通过。旧报告、旧 `source-use.json`、审核状态和综合资产不修改、不重签。仅更新规范不产生新通过结论。

## 命令检查什么

单个命令按依赖顺序自动完成：

1. 检查运行时、阶段 Case 和来源清单。
2. 创建独立产品实例，固定代码、配置、输入、Case 和判据版本。
3. 执行类型检查、产品测试和评测设施合成自检。
4. 核验全部来源文件、解析结构、图片解码与引用闭包。
5. 通过真实产品入口检查并发布全部保留输入，读取已发布文档。
6. 保存一份输入投影，关闭后由新进程重新读取。
7. 执行文件提交、数据库提交、审计写入和响应丢失故障探针。
8. 绑定全部证据并按 P0-F01～F32 逐 Case 复核。

程序自动处理运行标识、路径、摘要、请求 ID、中间 JSON 和日志。它不会自动重试失败步骤，也不会删除失败实例或覆盖旧输出。

## 如何看结果

完成后终端会显示结论和结果目录。每次运行生成两个相互隔离的目录：

```text
FlowmateData/p0-evals/<运行标识>/   # 被测产品实例：数据库、Artifact 和产品日志
agent-eval/runs/<运行标识>/         # 评测证据、步骤日志和结论
```

只有第二个目录是评测结果目录，不存在第二套评测 `runs`。

优先查看：

| 文件                      | 用途                                   |
| ------------------------- | -------------------------------------- |
| `summary.md`            | 给执行者看的中文结论、失败原因和下一步 |
| `stage-review.json`     | 完整执行后的逐 Case 正式判定           |
| `p0-f-evidence-v1.json` | 产品 F 原始观察及证据绑定              |
| `<步骤>.stderr.log`     | 对应步骤的错误详情                     |
| `<步骤>.step.json`      | 命令、时间和退出码                     |

退出码含义：`0` 为完整复核 PASS；`1` 为可信证据确认 FAIL；`2` 为阻断、设施错误或无法判定；`130` 为用户中断。命令结束不等于通过，以 `stage-review.json` 为准。

## 失败怎么办

- 显示“未完成”时，先查看 `summary.md` 指出的步骤，再看同名 `stderr.log`。修复后重新执行 `bun run p0:eval`，程序会创建新运行，不改旧证据。
- 产品测试和设施自检是独立检查。即使其中一项失败，程序仍可继续采集不依赖它的证据，最终由 Case 复核判定。
- 来源审计、输入检查、发布或全量验证失败会停止依赖步骤，避免用缺少的回执继续生成假结果。
- 用户中断后先确认本次 Bun/Python 进程已经结束且句柄释放。不要盲删 `instance.lock`，不要重用半完成实例。
- `PASS` 只证明本次固定版本下的 P0 确定性基础能力，不证明数据许可、Agent、模型、OCR 业务语义或生产用途。

## 资产和底层排错入口

[cases.json](cases.json) 保存 P0 Case 和 Oracle，不创建业务 Gold。正常输入来自 `data/invoices/voxel51/`；综合数据集 `agent-eval/data/` 在完整 Agent 实现后另行核验启用，不参与 P0。

底层脚本保留用于定位问题，不要求执行者手工串联完整流程。以下两项可以直接执行：

```powershell
bun run typecheck
bun run test:p0
```

`p0`、`p0:source-audit`、`p0:fault-probe`、`p0:verify` 和 `p0:review` 仍可用于复现单个失败步骤，但它们需要本次实例、摘要、引用文件和输出目录等完整参数。请从该运行目录的 `<步骤>.step.json` 复制原命令，不要手工猜参数；日常评测只运行 `bun run p0:eval`。

受控恢复的 `checkpoint` 和 `--recovery-checkpoint` 是产品诊断入口，不是日常 P0 评测的额外步骤。P1 起阶段 Agent 评测统一使用 Inspect AI；P0 专用命令不会扩展成跨阶段评测平台。
