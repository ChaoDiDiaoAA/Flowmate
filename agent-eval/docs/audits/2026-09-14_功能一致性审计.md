# 5. 发现的不一致问题

以下只有 GAP-001 是已确认的功能启用时点冲突。GAP-002～006 依本次审计“不能只有泛化描述”的要求列为 S2：总体覆盖入口存在，但关键子不变量没有显式落入 Case/Oracle/阶段映射；应补登记，不应声称整个模块缺失。E:L7、22、327、1039 将详细 Case 留给阶段方案是合理的，不能用本报告要求提前实现全部夹具或新增评测平台。

## GAP-001：原生模型重试被提前到 P1/P2

**等级：** S1。标记：`EVAL_TOO_EARLY`、`EXIT_GATE_MISMATCH`。

**产品方案：** [P §4.2，L323](D:/code/Flowmate/docs/spec/00_Flowmate完整方案.md:323) 明确：“P1 关闭自动模型切换，固定有界调用。P3 起按需启用 SDK 支持的重试策略”。P:L221 还限定模型重试只能使用已启用 Pi 策略；P:L583 区分 P1 固定上限、P3 用量账目、P11 原子预留、P13 崩溃结算。

**评测方案：** [E RTC-13-01/03/04，L453](D:/code/Flowmate/agent-eval/docs/audits/baselines/2026-09-14_Agent评测总方案_修正前.txt:453) 分别要求“P1：原生重试有界且关联同次尝试”“P1：取消后不发新请求”（场景为重试等待取消）和“P2模型/只读重试”。[E:L335](D:/code/Flowmate/agent-eval/docs/audits/baselines/2026-09-14_Agent评测总方案_修正前.txt:335) 明确表中阶段是“首次执行阶段”。E:L1129 对 P3 只列 RT-13 观测，未消除此矛盾。

**问题：** P1 基本取消和有界请求不需要实际触发重试；瞬时失败后原生恢复、进入重试等待后取消却需要模型重试策略已经启用。后两者被放在产品允许启用点之前。P2 的只读查询重试可以合法存在，冲突仅是模型重试部分。

**后果：** 按 RTC 目录制定 P1/P2 必测项时，开发要么提前实现/启用模型重试，要么当前阶段无法证明机制触发；也可能把没有实际重试的普通取消误记为 RTC-13-03 已通过。

**应该以谁为准：** 产品主方案，P3 起按需启用；不是强制所有 P3 组合都必须打开重试。

**建议修正方向：** 调整 Eval 的 RTC-13-01/03 实际重试变体和 RTC-13-04 模型部分为 P3 起按已启用策略执行；在 RT-13 及 P3 映射中区分“P1 有界调用”和“P3 原生重试”。P1 的不可重试错误拒绝、基本取消、请求上限，以及 P2 已启用只读重试保留。

**反证核查：** E:L110/114 允许提前准备资产，但 E:L335 明说首次执行；不能以资产预制解释此处。全局“只评已启用能力”会限制实际执行，却不能让两个首次阶段定义同时正确。

## GAP-002：实际装载核验前禁止执行，缺少早期明确时序判据

**等级：** S2。标记：`PRODUCT_WITHOUT_EVAL` 的 **PARTIAL 子能力覆盖**；不标 `EVAL_TOO_LATE`。

**产品方案：** [P §2.4，L189](D:/code/Flowmate/docs/spec/00_Flowmate完整方案.md:189) 要求实际绑定通过后才允许 prompt 和工具执行；[P §19.1，L1701](D:/code/Flowmate/docs/spec/00_Flowmate完整方案.md:1701) 明确由 core/configuration 核对实际装载、固定 RuntimeSnapshot，核验完成前禁止模型或工具执行；P:L1705、2499 说明必要运行引用逐阶段建立，完整生产治理才到 P13。

**评测方案：** [E RTC-01，L343](D:/code/Flowmate/agent-eval/docs/audits/baselines/2026-09-14_Agent评测总方案_修正前.txt:343) 覆盖最终配置一致、非法配置和半初始化失败不可运行；E:L1149 覆盖绑定/消费/终态，E:L1303 在 P10 覆盖必要 Hook 失败不 ready，E:L311 在 P11 明确子工具前绑定，E:L1371 在 P13 明列 RuntimeSnapshot。早期没有明确“核验尚未结束时不得发首请求”的检查项。

**问题：** 最终配置正确、初始化没有报错，不能证明请求发生在核验通过之后。反例是：首模型请求先发出，随后才完成相同配置的装载核验；现有配置一致和失败清理判据可能仍通过，但产品启动时序已违规。

**后果：** P1 初始绑定或 P4 重绑可能只保留事后快照一致证据，无法确认准入前零请求。后续扩展/子路径虽然有专项保护，根启动路径仍可能漏掉这个窗口。

**应该以谁为准：** 产品主方案；core/configuration 固定快照、runtime-pi 提供装载证据的 Owner 不变。

**建议修正方向：** 在 P1 配置/初始化 F 及 P4 重绑 F 中挂接“核验完成前零模型/工具执行；通过后身份/快照一致”的 Oracle；失败、延迟核验及旧绑定变体按阶段细化，并纳入 P10/P11/P13 回归。由产品提供/运行 F，Eval 消费证据，不新增 Runtime API 或质量侧启动状态机。

**反证核查：** E:L14/150/1404 已要求继承产品 F，所以不是全无覆盖，更不能认定首次真实覆盖必然迟至 P13。这里补的是显式时序覆盖身份。

## GAP-003：P13 生产日志治理只有总引用，未明确不可替代的检查项

**等级：** S2。标记：`PRODUCT_WITHOUT_EVAL` 的 **PARTIAL 横切覆盖**。

**产品方案：** [P §18.5.3，L1673](D:/code/Flowmate/docs/spec/00_Flowmate完整方案.md:1673) 要求单写者、Host 不依赖主 IPC 落盘；P:L1675–1677 要求实例总额包含遗留分段、多进程配额、重启不清零，只清理合法关闭分段且不越出 logs；[P §18.5.4，L1681](D:/code/Flowmate/docs/spec/00_Flowmate完整方案.md:1681) 要求故障降级、损坏尾行、有界查询/导出及故障验证。P:L2475 将完整生产增量放在 P13。

**评测方案：** E:L104 提到生产日志，E:L1053/1063 覆盖 P0 日志失败/脱敏/有界；[E:L1404](D:/code/Flowmate/agent-eval/docs/audits/baselines/2026-09-14_Agent评测总方案_修正前.txt:1404) 统一沿产品21.15复用 F；E:L1476 将日志保留参数留给 P13。MOD-26 的明确判据是关联、缺口、脱敏和只读回放，P13 被测/Oracle 段 E:L1371/1377 没有列出上述生产日志组合不变量。

**问题：** “日志有界”不能独立证明多进程共享实例总额；“Host 故障可恢复”不能证明断 IPC 时日志仍在本地按配额落盘；“保留/查询”也不能证明不清理活动文件或业务证据。只有泛化引用，尚不能建立每项的阶段覆盖分母。

**后果：** P13 可能沿用 P0 单进程限额和脱敏 F，就将生产日志治理整体标为通过；这是拆分阶段方案时的覆盖风险，不是已发生的运行缺陷。

**应该以谁为准：** 产品日志与实例维护职责；Logger 只报告健康，不能接管业务停写。

**建议修正方向：** 在 Eval P13/MOD-26/28/29 下登记日志子能力及产品 F 引用：独立落盘、单写者与总配额、重启占用、只清理合法分段、有界授权查询和再脱敏导出、磁盘/队列/flush 故障降级。不要求增加 MOD 编号、集中日志平台或日志数据库。

**反证核查：** 按宽泛章节继承可以认为已纳入范围；按本次要求的功能级可追溯标准仍为 PARTIAL。这里不声称 Eval 排除了这些能力，也不将具体配置值尚未固定列为缺陷。

## GAP-004：桌面故障时后台控制可达性及 IPC 信任边界覆盖不明确

**等级：** S2。标记：`PRODUCT_WITHOUT_EVAL` 的 **PARTIAL P12 覆盖**。

**产品方案：** [P §3.2，L227](D:/code/Flowmate/docs/spec/00_Flowmate完整方案.md:227) 区分 IPC/命令错误、组件错误边界、异步/事件错误；页面故障不等于 Run 停止，应用侧停写/恢复仍可用，无法操作时由独立 CLI/运维入口接管。P:L231 禁止以组件兜底替代这些边界。[P §20.4，L2032](D:/code/Flowmate/docs/spec/00_Flowmate完整方案.md:2032) 要求 contextIsolation、关闭 Renderer Node、preload 白名单及主进程输入/来源校验。

**评测方案：** [E MOD-23，L196](D:/code/Flowmate/agent-eval/docs/audits/baselines/2026-09-14_Agent评测总方案_修正前.txt:196) 和 E:L1335/1341/1343 覆盖实际桌面、接管、状态/故障 F；E:L579–580 覆盖通用越权与隐私。但没有明确区分“业务接管正常操作”和“Renderer/异步交互已坏、后台仍在运行时备用控制可用”，也没有把桌面 IPC 来源/白名单专项挂入覆盖表。

**问题：** 正常页面能取消/接管，并不能证明页面崩溃后还能停止新动作；Gateway 拒绝非法模型请求，也不能证明恶意 Renderer 无法使用过宽 preload 能力。

**后果：** P12 桌面 E2E 正常路径和通用安全测试可能通过，但故障时用户失去控制入口，或桌面桥接绕出产品授权面。

**应该以谁为准：** 产品 Application/Renderer/main/preload 边界；P12 不提前要求 P13 Host。

**建议修正方向：** 将组件失败、异步/订阅失败且后台存活、备用控制入口、IPC来源伪造/白名单与直接文件执行拒绝分别挂到 P12 MOD-23/28、BM-07/08/09 的产品 F 引用。P13 增加 Host 变体。无需给纯桌面机制测试强行增加真实模型 A。

## GAP-005：公共组装的无隐式启动与同实例单控制者缺少明确覆盖挂接

**等级：** S2。标记：`PRODUCT_WITHOUT_EVAL` 的 **PARTIAL Application 覆盖**。

**产品方案：** [P §20.3.2，L2015](D:/code/Flowmate/docs/spec/00_Flowmate完整方案.md:2015) 定义 CLI→公共组装→Application/Kernel；P:L2026 要求 CLI 与桌面不能同时取得同一实例执行权；P:L2028 要求不安装/启动 Electron 时 CLI 可验证当前能力，导入公共组装不自动启动。

**评测方案：** [E:L106](D:/code/Flowmate/agent-eval/docs/audits/baselines/2026-09-14_Agent评测总方案_修正前.txt:106) 明确公共 Application 与同一组装；E:L354 将 CLI/桌面配置一致性放在 P12；P0 Oracle/退出 E:L1053/1063 主要是输入/存储/日志，未明确这三项启动控制判据。

**问题：** 两入口复用同一组装，不等于纯导入无副作用、CLI 不依赖 Electron 或两入口竞争时只有一个有效控制者。不同实例配置隔离（RTC-01-03）也不能替代同实例执行权竞争。

**后果：** 早期 CLI 可能隐含桌面依赖，或导入时启动资源；P12 同时运行 CLI/桌面可能形成双控制者。模块复用名义成立仍不能证明上述约束。

**应该以谁为准：** 产品 Application/启动层，Eval 不实现第二份实例锁。

## GAP-006：StepAttempt 恢复历史与完整步骤视图的关键子项仍是泛化覆盖

**等级：** S2。标记：`PRODUCT_WITHOUT_EVAL` 的 **PARTIAL P8/P12 覆盖**。
