# Flowmate 数据集对齐修订方案

## 交付约束

按用户确认，仅交付一套当前质量数据。固定 `manifests/audit/`、`manifests/materialization/` 和 `manifests/inventory.json`；目录和资产文件名不追加版本后缀。原票共 2,902 份，保留 112 个重复别名、1,414 份来源标签、1,200 份 Gold 候选和 600 套模拟资料。七类用例从旧 6,000 个退役 423 个至 5,577 个，不补数；当前发布状态以迁移记录和检查报告为准。

机器准备期间的有效修订合入当前资产，必要来源摘要保留在元数据。现有 `manifests/reviews/user-confirmation-20260915T145419376406Z.json` 已保存用户对旧 7,801 项资产的批量审核声明，必须连同绑定旧内容保留；该声明不等于逐字段 Gold。未改动的 Gold 和来源保持原内容；修改后的业务资料、用例和政策需重新审核，不能继承旧确认。实际运行历史也必须保留其内容和身份。原图不复制为多套，不因修订清理；审核和运行状态不由脚本代填为成功。

## 当前业务范围与退役清单

保留外部解析导入和原件证据，A2 收货、合同价格、数量及订单余额检查，按需匹配，以及人工修订、澄清、具体 B2B 提交确认、失效处理和接管。ERP 可提供获准只读业务资料。P0–P13 顺序、Pi 原生 Runtime/Memory/Extension/Subagent 和平台基础验证保持不变。

## 逐项修订

| 审查项 | 修订内容 | 接收依据 |
|---|---|---|
| A01 完成判据不足 | `oracle.checks` 明确必要项、硬约束、维度、证据和规则实现状态；局部断言不能充当整例通过 | 未实现规则或缺证据阻断通过；真实证据入口验证受信来源与内容摘要 |
| A02 缺证据掩盖失败 | 聚合先保留已确认必要项失败，再列出未解决项 | 同时存在 FAIL 与缺证据时保留 FAIL 和缺口 |
| A03 安全维度混用 | 分别评模型行为、平台控制及实际后果，并检查攻击是否真实到达 | 网关拒绝不能掩盖模型越权请求；真实后果独立记录 |
| A04 合法对照循环 | 基础合法对照独立；攻击绑定同用途、同操作的对照身份和修订 | 不接受输入中伪造的对照 pass；对照必须独立加载并重新评分 |
| A05 夹具并非单故障 | 构造有效非空解析、图片引用、原图和元数据底包，再引入缺图、摘要不符等变化 | 基础合法包可核对，故障范围明确，未真实执行导入不声称导入通过 |
| A06 路径越界不触及目标 | 受控临时根下建立合成哨兵，越界路径实际指向目标 | 临时目录读取得到预设哨兵；受保护目标不进允许根 |
| A07 主方案映射不足 | 固定主方案摘要、MOD/RT/RTC/RTX、Driving Task 和关键横切条文；检查级引用并报告缺口 | 条目存在不等于条款全部覆盖；F/A/B 未准备变体保留缺口 |
| A08 阶段过晚 | 原生历史损坏场景归 P4；衍生视图同步刷新 | 保留相关用例身份，阶段和视图一致 |
| A09 审核入口不足 | 支持 Gold、business、case、policy；目标摘要、Owner、检查项、证据、暴露、争议和裁决 | 空表不能通过，实际记录留存父内容，审核通过不自动成为验收资格 |

## 数据调整原则

1. 保留来源、Gold 和业务包数量，按批准范围退役用例；不通过增加副本或重新分配重复实例维持旧总数。
2. 原票抽取仍一票一例，原票金额与模拟金额分别使用。
3. 对运行、安全、平台的重复分配补充具体初态、触发和原子预期；纯机制用例清除无关原票输入。
4. 全局语义键计数与重复序号一致；同票关联仍不是独立企业样本。
5. 原票及近重复组继承同一用途；当前不声称未见模板或未见供应商泛化。
6. 新目录索引、用途成员、阶段/BM 视图、审核批次和物化摘要从当前资产重新生成。
7. 保留已有材料审核声明，结构化逐字段 Gold 发布数仍为 0；所有当前产品用例保持未运行。

## 实施与检查顺序

1. 核对旧质量清单、有效修订、来源摘要及已有用户审核声明，固定声明所绑定的旧内容。
2. 同步场景、业务资料、政策和设施；保留正常授权、隔离与平台验证，运行相关设施自检。
3. 从当前两份主方案提取需求，验证保留资产身份、退役清单和新范围数量，不替换未改 Gold 或来源。
4. 使用 `sync_invoice_scope.py` 在项目暂存根生成数据，保存 `manifests/history/*.zip` 和 `scope-sync.json`；旧归档保留审核所依据的内容，变更资产不继承旧确认。
5. 重建任务单、用途成员、阶段/BM 视图、需求覆盖和物化，全量检查来源、引用、摘要、算术、数量、合法对照和审核生命周期。
6. 检查成功后受控发布唯一当前质量根，替换后再次检查；保留历史归档和真实审核记录。
7. 逐字段 Gold 发布、变更内容复核、产品接入和真实 SDK/企业接口运行另按实际阶段完成，不能伪造成当前成果。

## 当前命令和文件

- `agent-eval/tools/finalize_invoice_data.py`：仅作初始机器草案合并，不能用于覆盖已有人工审核历史的当前数据。
- `agent-eval/tools/sync_invoice_scope.py`：在暂存根同步已批准范围，保留审核绑定旧内容、迁移记录并校验后发布。
- `agent-eval/tools/invoice_requirements.py`：需求提取、用例丰富、覆盖报告及映射检查。
- `agent-eval/tools/invoice_case_catalog.py`：业务与机制场景定义。
- `agent-eval/tools/review_invoice_data.py`：实际审核入口、当前资产及统一清单。
- `agent-eval/tools/verify_invoice_data.py`：产品及质量数据完整性和生命周期检查。
- `agent-eval/src/runner/`、`graders/`、`contracts.py`：离线物化、模拟目标、受信证据和逐项评分。
- `agent-eval/tools/test_invoice*.py`、`agent-eval/tests/`：制作、审核、场景与评分设施自检。

日常检查运行 `python agent-eval/tools/verify_invoice_data.py --project .`，不需要选择历史发布号。目录职责、详细制作规则和审核命令统一维护于 [数据制作方案](data-preparation.md)；当前数量和缺口由 `agent-eval/data/manifests/preparation-report.json`、`coverage.json` 与 `materialization/report.json` 给出。

## 完成边界

工程修订完成表示当前材料和设施通过对应检查，保留用户对旧材料的真实批量审核声明，但不表示 1,200 份逐字段 Gold 已发布，也不表示 5,577 个产品用例已执行。覆盖报告中的 `partial_prepared` 和 `uncovered` 是制作状态；现阶段没有完整需求通过率或真实业务自动化率。

## 本次实施结果（2026-09-16）

已同步两份主方案、数据制作文档、生成/映射/物化/校验工具及当前数据。活动数据为 5,577 例、177 个场景族、3,516 个语义键；退役 423 例，不补数。2,210 例可构造离线夹具，3,367 例仍有真实模型、SDK 或适配器依赖；实际产品运行数仍为 0。完整数据使用手册与附录已按当前 Case 重建。

发布前后全量校验通过：19,377 个产品数据文件、11,429 个质量文件；63 项数据工具自检与 45 项离线设施自检通过。保留用例的身份、原票关联、用途、阶段与 Runtime 初态均与迁移前核对；原票、Gold 候选和审核声明保留。旧审核依据逐文件归档到 manifests/history/，退役和修订摘要见 manifests/scope-sync.json。

后续人工复核可沿审核记录回溯到本次基线；Case 或策略内容/版本改变后，仍需重新生成受影响的覆盖、对照引用和物化记录，不能复用已过期的派生结果。
