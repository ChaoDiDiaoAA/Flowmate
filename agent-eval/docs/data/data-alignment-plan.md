> **2026-09-20架构修订。** Inspect AI统一阶段及完整Agent综合评测，CLI执行、Inspect View查看。现有 `data/` 综合材料保持不动，完整Agent实现后再核验启用；各阶段当期使用 `stage-evals/Pn/`，不等待整体完成。每阶段只保留README.md、cases.json及必要gold.json/fixtures，Oracle嵌入Case，质量优先、不追求数量。所有适配代码在agent-eval/src；详细接口与使用见[评测主方案第10章](../spec/01_Flowmate_Agent评测总方案.md#10-评测设施与工程对接)。本次不实施适配或生成运行，既有数据的数量/审核/摘要状态不变。

### 新规范与旧工具的兼容边界

本次调整的是现有综合集的后续使用安排，原先可按阶段筛选的历史不改写；阶段规则集中于[评测主方案§10.5](../spec/01_Flowmate_Agent评测总方案.md#105-数据怎样准备阶段集怎样映射)。整理P0时建立README/Case索引复用现有F及报告，不要求业务Gold或真实Agent适配；本次不创建目录。

当前离线assemble_benchmark仍读取综合清单，--stage不是阶段目录加载器；I2须验证新stage入口不依赖无关综合资产。P0报告脚本固定三项阻断，后续按实际材料、用途、Oracle和Benchmark依赖判断；真实用途not_verified不能因换目录解除，旧Case待复核和pin drift也不能无条件阻断无关阶段。详细代码依据及解除条件见§10.5.7，本次不修改实现。

新运行固定Case/Gold/输入/Oracle/Grader、产品/配置和环境版本及实际摘要，写入运行binding，不增加阶段manifest。规范或判据改变需复核证据适用性；不覆盖、不重签历史清单和报告，不把数据修正计为Agent能力提升。四类完成状态分别记录，不因对齐文档就升级阶段结论。

本轮将评测材料整理为可理解、可筛选、可接入的初始集。依据[产品总方案](../../../docs/spec/00_Flowmate完整方案.md)与[评测总方案](../spec/01_Flowmate_Agent评测总方案.md)，不修改主方案来降低要求。当前已有P0产品基础，但本综合集尚未接入真实Agent；其离线执行保持blocked，没有Agent运行或Baseline。

## 一、范围与三类归属

保留 2,902 份原票及配对解析、1,414 份提供方标签、100 份 Gold、80 套模拟业务资料。Gold 人工核验 0；保存的标注不是人工审核。Gold/业务资料可以多于本轮任务实际使用的份数。

Agent 任务最多 100 个：抽取 20、匹配 20、人工协同 15、证据取用 15、恢复 15、提交 15。配额是上限，实际选入需要完整目标、获准输入、工具/状态环境、自然过程、终点和独立判据，不以数量凑满为目标。

| 类型 | 内容 | 权威位置 | 分母 |
|---|---|---|---|
| `agent_task` | 完整 Agent 决策任务 | `data/cases/<caseId>.json` | Agent 任务，≤100 |
| `product_contract` | 产品确定性规则、触发与断言 | `data/contracts/<module>.json` | 独立契约场景 |
| `eval_selftest` | 装配/隔离/评分/统计的合成自检 | `tests/fixtures/evaluation-selftests.json` | 设施自检 |

机械检查应归产品契约；完整任务可以引用契约，不通过把断言包装成用户句子来扩大 Agent 任务数。同一任务跨 Benchmark 只引用一次权威文件。检查项、事件、明细、调用和子 Agent 均不是新的独立任务。

## 二、六维分类及 Schema

每个任务保存六个并列维度：`capabilities`、`taskShape`、`difficulty`、`conditions`、`targetFailureModes`、`business`。前五项不能嵌套在业务分类下；MOD/RT、阶段、用途、Benchmark 是追溯或选集关系。

新的任务、契约套件和自检套件使用 `schemaVersion: 1`；逐条件覆盖清单单独采用 `schemaVersion: 2`；新的有版本内容从 `version: 1` 开始。Schema 是结构协议，version 是内容修订，不能混用。保留的来源标签、Gold 与业务包拥有既有领域 Schema/内容修订，不为目录整理强改来源版本或答案值。

任务必备结构包括身份、六维分类、`task`、`setup`、`interactions`、`oracle`、控制/比较引用、`traceability`、`applicability`、`split`、`leakageGroup`、`lifecycle`。嵌套参数与可选来源/断言元数据见[数据手册](../../data/README.md)；验证器拒绝未知配置，不把任意 JSON 当成执行适配器选项。

## 三、规范与映射

产品主方案定义行为和责任，评测总方案定义测量与证据。规范来源使用路径、摘要、章节及直接引文定位，检查项通过 `requirementRefs` 绑定实际验证的要求，禁止给所有检查复制整个模块的引用。

- MOD-10 原文解析、MOD-14 独立验真、MOD-22 ERP 写入不进入活动产品分母。
- MOD-30–32 归评测设施；通过设施自检不证明产品实现或模型效果。
- BM-06 退役；其他 11 个 BM 身份保留；BM-10 真实业务成员为空。
- BM-11 聚焦 RT-01–16；RT-17 是第三方子 Agent 插件，归 BM-12。RT-08 原生扩展按适用检查映射。
- P0–P13 是唯一功能建设轴。P12 三层测试环境、P13 四级发布条件各自独立，不能跨范围继承成绩。
- `module-catalog.json` 提供逻辑导航；`coverage.json` 提供直接检查关联和缺口，二者都不是完整覆盖或产品通过证明。

## 四、最新活动材料与迁移

本节记录初始综合集原有迁移策略：当时只保留最新活动数据，旧身份通过migration.json保留ID/版本/摘要映射。**这不是本次Inspect架构修订的执行指令**；现有Case、发布副本、映射及其他材料保持原样，不再次清理或重建。后续启用综合集须受控核对当前版本，原有规则不能授权删除历史评测证据。

被保留的原始输入保持原位与字节不变。必要来源分组、既有暴露事实、原图标注出处和真实核验状态用当前清单表达。来源与答案不能因迁移获得更高审核状态；未证明的条件进入明确缺口。

实际运行产物属于数据集外 `agent-eval/runs/`，仅在真实执行发生时创建。JSON 是唯一编辑源，JSONL 为按需导出视图；不建立长期维护的镜像。运行记录、答案、来源和评测设施不向被测主子 Agent 开放。

## 五、初始制作的历史实施与接收次序

下列步骤说明原综合集制作流程，不在本次执行；Inspect接入及阶段数据按评测主方案第10章实施，不通过重建这批材料启动阶段评测。

1. 固定两份规范及保留来源摘要，核对实际原票、标签、Gold、业务资料数量。
2. 按完整工作目标筛选任务，审查输入、决策、过程、终点、Oracle 和真实证据依赖。
3. 将确定性规则转入产品契约，将设施逻辑转入自检，合并完全重复语义；不同故障窗口不盲目合并。
4. 写入 Schema 1、六维分类、直接检查绑定、split/分组及控制依赖。
5. 重建当前目录、成员清单、模块导航、覆盖、视图和报告，并记录迁移身份关系。
6. 核验来源不变、引用闭合、预算、隔离、无旧材料副本、无伪造审核/运行/基线。
7. 完整Agent实现后，核验综合材料所需的公开执行、可信采证及适用Gold/Oracle核验条件，受控冻结实际范围并执行；阶段开发使用独立阶段集。

## 六、必须分别报告的状态

| 维度 | 当前含义 |
|---|---|
| 材料准备 | 文件及结构已形成，由 verify 核对 |
| 内容审核 | 初始材料待审阅；机器通过不升级人工状态 |
| Gold 审核 | 100 份保留，真人核验 0 |
| 覆盖 | 检查项直接引用及未覆盖要求独立列出 |
| 执行资格 | 所有产品资产 blocked，保留具体依赖原因 |
| 实际执行/成绩 | 真实产品运行 0、Baseline 0 |
| 正式验收 | 不具备资格；acceptance 标签不等于冻结 |

最终实际数量不在本方案写死，从[制作报告](../../data/manifests/preparation-report.json)、[当前索引](../../data/manifests/active-dataset.json)、[覆盖清单](../../data/manifests/coverage.json)核对。工具入口是 `python agent-eval/tools/initial_dataset.py prepare|verify|report --project .`（运行时选择一个子命令），详细示例见[使用指南](data-usage-guide.md)。
