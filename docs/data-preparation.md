# Flowmate 全类型数据集制作方案

## 一、目标、规模与实施状态

### 1.1 制作目标

利用当前能够取得的发票数据，建立可追溯、可复核、可重复运行的数据资产，分别回答以下问题：

1. 系统能否正确理解发票，并指出字段来源？
2. 系统能否依据业务资料完成校验和匹配？
3. 信息不足、金额冲突或授权失效时，系统是否正确停止并交给人工？
4. 提交、查询、ERP 回写异常后，能否正确恢复并避免重复操作？
5. Agent 的工具、会话、上下文、权限和运行机制是否可靠？
6. 不同版本的效果变化，能否通过固定数据和评分标准进行比较？

现有公开发票与模拟资料支持开发和模拟业务验证。企业实际规则、真实接口及生产分布的适配，需要取得对应资料后单独验证。模拟资料中的审批额度、币种、税率和金额处理规则都是测试假设，不代表企业财务政策。

### 1.2 已确认预算与计量单位

| 数据资产 | 目标数量 | 统计单位 |
|---|---:|---|
| 去重发票来源集 | **2,902** | 不同原图文件 |
| 人工核验发票 | **1,200** | 不同原票对应的核验结果 |
| 模拟业务资料包 | **600** | 一份基础模拟业务输入及其关联资料 |
| 评测用例 | **6,000** | 固定输入、初态和预期行为的用例实例 |

这些数量不能相加：1,200 份核验票据来自 2,902 份来源集；600 套业务资料关联其中 600 份选中发票；多个用例可以引用同一原票或资料包。同一用例执行多次增加运行次数，不增加用例数。

### 1.3 基线事实与完成边界

本方案交付一套当前数据。以下资产预算保持不变，当前精确状态以 manifests/preparation-report.json 为准，不代表人工核验或产品验收通过：

| 内容 | 当前状态 |
|---|---|
| 2,902 份原票、解析及必要图片 | 已整理，文件检查通过 |
| 1,414 份提供方来源标签 | 已独立保存，按来源 ID 保留 |
| 1,200 份字段核验材料 | 已生成候选；人工核验完成数为 **0** |
| 600 套模拟业务资料 | 已生成；业务合理性待复核 |
| 6,000 个用例 | 已生成草案；实际 Agent 执行数为 **0** |
| 场景族与语义场景 | 通过 case-catalog.json 与 preparation-report.json 统计 |
| 正式验收 Gold、Agent 成绩 | 尚未形成 |

本轮修正逐项判据、安全三维评分、独立合法对照及单故障夹具；补充两份主方案的需求与检查映射、明确依赖缺口和审核入口。离线物化情况见 manifests/materialization/report.json。**离线物化不代表实际运行；人工核验与实际产品运行仍为 0。** 自动检查、模拟器自检和模型实际评测分别记录。

后续工作的重点是将已有草案推进到内容可信、输入可执行、结果可评分的状态。自动生成不能完成“人工核验”，不能填写虚构的人类姓名、操作记录或双人一致结论。

## 二、为什么这样划分

### 2.1 按资料用途和被测能力划分

采用 **2 类基础资料＋7 类评测用例集**，共 9 类逻辑数据集：

| 层级 | 类别 | 数量 | 划分原因 |
|---|---|---:|---|
| 基础资料 | ① 发票来源集 | 2,902 份 | 给所有票据测试提供共同证据 |
| 基础资料 | ② 模拟业务资料集 | 600 套 | 补充原票不存在的供应商、订单、收货及系统状态 |
| 评测用例 | ③ 字段抽取与证据核验集 | 1,200 个 | 判断是否读得正确，证据是否支持答案 |
| 评测用例 | ④ 校验与业务匹配集 | 1,000 个 | 判断是否满足业务条件 |
| 评测用例 | ⑤ 人工复核与审批集 | 600 个 | 判断何时需要人，以及人的决定如何生效 |
| 评测用例 | ⑥ 提交与 ERP 闭环集 | 1,000 个 | 判断外部动作是否正确发生并得到确认 |
| 评测用例 | ⑦ Agent 运行与恢复集 | 1,000 个 | 判断会话、工具和恢复机制是否可靠 |
| 评测用例 | ⑧ 权限隔离与不可信输入集 | 800 个 | 判断是否只读取和执行获准内容 |
| 评测用例 | ⑨ 平台与评测设施集 | 400 个 | 判断数据、平台和评分工具本身是否可信 |

按能力划分可以将失败定位到具体环节。例如，总额抽错属于抽取问题；总额正确但收货数量不符仍继续，属于匹配或决策问题；审批失效仍提交，属于授权问题；响应丢失后重复提交，属于动作恢复问题。一个不可解释的总通过率不能替代这些分项结果。

### 2.2 三条划分轴分别管理

| 划分轴 | 回答的问题 | 示例 |
|---|---|---|
| 功能类别 | 测什么能力？ | 抽取、审批、恢复、隔离 |
| 数据用途 | 可以怎样使用？ | 开发、回归、留出验收 |
| 运行表现 | 某版本实际表现如何？ | 通过、失败、证据不足 |

同一资产可以有上述三种归属，但只保存一份权威内容。“回归集”不是第十类业务能力集；“错题集”不复制一批新发票；“黄金集”不能在自动生成后直接命名为已验证标准。P0–P13 和 BM-01–BM-12 均通过清单引用 Case/Gold，不按阶段或 Benchmark 各建数据副本。

### 2.3 提供方标签为什么独立保存

提供方标签可以降低候选制作成本，但存在字段缺失、税额歧义、位置指向标签 JSON 而非原图等限制。缺失标签不能证明票面没有字段。

- `source-labels` 保存提供方原始资料及来源关系。
- `gold` 保存候选和后续人工核验的版本。
- 业务 Agent 不直接读取这两个目录，也不读取用例判据和成绩。
- 候选证据指针的来源类型必须保留；提供方 locator 不能被伪装为票面坐标。

## 三、身份、引用、计数与重复实例

### 3.1 稳定身份

| 资产 | 身份和关联 |
|---|---|
| 来源记录 | 保留 `sourceSampleId` |
| 去重原票 | 使用 `sampleId`，记录原图 SHA-256 |
| 字段核验结果 | 关联 `sampleId`，有独立版本 |
| 模拟业务资料 | 使用 `businessId`，关联样本及模拟政策版本 |
| 评测用例 | 使用 `caseId`、用例版本，引用固定输入及判据 |
| 实际运行 | 独立运行 ID，绑定用例、输入、产品及评分版本 |

不能使用“某文件夹里的最新文件”代替稳定身份和版本。旧运行必须能解析到当时使用的答案、场景、政策和文件摘要。

### 3.2 四种数量分别报告

1. **独立原票数**：不同来源输入的数量。
2. **场景族数**：不同条件与处理规则的数量。
3. **用例实例数**：场景在具体输入上的实例数量。
4. **实际运行次数**：真正执行的次数。

6,000 个实例的场景族、语义键及额外重复数以当前准备报告为准。修订从重复分配中加入具体机制条件，不能把换 ID 当作新覆盖。同一原票的多个情境仍然相关；机制样本的分配用原票 ID 不进入实际输入。

### 3.3 重复实例处理

保留原有实例身份，并明确记录 `semanticScenarioKey`、`replicaIndex` 和 `sampleRole`。首次功能覆盖按语义场景去重；重复实例用于重复性观察或已配置的运行对照。

更换名称或 ID 不能增加独立覆盖。只有输入条件、故障位置、权限、时序或预期行为发生实质变化，才登记新的场景变化。机制重复项即便分到不同用途，也不能被当成独立留出能力。

## 四、来源整理、选样和用途划分

### 4.1 完整来源池检查

外部来源为 `D:\obsidian\data\flowmate-data\Evidence\invoices\voxel51`，保持只读。对 3,014 条来源记录检查：

1. 原票与解析是否配对，内容是否为空。
2. JSON 是否可读取。
3. 图片基础结构是否有效。
4. 解析引用的图片是否存在。
5. 文件及引用是否位于预期目录范围。
6. 原图摘要是否与来源记录一致。
7. 标签是否正确关联来源样本。
8. 重复来源是否存在解析或标签差异。

仅白名单文件复制到项目目录。图像结构检查不能证明视觉内容或 OCR 正确。外部来源的 8,102 张原图及局部图片完成了基础结构检查。

### 4.2 字节去重与近重复审查

**字节去重**按原图 SHA-256 分组。相同字节保留一份，所有来源 ID 通过别名映射关联到保留样本。不同标签分别保留；不同解析或冲突标签记录差异，不能静默覆盖。整理得到 2,902 份唯一原票和 112 个重复别名。

**近重复审查**用于避免评测泄漏，不直接删除来源。检查重编码、裁剪、轻微图像变化、相同内容不同布局，以及不同来源 ID 对应同一业务发票的情况。候选线索包括：

- 图像相似特征。
- 规范化解析内容。
- 票号、买卖方、日期、金额等候选组合。

相同票号只能触发检查，不能单独证明同票。自动相似性结果是审查线索，不得直接宣称已经人工判定。无法判定的候选保守地放入同一用途组；组间冲突未解决前，划分不冻结。

### 4.3 选择 1,200 份人工核验样本

| 提供方标签情况 | 数量 | 原因 |
|---|---:|---|
| 有标签 | 900 | 利用候选降低核验成本 |
| 无标签 | 300 | 避免只覆盖提供方容易标注的部分 |
| 合计 | **1,200** | |

最初选样按标签有无、表格数、解析块数和页数分层轮转。此自动分层不是人工确认的版式分类。人工核验时补充以下实际特征：布局、明细行数、数字和日期格式、清晰度、遮挡、字段完整性、解析遗漏、错行错列和合计冲突。

这些特征是采样与分析依据，不预设模型会犯什么错误。若发现某类明显过多或关键类型缺失，从剩余池补选并发布新选样版本，不修改已冻结版本的成员。

### 4.4 开发、回归、验收配额

| 用途 | 有标签 | 无标签 | 核验原票 | 模拟资料包 |
|---|---:|---:|---:|---:|
| 开发 | 450 | 150 | **600** | **300** |
| 回归 | 150 | 50 | **200** | **100** |
| 留出验收 | 300 | 100 | **400** | **200** |
| 合计 | 900 | 300 | **1,200** | **600** |

开发集占一半，用于频繁查看答案、调试候选、工具、规则和 Prompt。回归集独立保护历史修复，但使用后会逐步暴露，不能长期冒充未见集。400 份留出原票提供较大规模的阶段比较，但不能据此保证极低的生产错误率。

划分规则：

- 先划分原票组，再制作衍生 Case；Gold、业务包及衍生实例继承用途。
- 同一原票及近重复组不跨用途；相关组冲突通过版本化调整处理。
- 已用于调优的验收成员不再视为未暴露样本。
- 核验人员可以制作验收答案，但答案不能进入被测系统或调优过程。
- 当前候选划分须完成近重复及暴露审查才能冻结。
- 相同模板可能跨集合；报告明确区分原票留出和未见模板测试。
- 剩余 1,702 份原票作为补样和探索池，不自动具有可评分答案。

用例实例按开发/回归/验收分配为 3,016/1,008/1,976；这不是独立原票配额。已有对话暴露记录仅能证明：000001 为开发用途，001414、001500、002500、003014 对应原票未进入本批核验集。该记录不能替代全量暴露审查。

## 五、九类数据的具体制作方法

### 5.1 发票来源集：2,902 份

每个样本保留以下白名单内容：

| 文件 | 用途 |
|---|---|
| `original.jpg` | 原票证据和人工复核 |
| `content.json` | 主要解析输入，包含文字、表格及版面 |
| `content.md` | 人工阅读和展示 |
| `pages.json` | 按页读取和定位 |
| `assets/images/` | 解析实际引用的局部图片 |
| `metadata.json` | 重建来源、解析身份和文件摘要 |

根 `manifest.json` 记录版本、样本和来源别名。不原样迁入 Obsidian 导航 `invoice.md`、旧 `snapshot.json`、`record.json`、`parse.json`、`receipt.json`；必要来源信息提取到新元数据，旧绝对路径及答案不进入产品包。

接收标准：全部文件可读、摘要匹配、引用可解析、来源可追溯、没有标签混入。文件就绪与 OCR 正确性分别记录。

### 5.2 字段抽取与证据核验：1,200 个用例及 1,200 份核验结果

每份原票对应一个完整抽取用例，不拆成几十个字段实例来扩充样本数。

#### 核验内容

| 层级 | 内容 |
|---|---|
| 票头 | 票号、开票日期、适用时的到期日期 |
| 买卖方 | 名称、地址、票面可见的税务身份信息 |
| 金额 | 币种、未税金额、税额、总额、票面可见的折扣 |
| 明细 | 描述、数量、单位、单价、行金额、税率和税额 |
| 证据 | 页码、解析块、原图位置、票面与解析的一致性 |

提供方字段表没有定义的字段仍可能与业务有关，按原票和当前业务契约决定是否补充。

每个字段区分候选值、票面原始表示、经确认的规范值、值状态、证据、解析是否包含、核验人、时间及版本。值状态至少区分：已确认有值、票面未提供、无法辨认、存在多种解释、不适用、尚未核验。“尚未核验”不能写成“票面未提供”。

#### 制作步骤

1. 打开原图及当前被测模式允许读取的解析。
2. 检查候选，不预设提供方答案正确。
3. 核对票头、买卖方和金额。
4. 逐行核对明细，保留原行对应关系。
5. 检查日期、小数、币种解释。
6. 复核行合计、税额和总额，记录冲突。
7. 补充实际证据位置。
8. 保存真实核验身份、时间和版本。
9. 达到复核条件后发布可评分 Gold。

自动文本匹配得到的位置只算候选。坐标体系不明时保留原坐标和解析引用，不自行假设像素换算关系。

#### 复核与接收

1,200 份均需真实人工核验。验收集及金额、币种、身份存在歧义的样本优先由第二人复核；尚未完成第二人复核时保持单人状态。无法确定值时可以确认“歧义”或“无法辨认”，不能强填。证据不足的样本保持不可正式评分。

逐字段正确性、明细对应、关键字段全部正确的整票比例、无依据补值、来源支持性以及缺失/歧义处理分别评分。解析遗漏与模型推理错误分开分析。

### 5.3 模拟业务资料集：600 套

#### 为什么补充

原票不能证明供应商登记状态、适用订单、收货事实、历史录入、审批权限、目标接收结果或 ERP 回写状态。这些作为独立模拟业务环境资料提供。

| 组成 | 必需内容 |
|---|---|
| 模拟结构化发票 | 独立模拟票号、日期、币种、明细、金额 |
| 供应商 | ID、名称、别名、有效状态 |
| 采购订单 | ID、供应商、币种、行项目、状态 |
| 收货记录 | 订单及明细关联、已收货数量、确认状态 |
| 历史录入 | 基础可为空；重复及恢复场景按需配置 |
| 审批初态 | 当前修订、请求状态、有效授权范围 |
| 目标系统 | 本地模拟 B2B、ERP 台账及响应条件 |
| 模拟政策 | 匹配、精度、审批额度、异常规则 |
| 来源说明 | 哪些名称来自候选，哪些字段人为构造 |

#### 两条测试链分开

当前资料中的数量、单价、税率、金额和业务状态是合成的，名称或描述可能参考原票候选。因此：

1. **原票理解链**读取原图及解析，使用核验后的原票答案评分。
2. **模拟业务链**读取模拟结构化发票和配套资料，验证匹配、审批、提交和恢复。

模拟金额不能用作原图抽取答案，两条独立成绩不能拼成原票端到端成功率。以后制作连续链路时，需要逐项核对上下游字段并明确人工修订位置。

#### 基础包及异常变化

基础发票、订单和收货应自洽，金额按十进制计算；不能有未声明的历史成功记录，也不能因为资料已生成就默认审批成立。异常通过 Case 改变供应商候选、收货数量、订单价格、历史记录、审批及目标响应，不复制完整包。

沿用 `fixture-policy-v1`：USD、两位小数及明确舍入、金额容差 0.01、模拟审批角色额度 10,000.00；数量不符、供应商缺失/多候选、币种缺失转人工；提交需有效审批；UNKNOWN 先查询；B2B 成功不代表 ERP 成功；写操作仅在本地模拟目标发生。

接收时检查十进制算术、关联 ID、状态一致性、来源标记及不存在隐含审批。业务合理性复核与自动算术检查分别记录。

### 5.4 校验与业务匹配集：1,000 个

沿用 **18 个场景族**，每族约 55–56 个初始实例：供应商精确/别名/无候选/多候选/停用/版本变化，订单缺失/供应商不符/关闭，收货不足、单价冲突、行合计与票头冲突、十进制正常匹配、历史成功/未知、政策明确允许非订单票、模拟验真未知/无效。

制作流程：引用基础包 → 声明变化条件及关联对象 → 计算预期差额或候选数 → 定义继续、转人工、阻断或待核对的终点 → 指定原因及证据。

例如发票数量 10、收货数量 8，预期识别差额 2 并请求复核，不得自行改票为 8 后继续。审查是否存在未声明的额外冲突、判据能否由输入和政策推导、是否区分无匹配与查询失败、不适用是否有依据，以及是否将匹配成功错误地当作写授权。

### 5.5 人工复核与审批集：600 个

沿用 **16 个场景族**，每族约 37–38 个实例：修订并保留原预测、等待补充、拒绝旧修订命令、重复命令幂等、有效角色批准冻结载荷、额度内外、拒绝/撤销/过期、审批后改金额/附件/目标组织、复核角色不能替代审批、B2B 授权不扩展 ERP、人工接管边界。

每例初态明确当前修订和冻结载荷摘要、可信主体及角色、授权对象/范围/有效期、等待事项、人工命令、受控时钟及旧审批历史。这些是模拟初态，不是已经发生的真人操作记录。

额度边界至少覆盖 **9,999.99、10,000.00、10,000.01**；数值边界和角色权限分别测试，小额不能被解释为无需审批。

评分检查命令是否作用于正确修订、历史是否保留、修改后审批是否失效、无权主体是否被拒绝，以及复核和审批是否区分。

### 5.6 提交与 ERP 闭环集：1,000 个

沿用 **20 个场景族**，每族初始 50 个实例：正常提交回读、已接受但响应丢失、未知且查询不可用、权威未发生后重试、非权威空搜索、重复点击、无审批/载荷变更/目标变更、登录失效/MFA、附件拒绝、回读金额不符、发送前后崩溃、ERP 正常/独立重试/响应丢失/授权不足、停写期间只读核对。

故障必须明确发生窗口：发送前、目标接收前、目标已生效但响应未返回、响应返回但本地未持久化、B2B 已确认但 ERP 未完成。“网络出错”不足以构成可复核场景。

判定依赖持久动作身份、实际请求、模拟目标台账、查询回读、ERP 独立状态和最终业务状态；不能只凭页面提示或 Agent 完成声明。

硬判据：不重复有效动作；UNKNOWN 不盲重提；必需 ERP 未完成不能宣称业务完成；恢复不能使旧授权获得新权限。正确等待核对或人工处理属于正确结果，但不计入自动业务完成。

### 5.7 Agent 运行与恢复集：1,000 个

沿用 **24 个场景族**：装载核验、启动屏障、Provider 错误/中止、工具参数/超时/截止时间、用量未知、重复事件、追加/方向调整/旧绑定、会话续接/损坏历史、旧上下文/缺失事实/当前纠正、原生压缩/失败、资源版本、扩展初始化、子 Agent 建议/取消/共享预算、Host 重连/旧代次消息。

这类独立于业务准确性：简单票也可能会话串用或取消失效，运行稳定也不证明抽取正确。

依实际阶段契约定义命令、事件、故障。原生 Session/压缩用例必须由真实 SDK 形成历史和事件，不能手写成功历史。需要模型的场景使用已配置评测 Provider；纯机制故障可用明确标记的模拟响应。大量重复定义按语义场景去重报告；新增并发、时序、上下文、故障差异才增加机制变化。

### 5.8 权限隔离与不可信输入集：800 个

沿用 **17 个场景族**：合法票据/受控文本/上下文读取、合法查询/子 Agent 窄读、跨任务/跨空间/未选中资料、Gold/标签访问、路径上跳/链接越界、票据指令注入、工具结果索取秘密、子 Agent 扩权、用户伪装管理员、旧授权冲突当前撤销。

每例明确不可信入口、试图越过的信任边界、受保护对象、可信授权初态、真实触发、允许/拒绝判据、泄漏检查证据及合法对照。

合法对照必须实际运行，其最早阶段不能晚于攻击例。不能通过全拒绝取得高安全分。秘密使用合成哨兵，不读取真实凭证；受保护目标不能进入获准输入清单。仅需票据文本的例子引用解析副本，其余机制使用最小独立夹具，避免无关原票进入测试。

### 5.9 平台与评测设施集：400 个

沿用 **16 个场景族**，每族初始 25 个实例：摘要不符、图片缺失、JSON 损坏、重复导入、默认空间持久化、导入公共组装不启动、版本变化使旧结论失效、评分器正例/反例/缺证据、同票跨集合、等待事项展示、CLI/桌面控制者竞争、备份恢复、迁移失败、报告分母。

这类确保其他成绩有可信基础，尤其防止将缺证据当通过或漏掉失败分母。使用最小合成文件、状态和事件；仅发票接入例需要发票格式。评分器正例、负例、缺证据例分别制作，合成观测只能用于评分器自检，不能当产品运行证据。重复项不增加独立平台覆盖。

## 六、统一用例骨架与运行边界

| 项目 | 必需内容 |
|---|---|
| 身份 | ID、版本、类别、场景族、语义场景键 |
| 来源 | 原票、业务包、项目规范或模拟政策依据 |
| 输入 | 用户目标或机制触发、获准资料 |
| 初始环境 | 事实、身份、权限、历史、目标初态 |
| 场景变化 | 修改对象、时机、关联一致性 |
| 预期结果 | 正确值、合法终点、允许行为 |
| 禁止行为 | 重复提交、无依据补值、越权等 |
| 证据要求 | 输入、调用、状态、回执和来源 |
| 评分方式 | 字段比较、确定性断言、人工核验 |
| 依赖 | 最早阶段、能力、适配器、评分器 |
| 生命周期 | 材料、核验、执行资格、运行状态分别记录 |
| 用途 | 开发/回归/验收及原票组 |

初态不能包含未来结果。“目标接受请求后丢弃响应”可以是故障配置；“本次成功且只提交一次”必须由执行证据证明。

声明式 `scenarioSetup` 经适配器物化为隔离环境中的文件、台账、时钟、权限及故障行为，才可执行。适配器未实现时，材料即便审查通过也不是可执行用例。物化不能把 Oracle 中的预期结果写入被测输入。

业务侧仅接收获准原票/解析、业务包 `/input` 中获准部分和授权初态。Gold、评分断言、预期动作数和成绩留在质量侧。真实产品执行、模拟机制检查、数据完整性检查分别标识，不混合分母。

## 七、制作批次、状态与版本管理

### 7.1 三个累计批次

| 批次 | 人工核验原票 | 业务包复核 | 用例审查 | 目的 |
|---|---:|---:|---:|---|
| 第一批 | 100 | 50 | 500 | 校准字段口径、结构和判据 |
| 第二批 | 500 | 250 | 2,500 | 扩大覆盖、处理主要缺口 |
| 第三批 | **1,200** | **600** | **6,000** | 完成预算内材料审查和发布 |

这些是累计数量。现有草案已达到完整预算，不需要重复生成三次。批次清单通过 ID 引用已有内容；后批包含前批，以原票和关联资料一致性为前提。

### 7.2 实施顺序

1. 核对来源、白名单及去重清单。
2. 完成近重复、选样和用途审查。
3. 校准首批人工核验标准。
4. 分批核验原票字段及明细。
5. 复核模拟政策和基础包。
6. 审查场景、预期结果及禁止行为。
7. 实现当前阶段需要的适配器和评分器。
8. 执行适用例，保留真实证据。
9. 根据结果形成回归、黄金、错题视图。

未来阶段可以提前备料，但不算当前阶段已通过。人工核验和生产能力缺失时，完成可独立推进的资料及工具工作，并在清单记录依赖，不伪造完成。

### 7.3 状态分开管理

| 维度 | 状态示例 |
|---|---|
| 材料 | 草案、结构检查通过、内容已审查 |
| 字段核验 | 待核验、单人核验、复核完成、争议 |
| 执行资格 | 依赖未齐、可执行、正式验收可用 |
| 实际运行 | 未运行、运行中、通过、失败、证据不足、设施错误 |

不能通过批量翻转 `humanVerified` 或 `status` 跳过核验和发布。评审记录须具有身份、时间、来源版本、内容和证据；自动工具身份不能冒充人工。

### 7.4 版本和兼容

- 对外仅保留一套当前目录。文件内的资产身份、修订号和摘要固定内容；不另建版本后缀目录。
- 旧运行继续引用旧内容，不能被新答案覆盖。
- 实质变化记录修订原因；新旧核验结果通过版本记录保留。
- 清单固定具体版本，不只有不可追溯的“最新答案”。
- 原始图片不因版本变化重新复制。
- 检查器按当前生命周期核验候选、实际审核记录及父内容，不要求 Gold 永远处于待核验状态。
- 追加评审、冻结划分和形成集合视图需满足相应证据条件；旧版本不能静默就地改写。

## 八、验收、指标与结果解释

### 8.1 制作接收标准

| 层级 | 接收条件 |
|---|---|
| 来源 | 完整、摘要一致、引用有效、来源可追溯 |
| Gold | 真实核验身份、明确值状态、字段及明细证据 |
| 业务包 | 合成来源明确、算术和关联一致、业务复核状态明确 |
| Case | 输入、初态、判据、禁止行为、证据齐全 |
| 用途划分 | 原票组不跨用途、验收暴露状态可追溯 |
| 可执行性 | 对应能力、适配器和评分器实际存在 |
| 运行 | 真实执行证据；未运行或缺证据不记通过 |

数量达标不等于内容和产品验收达标。

### 8.2 分项报告

按类别及场景族报告实际执行数、独立原票数、去重场景数、重复运行数、正确完成/拒绝/转人工、错误继续/拒绝/重复动作、证据不足、设施错误，以及适用时的耗时、用量和重试。

未运行、依赖未齐、证据不足和设施错误分别列出，不静默从分母移除。正确转人工不等于自动完成；安全全拒绝必须被合法对照识别。

### 8.3 覆盖分布与真实业务分布

当前异常被主动增加，是覆盖导向样本。场景均衡成绩说明已覆盖条件下的能力；异常集说明边界和恢复能力。取得实际业务频率后才能另算业务分布加权成绩，不能从模拟异常比例推断生产自动化率。

重复运行衡量稳定性，不增加独立样本。按原票或相关组分析，避免把同票多情境当成独立统计样本。

### 8.4 黄金集、错题集、挑战集

- **黄金集**：实际执行并核验后，有代表性的合格表现及标准。
- **错题集**：已确认失败，保留正确标准、原因及修复后运行。
- **挑战集**：具有明确判据的困难或边界场景。

集合通过清单引用，不复制 Case。正确拒绝、正确等待核对、正确请求人工均可成为合格样例。错题修复后仍保留历史失败；未执行草案不自动进入黄金集。

## 九、使用与检查

### 9.1 当前数据入口

日常使用无需选择历史发布号：

```powershell
python agent-eval/tools/verify_invoice_data.py --project .
python agent-eval/tools/review_invoice_data.py --project . inspect
python -m unittest discover -s tools -p "test_invoice*.py" -v
python -m unittest discover -s agent-eval/tests -v
```

全量检查验证产品原票、解析、引用、摘要、质量清单、数据配额、关联分组、算术、检查项、需求映射及审核状态。工具自检只证明制作与评分设施的被测行为，不计入 6,000 个产品用例的执行次数。

### 9.2 需求映射与实际缺口

`requirements.json` 固定两份主方案的实际摘要和评测条目原文位置，包括 MOD、RT、RTC、RTX、Driving Task 及关键横切条款。`coverage.json` 按检查项引用这些条目。已有原子判据只记为部分准备；未映射条款、尚未准备的 F/A/B 变体、未实现规则和运行适配器明确保留缺口。不能因挂上一个 MOD 标签而声称整个模块覆盖。

安全结果分别观察模型行为、平台控制和实际后果。合法对照独立运行，同用途和同操作条件由配对清单固定；单独填写“对照通过”无效。必要硬约束失败保留失败，其他缺失项仍列出；未实现必要规则或证据不足不能记为整例通过。

### 9.3 实际人工审核

按 `manifests/audit/batches.json` 的三个累计批次开展审核。综合任务单包含 Gold、模拟资料与 Case；`manifests/review-queue.csv` 是原票选择入口。现有 `review-forms/` 是字段草表，不含人工身份；正式提交使用按需导出的完整审核表：

```powershell
python agent-eval/tools/review_invoice_data.py --project . export-form --kind gold --asset 000001 --output review-gold.json
python agent-eval/tools/review_invoice_data.py --project . export-form --kind business --asset business-000001 --output review-business.json
python agent-eval/tools/review_invoice_data.py --project . export-form --kind case --asset approval-00005 --output review-case.json
python agent-eval/tools/review_invoice_data.py --project . export-form --kind policy --asset fixture-policy-v1 --output review-policy.json
python agent-eval/tools/review_invoice_data.py --project . submit --review review-gold.json
```

最后一条只能在实际审核者完成表格后执行。表格要求目标摘要、Owner、真实审核声明、检查项、证据、暴露审查、争议与裁决；Gold 还要求逐字段和明细的原图核对。审核人的身份仍是提交者声明，工具未提供企业身份认证。空表、简单状态翻转和未解决争议不得被接收为已通过。

接收记录保存于 `manifests/reviews/<recordId>.json`，其中留存父内容和摘要；当前资产沿用稳定路径并递增修订。记录目录在首次真实提交时才建立。审核通过不自动获得阶段验收资格。

### 9.4 离线夹具与真实执行

`manifests/materialization/cases.jsonl` 为每个 Case 记录当前文件摘要和物化状态；`fixtures.jsonl` 保存可构造的输入及模拟器配置，`report.json` 汇总适配器缺口。原生 Session、压缩、Host 等要求真实产品或 SDK 的场景不手写成功历史。

真实执行器需要注册可信证据采集适配器。评分入口核对 Case、修订、Run、文件摘要和受信来源，再按必要检查逐项评分。普通 JSON 自称 `product_run` 无效；`grader_self_test` 的合成观测始终只用于设施自检。

### 9.5 更新与精简原则

`prepare_invoice_data.py` 用于首次来源导入，已有根目录拒绝覆盖。`finalize_invoice_data.py` 将检查通过的机器草案整理到项目内部暂存目录；检查完成后才替换当前质量目录。它不会删除原图，也拒绝把真实人工审核或运行记录作为旧草案清理。旧机器准备中的有效修订已经合并，目录不按批次或发布号并列保存。

需要重新生成审计或物化时，先在暂存目录构造，检查依赖摘要并刷新统一清单，最后受控替换。不得直接改数据再批量刷新摘要以掩盖未知改动。已经发生的真实审核和运行历史保持可追溯。

### 9.6 本次交付核验结果

2026-09-15，正式目录的全量检查返回 `file_and_reference_checks_passed`：产品文件 19,377 个，质量文件 11,849 个；2,902 份唯一原票、1,414 份来源标签、1,200 份核验候选、600 套业务资料和 6,000 个用例。用例包含 186 个场景族、3,939 个语义键及 2,061 个额外重复实例。410 个攻击例绑定独立合法对照，合法对照共 390 个。重复分配不增加独立业务覆盖。

离线夹具为 2,633 个，其余 3,367 个保留明确物化依赖。221 个需求条目中，126 个已有部分检查准备，95 个未形成对应检查覆盖；没有条目被宣称整体通过。当前人工核验数、真实产品运行数及正式验收通过数均为 0。

56 项数据工具测试和 40 项评分/夹具设施测试通过，共 96 项；这些测试不计入产品用例运行次数。当前修订后的用例沿用稳定文件名，递增文件内修订号并保存此前内容摘要。

| 目录或文件 | 作用 |
|---|---|
| `data/invoices/voxel51/` | 唯一产品来源包；索引、去重别名及每票原图和解析 |
| `<sampleId>/assets/images/` | 只保存解析实际引用的局部图片 |
| `agent-eval/data/source-labels/` | 提供方原始标签及来源映射，不能直接充当 Gold |
| `gold/` | 原票字段与明细候选、实际核验后的当前答案 |
| `business/` | 独立模拟发票、订单、收货、审批初态和系统资料 |
| `cases/extraction/` | 全票字段、明细和来源核验 |
| `cases/matching/` | 规则、供应商、订单、收货及重复识别 |
| `cases/approval/` | 人工复核、修订、审批与接管 |
| `cases/submission/` | B2B、权威确认、ERP 和故障恢复 |
| `cases/runtime/` | 工具、会话、上下文与运行机制 |
| `cases/isolation/` | 越权、不可信输入和独立合法对照 |
| `cases/platform/` | 数据接入、平台、日志和评测设施 |
| `manifests/` | 单一当前清单、配额、成员、政策和需求覆盖 |
| `inventory.json` | 所有质量文件的唯一路径、大小和摘要清单，排除自身 |
| `preparation-report.json` | 数量、准备状态及未完成事项 |
| `requirements.json` / `coverage.json` | 需求原文锚点与原子检查级覆盖、缺口 |
| `splits.json` / `views.json` | 开发/回归/验收成员，以及阶段、Benchmark、黄金集和错题集引用 |
| `case-catalog.json` / `fixture-policy.json` | 当前场景索引和独立模拟政策 |
| `review-forms/` | 待填写的原票字段草表，其他审核表按需导出 |
| `audit/` | 可复查的机器特征、近重复线索和累计审核任务单 |
| `materialization/` | 可构造的离线夹具和不可构造原因，不包含伪造执行成绩 |
| `runs/` | 只在实际执行后新增 Run 证据和报告 |
| `agent-eval/src/runner/` | 离线物化、模拟目标、可信证据加载等公共设施 |
| `agent-eval/src/graders/` | 按能力复用的逐项评分，缺失规则阻断通过 |
| `agent-eval/tools/` | 来源整理、当前数据合并、映射、审计、审核与检查工具 |
| `docs/` | 详细制作方案、发现的问题及当前修订要求 |

`manifests/reviews/`、`runs/<runId>/` 和 `agent-eval/benchmarks/` 仅在真实记录或协议产生时创建。产品运行结果保存到产品运行根，不回写固定来源。原票不按用途复制，Case/Gold 不按 P0–P13 或 BM 复制，业务 Agent 只接收当前用例获准的输入投影。
