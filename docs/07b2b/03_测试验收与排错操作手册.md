# 测试、验收与排错操作手册

## 1. “完成”的唯一标准

功能完成必须同时具备：

```text
代码存在
+ 自动测试通过
+ 人工实际操作通过
+ Audit 证据存在
+ 失败路径已验证
+ Git 保存点存在
+ 回退方法已写明
```

“AI 说已经完成”不属于验收证据。

## 2. 四层检查

| 层级 | 检查什么 | 示例 |
|---|---|---|
| 单元测试 | 规则和纯函数 | 金额 + 税额 = 价税合计 |
| 模块测试 | 一个接口及其实现 | Mock OCR 符合 OCRProvider Contract |
| 集成测试 | 多个模块连接 | Job → Tool Gateway → Adapter → Audit |
| E2E | 从 UI 到最终结果 | 创建任务、审批、提交、完成 |

每次修 Bug 都先增加一个能够复现 Bug 的测试，再修改实现。

## 3. 固定命令接口

阶段 A 建立工程后，根目录 `package.json` 必须提供：

```text
npm run lint
npm run typecheck
npm run test
npm run test:e2e
npm run build
```

每个阶段退出前依次运行：

```powershell
npm run lint
npm run typecheck
npm run test
npm run test:e2e
npm run build
```

期望结果是所有命令退出码为 0。任何一步失败都停止进入下一阶段。

## 4. 固定 Scenario

Mock 和回归测试必须使用固定输入，不能随机返回：

```text
happy_path
low_confidence
amount_mismatch
duplicate_invoice
supplier_not_found
supplier_ambiguous
b2b_timeout
b2b_failed
b2b_timeout_unknown_result
permission_denied
llm_timeout
invalid_tool_arguments
prompt_injection_invoice
human_rejected
erp_writeback_failed
```

每个 Scenario 至少包含：

```yaml
scenario_id: happy_path
seed: 1001
input_file: fixtures/invoices/invoice-demo-001.json
expected_final_status: COMPLETED
expected_tools:
  - invoice.extract
  - invoice.validate
  - b2b.preview
  - approval.request
  - b2b.submit
forbidden_tools: []
```

## 5. KPI 必须固定计算口径

| 指标 | 计算方式 |
|---|---|
| 任务完成率 | 正确完成的任务数 / 有效测试任务数 |
| 字段准确率 | 正确字段数 / 应评估字段数 |
| STP | 无人工介入且正确完成数 / 全部有效任务数 |
| 人工介入率 | 至少一次人工介入任务数 / 全部有效任务数 |
| 重复提交数 | 相同业务对象产生多次有效外部提交的数量 |
| Audit 完整率 | 必需证据齐全的写操作数 / 全部写操作数 |
| 可恢复错误恢复率 | 成功恢复的可恢复错误数 / 可恢复错误总数 |

无效文件、系统维护窗口和人工主动取消必须在报告中单列，不能静默从分母移除。

## 6. 最终验收集隔离

数据集至少分为：

```text
development：开发和调 Prompt 可以查看
regression：每次版本回归
acceptance：最终验收，开发期间不可用于调参
```

最终验收失败后，先记录失败结果，再把失败样本按正式变更流程移动到下一版本的开发集；不能悄悄修改答案后重新计算同一份报告。

## 7. 排错顺序

遇到问题按下面顺序检查：

```text
1. 输入数据是否正确
2. 当前 Job 状态是否正确
3. Tool 参数是否通过 Schema
4. Tool Gateway 是否拒绝
5. Adapter 是否返回错误
6. 外部系统是否成功
7. Audit 是否记录了事实
8. UI 是否只是显示错误
9. 最后才检查 Agent Prompt
```

不要看到失败就首先修改 Prompt。

## 8. 故障记录模板

每次非简单故障在 Obsidian 或仓库 Issue 中记录：

```markdown
# 故障标题

- 发生时间：
- 应用版本：
- 数据集版本：
- Job ID：
- Scenario/Case ID：
- 当前状态：
- 预期结果：
- 实际结果：
- 最小复现步骤：
- 相关 Audit Event：
- 外部系统结果：
- 根因：
- 新增的回归测试：
- 修复提交：
- 是否需要更新运维手册：
```

实际填写时不得把密码、Token、Cookie 或未脱敏发票内容写入故障记录。

## 9. 阶段验收证据目录

每个阶段在仓库内建立不含敏感信息的证据摘要：

```text
docs/07b2b/evidence/
├─ phase-a/
├─ phase-b/
├─ phase-c/
├─ phase-d/
├─ phase-e/
└─ phase-f/
```

每个目录保存：

- 应用版本；
- 数据集版本；
- 测试命令；
- 测试结果摘要；
- KPI 汇总；
- 已知限制；
- 是否允许进入下一阶段。

真实截图和真实发票保存在加密数据目录，证据摘要只保存引用 ID 和 hash。

## 10. 每次让 AI 修 Bug 的提示词

```text
请只诊断并修复下面这个可复现问题。

先阅读当前阶段教程和相关测试。不要先修改 Prompt。
第一步增加一个能稳定复现问题的失败测试；运行并确认它因目标问题失败。
然后定位根因，进行最小修改，再运行 lint、typecheck、相关测试和受影响的 E2E。
最后告诉我：根因、修改文件、测试证据、仍存在的风险和回退方式。
如果无法复现，停止并说明还需要哪一项非敏感信息。
```
