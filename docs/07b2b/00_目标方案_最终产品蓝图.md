# Flowmate 目标方案：最终产品蓝图

> 版本：V1.0 目标基线  
> 适用对象：一名依靠 Vibe Coding 独立开发、测试、部署和维护的开发者  
> 本文回答：**最终要建成什么。** 具体怎么一步步建，由总导航、DATA 流水线和 A～G 阶段教程负责。

## 1. 一句话目标

Flowmate 是一个以 Pi SDK 为 Agent Runtime、以确定性业务控制和人工兜底为安全骨架的单机企业数字员工平台；它的第一位数字员工负责把真实发票安全地录入 07B2B，并将结果回写业务系统、保存完整审计证据。

它不是聊天机器人，也不只是一个自动点网页的脚本。

## 2. 最终业务结果

最终系统要稳定完成：

```text
接收真实发票或待办任务
→ 读取 PDF/OFD/图片/XML
→ 提取并标准化发票字段
→ 执行确定性业务规则
→ 查询供应商、PO、收货或合同
→ 识别正常、异常和高风险情况
→ 必要时请求人工复核或审批
→ 登录并填写 07B2B
→ 提交并确认最终状态
→ 回写 ERP/财务系统
→ 保存字段、规则、工具、审批、截图和外部结果
→ 完成任务或安全转人工
```

最终价值不是“AI 能做一次”，而是：

- 正常任务减少重复人工录入；
- 异常任务可以解释并转人工；
- 未授权动作无法执行；
- 重启或崩溃后任务不会丢失；
- 超时后不会造成重复业务提交；
- 每次执行都能追踪、复核和恢复；
- 唯一维护者能够独立部署、备份、回滚和排错。

## 3. 第一版使用者

第一版只服务三类角色，不建设复杂 RBAC 后台：

| 角色 | 使用系统做什么 | 明确不能做什么 |
|---|---|---|
| 操作员 | 创建任务、查看状态、处理人工复核、接管页面 | 读取原始密钥、修改系统安全策略 |
| 审批人 | 审核高风险提交、批准或拒绝 | 自己创建并批准同一个高风险动作 |
| 唯一维护者 | 配置、部署、排错、备份、恢复、升级 | 绕过业务授权或隐瞒失败记录 |

在小规模试点中，同一个现实人员可能兼任这些角色，但系统仍必须分别记录“发起、复核、批准、维护”动作。

## 4. 第一版范围

### 4.1 必须交付

```text
1 个数字员工：07B2B 发票录入员
1 条确定性主流程：发票录入
1 个 07B2B 平台

1 个生产运行实例
1 套真实数据资产库
```

- 多租户 SaaS；
- 多 Agent 编排；
- 多 B2B 平台；
- Kubernetes、Kafka、Redis；
- 微服务；
- 图形化 Workflow Designer；
- Agent/Skill/插件市场；
- 自研 LLM Provider；
- 自研 Agent Loop、Streaming、Compaction、Session Runtime；
- 绕过验证码、MFA、扫码或平台安全机制；
- 无人工兜底的全量自动写入；
- 以 Obsidian 代替生产事务数据库。

### 4.3 固定技术栈

第一版统一采用：

```text
TypeScript
React
Electron
npm workspaces
Pi SDK
Zod
SQLite
Vitest
Playwright Test

```

依赖安装和工作区管理统一使用 npm，提交 `package-lock.json`；阶段教程不得再引入第二套包管理器。

## 5. 最终产品界面

最终 Electron 应用至少包含以下页面：

### 5.1 任务中心

展示：

```text
待处理
执行中
需要人工
等待审批
结果未知
失败待处理
已完成
已取消
```

支持创建、启动、暂停、恢复、取消和受控重试。

### 5.2 任务详情与执行驾驶舱

同一页面展示：

- 原始发票预览；
- OCR 原始字段、标准字段、置信度和来源；
- 供应商、PO 和业务规则结果；
- 当前 Job 状态；
- 结构化 Agent Timeline；
- Tool 调用和结果摘要；
- 07B2B 填表预览和关键截图；
- 人工修改、审批和接管入口；
- B2B、ERP 最终结果；
- Audit 证据索引。

界面不展示模型完整思维链，只展示可以审计的结构化执行事实。

### 5.3 人工复核中心

处理：

- OCR 低置信度；
- 金额或税额冲突；
- 必填字段缺失；
- 供应商无匹配或多个匹配；
- PO 不存在或余额不足；
- 重复、作废、红冲发票；
- 业务规则无法自动决定。

每次修改保存 before、after、reason、时间和操作者角色。

### 5.4 审批中心

处理：

- 07B2B 真实提交；
- ERP 真实回写；
- 高金额；
- 新供应商；
- 业务定义的其他高风险动作。

Approval Token 必须绑定 Job、动作摘要、有效期和一次使用。

### 5.5 系统设置与健康页

展示：

- 当前运行模式；
- 应用、数据库、数字员工、Prompt、Tool、Workflow、Dataset 版本；
- ModelProfile，不显示密钥；
- 外部系统健康状态；
- Kill Switch；
- 备份状态；
- 告警和凭证到期提示。

## 6. 最终生产运行模型

一次任务的权威流程为：

```text
用户或真实 Invoice Source
        ↓
创建 InvoiceJob
        ↓
Flowmate Kernel 检查状态和当前目标
        ↓
创建 AgentRun
        ↓
AgentRuntime Interface
        ↓
Pi Runtime
        ↓
Agent 请求调用 Tool
        ↓
Tool Gateway
        ↓
Schema / Job State / Permission / Risk
Run Mode / Approval / Idempotency / Kill Switch
        ↓
Adapter Interface
        ↓
OCR / Supplier / PO / Verify / B2B / ERP
        ↓
返回外部事实
        ↓
Flowmate Kernel 更新状态
        ↓
Audit / Timeline / Metrics
        ↓
Completed、Needs Review 或 Failed
```

高风险动作额外经过：

```text
Agent 请求动作
→ approval.request
→ WAITING_APPROVAL
→ 人工查看真实动作摘要
→ 批准或拒绝
→ Tool Gateway 再次校验
→ 执行一次真实写入
```

## 7. 最终目标架构

```text
┌───────────────────────────────────────────────┐
│ Electron + React 产品体验                    │
│ Task Center / Cockpit / Review / Approval     │
├───────────────────────────────────────────────┤
│ Flowmate Kernel                               │
│ Job / Workflow / State / Policy / Idempotency │
├───────────────────────────────────────────────┤
│ Enterprise Tool Gateway                       │
│ Schema / Risk / Approval / Mode / Audit        │
├───────────────────────────────────────────────┤
│ AgentRuntime Interface                        │
│ EmbeddedPiRuntime 或经验证需要的隔离 Adapter  │
├───────────────────────────────────────────────┤
│ Pi SDK                                        │
│ ModelRuntime / AgentSession / Loop / Tools     │
│ Session / Resource / Skills / Extensions      │
├───────────────────────────────────────────────┤
│ Enterprise Adapter Interfaces                 │
│ Invoice / OCR / Verify / Supplier / PO         │
│ B2B / ERP / Credential / Audit Storage         │
└───────────────────────────────────────────────┘

旁路数据资产：
Obsidian Vault → Dataset Tools → Versioned Manifest → Eval/Regression

业务事实存储：
SQLite → Job / Run / Tool / Approval / Audit / External Result
```

### 7.1 为什么采用这个形状

每个主要 Module 只暴露一个清晰 Interface：

- UI 只使用 Flowmate 事件和命令；
- Kernel 不依赖 Pi 类型；
- Pi Runtime 不决定业务最终状态；
- Tool Gateway 是所有企业动作的唯一安全 seam；
- Mock 和 Real Adapter 满足同一个 Interface；
- Obsidian 不参与生产事务写入。

这样可以先用 Mock 快速开发，再逐个替换为 Real Adapter，而不重写业务核心。


关系：


## 10. 唯一正式状态机

正常状态：

```text
CREATED
→ EXTRACTING
→ EXTRACTED
→ VALIDATING
→ VALIDATED
→ MATCHING
→ MATCHED
→ PREPARING_SUBMISSION
→ WAITING_APPROVAL
→ SUBMITTING
→ SUBMITTED
→ VERIFYING
→ COMPLETED
```

异常状态：

```text
NEEDS_REVIEW
PAUSED_FOR_HUMAN
RETRY_WAIT
UNKNOWN_COMMIT_STATE
FAILED
CANCELLED
```

阶段 A 可以只走其中一部分，但不能创建第二套名称。Agent 不能直接把 Job 改为 `COMPLETED`，只能通过受控 Tool 请求 Kernel 执行合法状态变化。

## 12. 最终真实系统

生产执行路径需要以下 Real Adapter：

| 能力 | 最终真实来源 | 无法使用时的安全降级 |
|---|---|---|
| Invoice Source | 财务系统、发票池、邮件、共享目录或受控接口 | 暂停新任务或人工导入 |
| OCR/Parser | XML/OFD/PDF Parser、获准 OCR Provider | 备用 Provider 或人工复核 |
| Invoice Verify | 企业发票验真平台或获准服务 | 转人工，不自动提交 |
| Supplier | ERP/SRM/MDM | 转人工匹配 |
| PO/收货/合同 | ERP、采购或数据中台 | 转人工，不猜测 |
| 07B2B | 正式接口或获准 Playwright 自动化 | Kill Switch + 人工录入 |
| Credential | 受控 Secret Store、机器人账号 | 停止自动登录 |
| ERP WriteBack | 正式接口、ESB 或获准集成方式 | Outbox 保留并转人工 |
| Audit Storage | 加密本地或企业批准存储 | 停止生产写入 |
| Monitoring | 本地健康检查和获准告警通道 | 降低流量并人工巡检 |

生产执行路径不使用 Mock；Mock Adapter 和固定 Scenario 必须继续保留在开发与回归环境。

## 14. Obsidian 数据资产库目标

Obsidian 只承担人可读的数据控制台：

```text
数据来源登记
授权和保存期限
发票案例卡片
标注和业务复核进度
异常分类与业务规则
系统接入清单
Dataset Release 看板
故障案例与复盘
```

真实数据物理结构：

```text
D:\code\agent-learn\agent\FlowmateData\
├─ vault\                 Obsidian 数据卡片
├─ files\raw\            原始文件，只读
├─ files\sanitized\      脱敏开发副本
├─ labels\               expected.json
├─ manifests\            数据清单和 hash
├─ releases\             dataset-v0.x / v1.x
└─ backups\              加密备份
```

数据集发布后固定分为：

```text
development：开发和调试
regression：版本回归
acceptance：最终验收，开发期间隔离
```

Flowmate 测试程序读取发布后的 manifest，不直接把 Obsidian Markdown 当业务数据库。

## 15. 安全不变量

无论 Agent、Prompt 或外部页面如何变化，以下规则都必须由代码强制执行：

1. Agent 不获得原始密码、Cookie 或 Token；
2. Renderer 不读取密钥；
3. 高风险 Tool 未审批不能执行；
4. Shadow 模式禁止真实写入；
5. Canary 只允许白名单和批准流量；
6. Kill Switch 开启后禁止启动新写操作；
7. Unknown Commit 禁止自动二次提交；
8. 相同业务提交使用稳定 idempotency key；
9. Agent 不能直接修改业务最终状态；
10. 每个写操作保存意图、参数摘要、审批和外部结果；
11. 验证码、MFA、扫码和安全设备必须人工处理；
12. 真实数据不进入 Git；
13. 最终验收集不得用于修改 Prompt、规则或代码；
14. 外部系统权威结果优先于本地推测；
15. 无法安全自动完成时必须转人工。

## 16. 关键异常的最终处理

### 16.1 OCR 或规则不确定

```text
NEEDS_REVIEW
→ 人工查看原文和候选值
→ 保存 before/after/reason
→ 重新校验
→ 继续或拒绝
```

### 16.2 验证码、MFA 或未知页面

```text
PAUSED_FOR_HUMAN
→ 停止 Agent 页面操作
→ 人工接管
→ 系统验证恢复位置
→ Resume
```

### 16.3 B2B Submit 超时

```text
保存提交意图
→ 只发送一次 Submit
→ 响应未知
→ UNKNOWN_COMMIT_STATE
→ getStatus 查询权威结果
→ 已提交：SUBMITTED
→ 明确未提交：重新进入人工决定
→ 无法确认：保持暂停并升级人工
```

### 16.4 ERP 回写失败

```text
B2B 成功事实保持不变
→ WriteBack Outbox 保留
→ 受控幂等重试
→ 重试耗尽转人工
→ 不把 Job 误标为 B2B 未提交
```

### 16.5 唯一维护者不可用

```text
禁止新的高风险写入
→ 授权业务人员开启 Kill Switch
→ 停用机器人账号（必要时）
→ 切回人工流程
→ 保存 Job ID 和外部状态
→ 等待维护者或系统 Owner 处理
```

## 17. 单人生产部署目标

默认生产形态：

```text
1 台获准 Windows 工作站或受管服务器
1 个 Electron 应用实例
1 个 SQLite 业务数据库
1 个受控数据根目录
1 个专用机器人账号
1 套结构化日志与 Audit
1 套自动备份和恢复脚本
1 个 Kill Switch
```

阶段 A、B 使用 EmbeddedPiRuntime。

只有阶段 C 的连续任务和 Soak Test 证明 Electron 出现可复现的卡死、内存或崩溃隔离问题，才在同一台机器增加薄 Runtime 子进程。该 Adapter 只做进程隔离、命令映射、事件映射、健康检查和崩溃恢复，不重写 Pi Runtime。

只有当前单机实现出现经过测试证明的容量或可靠性问题，才评估 PostgreSQL、队列、Worker 或服务化。第一版不为假设中的规模增加基础设施。

## 19. 最终验收底线

最终具体阈值需要业务 Owner 正式确认；在确认前，项目采用以下不低于原方案的工程底线：

| 指标 | 最终底线 |
|---|---:|
| 关键数字字段准确率 | ≥ 98% |
| 允许自动化任务的提交成功率 | ≥ 95% |
| 稳定期 STP | ≥ 80%，高风险场景除外 |
| 未审批真实写入 | 0 |
| 严重错录 | 0 |
| 重复有效提交 | 0 |
| 非法状态跳转 | 0 |
| 写动作 Audit 完整率 | 100% |
| 任务可追踪率 | 100% |
| 可恢复错误自动恢复率 | ≥ 90% |
| Unknown Commit 自动二次提交 | 0 |
| 备份恢复演练 | 成功 |
| Kill Switch 演练 | 成功 |

指标报告必须记录应用版本、数据集版本、样本数量、分母口径、失败案例 ID 和已知限制。

最终验收必须使用来自真实生产分布、已经业务复核且冻结的 acceptance 数据；不能使用开发者自制 Mock 证明生产价值。

## 21. A～G 如何到达目标

| 阶段 | 只增加的主要不确定性 | 到达的目标能力 |
|---|---|---|
| A 全 Mock MVP | Agent、UI、Tool、状态机能否形成闭环 | 真实 Pi + 真实 LLM + Mock 外部系统 |
| B 真实 OCR | 真实文件能否稳定结构化 | 真实 Invoice/OCR/规则 + Mock B2B |
| C 真实测试环境 | 07B2B 是否可被安全操作 | 真实测试账号、页面、人工接管、截图 |
| D Shadow | 生产分布下的业务正确性 | 真实只读数据 + 人工结果对比 |
| E Canary | 少量真实写入的业务风险 | 白名单、审批、幂等、Kill Switch |
| F 正式交付 | 全链真实系统和可恢复上线 | 生产发布、验收和完整交付包 |
| G 单人运维 | 长期变化和唯一维护者风险 | 备份、恢复、升级、漂移和人工回退 |

DATA 流水线从 A 同时开始：

```text
DATA-01：Obsidian 数据资产库
→ DATA-02：真实数据采集、脱敏、标注和业务复核
→ DATA-03：校验、分割、冻结和版本发布
```

## 22. 目标完成定义

Flowmate 第一版只有同时满足以下条件才算达到目标：

```text
[ ] 一张真实发票可从真实来源进入系统
[ ] 真实 OCR/Parser 产生可追踪字段
[ ] 真实 Supplier/PO/Verify 可以查询
[ ] 低置信度和业务冲突能转人工
[ ] 真实 07B2B 可在授权下完成提交
[ ] Unknown Commit 不会产生自动重复提交
[ ] 真实 ERP 回写可恢复
[ ] 全过程 Audit 完整
[ ] Shadow 和 Canary 均通过
[ ] 最终 acceptance 数据集验收通过
[ ] 安装、备份、恢复和回滚演练成功
[ ] 唯一维护者不可用时业务可以切回人工
[ ] 生产执行路径不使用 Mock
[ ] 测试环境仍保留 Mock 和回归 Scenario
```

只完成其中某一项，例如“OCR 很准”“Agent 能调用 Tool”或“Playwright 能提交页面”，都不能称为最终交付。

## 23. 目标方案变更规则

本文是所有阶段教程的上游基线。以下变化必须先修改并重新审核本文，再修改阶段教程和代码：

- 增加新的数字员工或业务流程；
- 增加新的真实写操作；
- 修改正式状态机；
- 修改 Tool 风险和审批原则；
- 修改数据保存、授权或验收规则；
- 修改生产部署形态；
- 引入新的基础设施；
- 修改最终验收底线；
- 取消人工回退或安全不变量。

目标方案审核通过后，阅读顺序才调整为：

```text
目标方案
→ 项目总导航
→ 架构与术语
→ 环境与安全
→ 测试与排错
→ DATA 与 A～G 流水线
```
