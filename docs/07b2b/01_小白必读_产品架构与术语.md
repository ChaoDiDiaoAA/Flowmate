# Flowmate 产品架构与术语白话说明

## 1. 先记住一句话

```text
Pi 负责让 Agent 跑起来；
Flowmate 负责让它安全、可控地完成企业任务。
```

你不需要自己编写大模型循环、Streaming、上下文压缩或模型 Provider。你的主要工作是任务、规则、工具、安全、人工审批、真实系统连接和审计。

## 2. 一次任务如何运行

```text
用户创建 Job
→ Workflow 决定当前允许做什么
→ Pi Agent 判断下一步调用哪个 Tool
→ Tool Gateway 检查权限、审批、模式和重复提交
→ Adapter 访问 OCR、B2B 或 ERP
→ 返回结果
→ 状态机记录业务事实
→ Audit 保存证据
→ UI 显示结构化进度
```

Agent 可以建议动作，但不能跳过系统授权。

## 3. 常见词语

| 术语 | 白话解释 | 例子 |
|---|---|---|
| Job | 一张需要处理的业务任务单 | “录入发票 INV-001” |
| AgentRun | Agent 对某个 Job 的一次执行 | 第一次失败、第二次重试是两个 Run |
| Pi Session | Pi 保存的对话和工具调用上下文 | 不等于业务数据库 |
| Workflow | 固定业务步骤和允许的状态变化 | 校验完成前不能提交 |
| State Machine | 任务当前处于什么状态 | `WAITING_APPROVAL` |
| Tool | Agent 被允许调用的能力 | `invoice.validate` |
| Tool Gateway | 所有 Tool 执行前的安全检查站 | 审批、权限、幂等、Audit |
| Adapter | 对接某个外部实现的薄层 | Mock OCR、真实 OCR |
| Provider | 同一能力的具体提供者 | 阿里云 OCR、PaddleOCR |
| HITL | 人在关键步骤介入 | 低置信度复核、提交批准 |
| Shadow | 使用真实数据计算，但不真实提交 | 机器结果与人工结果对比 |
| Canary | 只给少量低风险任务真实写入权限 | 固定供应商、低金额、5% 流量 |
| Unknown Commit | 已发送提交请求，但不知道是否成功 | 超时后必须查状态，不能直接重试 |
| Golden Dataset | 输入和人工正确答案成对的数据集 | 发票 PDF + expected.json |

## 4. 只保留一套业务事实

业务事实必须保存在 Flowmate 数据库：

```text
InvoiceJob
→ AgentRun
→ ToolExecutionRecord
→ ApprovalRecord
→ AuditEvent
→ ExternalResult
```

Pi Session 只保存 Agent 上下文。即使 Session 损坏，Job、审批、外部提交结果仍必须存在。

## 5. 只保留一套正式状态机

完整状态机建议固定为：

```text
CREATED
→ EXTRACTING
→ EXTRACTED
→ VALIDATING
→ VALIDATED
→ MATCHING
→ MATCHED
→ PREPARING_SUBMISSION
→ WAITING_APPROVAL
→ SUBMITTING
→ SUBMITTED
→ VERIFYING
→ COMPLETED
```

异常状态：

```text
NEEDS_REVIEW
PAUSED_FOR_HUMAN
RETRY_WAIT
UNKNOWN_COMMIT_STATE
FAILED
CANCELLED
```

阶段 A 可以暂时不触发所有状态，但不能创造第二套名字。

## 6. Pi 必须复用的能力

以下能力原则上不自研：

- LLM Provider；
- ModelRuntime 和模型目录；
- Provider 认证解析；
- LLM 请求和 Streaming；
- Agent Loop；
- Tool Calling Runtime；
- SessionManager；
- SettingsManager；
- Compaction；
- ResourceLoader；
- Skill 和 Extension Runtime；
- abort、steer、followUp；
- Pi 已经提供的 RPC/JSONL 语义。

Flowmate 只在上层增加：

- ModelProfile 和每任务预算；
- DigitalEmployeeDefinition；
- Job/Workflow/Policy；
- Tool Gateway；
- Approval/Review/Takeover；
- Adapter；
- Audit/Eval/Release。

## 7. 单人版本的物理架构

阶段 A、B 优先：

```text
Electron
├─ React Renderer：任务和复核界面
├─ Preload：受控 IPC
└─ Main
   ├─ Flowmate Kernel
   ├─ Pi Runtime Host
   ├─ Tool Gateway
   ├─ Adapter Registry
   └─ SQLite
```

阶段 C 只有在实际证明 Electron 会被长任务拖死时，才增加薄子进程：

```text
Electron Main
→ child_process
→ Thin Pi Runtime Host
→ Pi SDK
```

该子进程不重新实现 Agent Loop、Session、Streaming、Compaction 或模型 Provider。

## 8. Obsidian 与运行数据库的边界

```text
Obsidian：人查看和管理真实数据资产
SQLite：Flowmate 运行时业务事实
文件目录：PDF/OFD/图片和 JSON 标注
```

Flowmate 不能直接把 Obsidian Markdown 当成生产事务数据库。数据流水线发布 `manifest.json` 后，测试和评估程序只读取发布版本。

## 9. 安全不变量

以下规则无论 Prompt 怎么变化都不能被绕过：

1. Agent 不获得原始密码；
2. Renderer 不读取密钥；
3. 高风险 Tool 必须经过 Approval；
4. Shadow 模式禁止真实写入；
5. Unknown Commit 禁止自动再次提交；
6. 相同业务提交使用稳定 idempotency key；
7. Agent 不能直接修改 Job 最终状态；
8. 每个写动作保存输入摘要、审批、结果和时间；
9. 验证码、MFA、扫码交给人处理；
10. 原始真实数据不进入 Git。

## 10. 什么时候才允许增加新架构

只有同时满足以下条件才增加 Redis、队列、PostgreSQL、服务化或多 Worker：

- 当前单机实现出现可复现的容量或可靠性问题；
- 已写测试能复现该问题；
- 新方案能解决该问题；
- 你能独立备份和恢复新增基础设施；
- 增加后的长期维护成本可接受。

“以后可能需要”不是增加复杂度的充分理由。
