
# 第 3 章错误处理与异常边界的适度完善方案

## 1. 审查结论与修改定位

**第 3 章的主体设计已经完整，不需要重做。** 已包含统一错误契约、各层异常负责人、影响范围、重试、恢复、清理及阶段验证。

需要完善的主要是：

- “预期业务拒绝”容易与 Job 的正式业务拒绝混淆。
- “未识别错误才标记内部缺陷”可能将未知外部错误误归为产品缺陷。
- 工具错误、订阅故障与关键持久化失败的影响范围需要与后文统一。
- `resume_run`、UNKNOWN 和重试的概括容易产生不同解释。
- 事务失败、执行结果不明、结果回送失败尚需集中区分。
- 清理和诊断本身失败时，不能承诺故障记录一定已保存。

本次保留 §3.1–3.6，完善分类含义、处置边界及交接原则；具体错误码、捕获位置、超时数值和测试步骤留到阶段方案。

## 2. 必要调整

### 2.1 区分错误类别、业务结论与根因

完善 §3.1：

- “预期业务拒绝”明确为当前请求或操作不满足条件，例如权限不足、参数不合法、版本冲突；不自动将 Job 置为 `rejected`。
- 企业规则不满足、人工拒绝审批和外部权威拒绝，分别由所属业务契约判断，不统一当作技术故障。
- 解析输入不合格属于输入质量问题；企业查询失败属于技术依赖问题。不能因归一化处理相近，就采用相同重试或业务处置。
- 超时、取消、预算耗尽和停写保留各自控制原因，不代表业务未发生、执行已停止或资源已释放。

修正未识别错误的归因原则：

> 保留已知来源与实际证据，按可确认的类别归一化；原因尚未查明时明确保留归因缺口，不仅因为错误码陌生就认定为产品缺陷。

实际不变量破坏和内部契约错误仍按程序缺陷处理。未知原因不妨碍采取必要隔离措施，也不能伪装为业务拒绝或空结果成功。

沿用现有 ErrorDescriptor，不新增分类平台或要求立即扩展全部字段。

### 2.2 明确错误描述不直接决定状态和权限

完善 §3.1–3.3：

- ErrorDescriptor 用于传递错误事实与建议，所属模块结合当前业务事实决定状态变化。
- `impactScope` 表达已知影响范围；共享资源失效时由受影响对象的负责人核验并扩大隔离范围，不能仅凭最初的 `call` 范围继续执行。
- `recoveryAction` 是后续处理方向，不是可直接执行的命令或授权。
- 现有 `resume_run` 表示进入受控执行恢复流程，不表示重新打开终态 Run；需要执行时沿用新 Run／有效绑定规则。
- UI 的允许操作仍来自当前权限和状态查询，错误中的建议不能直接决定按钮权限。

补充各类影响的原则：

| 情况                                 | 处置方向                                                     |
| ------------------------------------ | ------------------------------------------------------------ |
| 可恢复工具错误或明确准入拒绝         | 向 Pi 回送安全结果；是否继续取决于目标、权限、预算及终止条件 |
| UI、普通订阅或非必需诊断故障         | 隔离并报告，不仅因此判 Run 失败或重新投递输入                |
| 必需历史、事件或关键业务证据保存失败 | 按完整性影响阻断相关新执行，不能继续依赖未提交状态           |
| 共享存储、授权或控制状态不可信       | 按实际影响停止新准入／新写，保留在途核对责任                 |

单次工具失败不机械终结整个 Run；状态或控制完整性失效也不能交给模型反复试错。

### 2.3 集中区分执行、提交与结果回送

完善 §3.2、§3.4：

| 已知事实                     | 处理原则                                                               |
| ---------------------------- | ---------------------------------------------------------------------- |
| 已证明操作未执行或事务已回滚 | 可报告对应操作未生效；是否重试仍检查原身份及当前条件                   |
| 本地命令提交结果不明         | 按原 requestId 和持久事实核对，不盲目重复命令                          |
| 原生历史保存失败             | 使受影响绑定不可继续，阻断新执行并请求停止；恢复以最后成功提交历史为准 |
| 外部动作可能已生效           | 保留原动作／尝试身份，进入既有 UNKNOWN 核对                            |
| 输出校验或结果回送失败       | 不伪装合法成功，也不抹除已提交事实；按原命令或动作核对                 |

补充：

- 某个事务回滚只证明该事务内的本地更新未提交，不能推断此前事务或外部动作均未发生。
- 工具回送丢失、界面缺消息和调用方超时，均不能单独证明业务未执行。
- 取消、Run 失败或后续诊断异常，不回滚已接受修订和已确认外部事实。
- UNKNOWN 是外部结果不确定；输入投递不明、数据库提交不明分别沿所属协议处理，不全部混成提交动作 UNKNOWN。

不新增结果状态或通用核对服务。

### 2.4 对齐唯一重试负责人和受控恢复

保留 §3.4 的负责人划分，补齐限制：

- 模型请求重试由已启用的 Pi 原生策略负责。
- 普通业务 READ 重试由 Gateway 内部执行路径负责，Handler／Adapter 执行单次尝试。
- 原生或扩展工具若具有内部重试，固定唯一重试层，不额外套业务 READ 重试。
- 内部命令提交不明先查原请求；外部结果查询和发送裁决由 submissions 负责。
- 权限拒绝、永久输入错误、Schema 不兼容及不变量破坏不进入普通暂时性重试。
- 重试、等待和重绑不重置既有总期限、预算或业务有效期。

将“UNKNOWN 只允许核对／人工”的绝对表述统一为：

> UNKNOWN 首先按原动作核对，禁止通用错误重试或模型自行重发；只有第 12 章既定安全重试条件及当前准入成立，submissions 才可创建关联的新尝试，旧 UNKNOWN 事实保留。

恢复先核验当前事实、授权、未决动作及旧执行隔离条件，不直接重新调用失败函数，不自动恢复旧 Scope 或终态 Run。

### 2.5 完善清理、记录失败与人工接管边界

完善 §3.5–3.6：

- primaryError 与 cleanupErrors 分开，清理失败不覆盖原始失败。
- 清理按资源依赖关系执行，彼此独立的资源可以分别尝试；不能因某项失败跳过其他仍可安全完成的清理。
- 实际停止、资源释放、费用结算分别取证，不因清理完成就认定零消耗。
- 数据库或日志不可写时，不承诺错误、终态或审计一定已保存；先落实可执行的本地阻断，保留可取得的安全诊断，并明确持久证据缺口。
- 不为记录错误而递归调用失效日志／存储链路，也不增加第二套恢复事实库。
- 次次启动仍按已提交记录、实际资源和外部事实核对；没有退出日志不等于未执行。

明确人工和运维接管继续使用同一受控控制实例。独立 CLI／维护入口不意味着可在旧控制者未隔离时启动第二个控制者，也不能绕过审批或把资料缺失标为通过。
