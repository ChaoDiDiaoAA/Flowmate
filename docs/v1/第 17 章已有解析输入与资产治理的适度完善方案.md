## 2. 第 17 章的必要调整

### 2.1 区分产品输入准备与评测资产制作

整理 §17.1–17.1.1：

- P0 的必交付是项目内获准输入集合、来源与摘要、标签隔离、完整性检查及实际产品读取链路。
- 原票审核、结构化 Gold 发布、Case 制作和产品实际运行分别记录，不能相互替代，也不要求 P0 完成全部评测资产。
- 当前样本数量、重复别名和人工核验规模保留为有日期的盘点背景，不作为长期固定数量或当前完成状态。
- 重跑准备时以实际清单和检查结果为准，差异必须说明，不为满足旧数量补齐或静默排除。
- 保留现有外部导入根、项目来源根和独立质量根；路径由配置映射，原始外部来源不因导入成功而删除。

主方案自身写清交付要求；数据制作文档提供具体操作，不承担主方案未定义的产品行为。

### 2.2 明确各类数据对象及权威来源

在 §17.2 补充简短对照：

| 对象                       | 职责与边界                                                   |
| -------------------------- | ------------------------------------------------------------ |
| 原票与已有解析文件         | 保存来源内容和证据；内容变化不能原地冒充旧版本               |
| ParsedDocument             | 对已有解析的统一产品表示，不代表重新运行解析器或字段审核通过 |
| documents                  | 登记输入版本、归属及当前可用状态                             |
| artifacts                  | 管理受控文件位置、摘要和引用，不替代文档业务状态             |
| DatasetManifest            | 固定某次发布的成员、版本、角色和摘要                         |
| JobInputManifest／输入投影 | 固定任务获准使用的输入，不自动包含整个数据集或质量资料       |

明确三层关系：

- **文件校验通过**不等于解析内容语义正确。
- **文档 available**不等于每个任务、主体或模型均获准使用。
- **任务固定了输入**不等于资料永远有效；实际使用仍检查当前可用性、用途和权限。

项目来源清单与实例中发布的冻结清单不能成为两份独立可变权威。实例按已登记版本和摘要引用；必要副本必须一致，根目录同名文件或最新清单不能替换历史任务引用。

保留现有表和引用体系，不新增资产服务或清单数据库。

### 2.3 澄清输入要求、去重和版本变化

完善 §17.1.1–17.3：

- 当前数据包的文件名和保留集合属于已确定的来源映射；其他解析来源按获准接入契约确定必需文件及引用，不机械要求相同文件名。
- 当前版本声明保留的文件及依赖必须完整。缺页、空内容或阻断警告不能伪装成完整输入；非阻断警告保留来源与影响。
- 只有原票而没有合格解析时，要求使用外部工具补充，不在产品内自动调用解析器。

补充去重边界：

- 原票字节相同，可以归入同一来源组，但不证明解析内容、解析版本或标签也相同。
- 同组解析存在差异时，保留来源和差异，明确选用依据；不能按目录顺序或“最新文件”静默覆盖。
- 当前准备流程不自动合并不同解析结果；无法确定有效选用结果时，报告缺口并交外部整理。
- 提供方标签独立保留，不参与产品选择解析结果；评测侧继续按原票组避免重复计分与跨集合泄漏。
- 文件去重不直接决定发票业务重复或提交动作身份。

版本规则按对象区分：原票或解析内容变化建立新文档版本；清单成员、用途或引用变化建立新清单版本；可用状态变化沿既有状态规则处理，不为一次状态更新伪造新内容版本。

### 2.4 明确发布、重试与恢复边界

完善 §17.3，并同步 §17.5 的发布措辞：

**暂存与核验文件 → 保存完整不可变文件及清单 → 受控提交数据库引用和发布依据 → 对读者开放。**

明确：

- 文件系统与 SQLite 不存在天然的跨系统原子事务。
- 完成标记或 manifest 文件存在，不能单独证明已经发布；产品只接受已提交、可核验的发布引用。
- 部分失败不暴露半完整版本，也不覆盖原有效版本。
- 重复导入相同来源与内容复用已有记录；内容不同按新版本或冲突处理，不能借重试覆盖。
- 恢复先核对已提交引用、文件和摘要，再继续未完成准备；不因重新扫描目录而自动改变已发布成员。
- 清理仅处理本次拥有且未被有效引用的暂存资源，不删除来源文件或仍被历史任务引用的版本。

在本节补充一张简短发布流程图，表示核验失败、提交失败和读者可见边界；不引入导入调度器、消息队列或新状态枚举。

### 2.5 区分撤回、不可用与物理删除

完善 §17.4–17.5：

| 情况                     | 处理原则                                                       |
| ------------------------ | -------------------------------------------------------------- |
| 文件缺失、损坏或摘要不符 | 原版本标为不可用；只有恢复为同版本内容并重新核验后才能恢复可用 |
| 输入版本被撤回           | 保留撤回事实，阻断受影响的新使用；旧清单不能恢复使用资格       |
| 发布新版本               | 不自动替换旧 Job、快照或运行所引用的版本                       |
| 物理删除                 | 按保留、引用及恢复要求受控执行，不因撤回或 Run 结束立即删除    |

进一步明确：

- “撤回影响已发布清单”是指其成员当前不能继续使用，不是修改不可变清单的历史内容。
- 影响中的输入投影、步骤和待执行动作按既有规则失效；已发送动作继续按原身份核对。
- 撤回不会自动清除已进入 Session 历史、快照或证据的内容，不能声称换投影、压缩或删除源文件就完成全部擦除。
- 恢复旧备份仍须核验当前撤回及使用资格，不能只依据备份当时的 available 状态。
- 同一来源组的别名或副本不能成为绕过已登记撤回范围的入口。

本轮不建设自动删除、历史清洗或跨系统数据擦除功能；具体保留与维护操作由 P13 确定。

### 2.6 保持补样与可选投影的范围

集中说明：

- 当前仍以用户提供的原票和已有解析为主，不因资产治理而扩大为采集平台。
- 补样只在明确缺口和获准范围内开展。
- Obsidian 等浏览投影不成为输入事实或发布状态的权威来源；投影失败不否定已成功发布的数据。
- 来源元数据中的网址、路径或用途声明只提供信息，不自动触发下载、执行或授予访问权。
- 保留现有来源、用途、隐私和质量检查，不增加企业数据治理平台。
