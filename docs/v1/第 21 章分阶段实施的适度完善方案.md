
# 第 21 章分阶段实施的适度完善方案

## 1. 审查结论与修改定位

**P0–P13 的顺序和主要能力划分合理，不需要重新拆阶段。** 已覆盖从基础、原生执行、工具、会话、上下文到业务、扩展、协作及生产交付的完整路线。

需要完善的主要是：

- “首次建立、继承使用、后续增强”没有始终区分。
- 少数退出条件容易被理解为需要提前实现后期模块。
- Driving Task 成功与阶段完整通过的关系需要明确。
- 必需能力受阻、可选模式未启用及环境缺失的处理不够集中。
- 各阶段累积的“承接”段落较多，掩盖了当期目标和增量。

本次只调整阶段表达、依赖及交付判据。保持顺序、功能范围和技术路线，具体实现仍由阶段方案确定。

## 2. 第 21 章的必要调整

### 2.1 统一各阶段的阅读结构

整理 §21.1–21.14，保留现有要求，归并重复的承接说明。各阶段统一突出：

| 内容           | 主方案需要说明                                |
| -------------- | --------------------------------------------- |
| 阶段定位       | 本阶段主要解决什么问题                        |
| 当期能力增量   | 首次建立什么，增强哪些既有能力                |
| 能力来源与职责 | 复用哪些 Pi／插件能力，产品接入和实现哪些规则 |
| 前置依赖与边界 | 依赖哪些已成立能力，哪些尚未启用              |
| Driving Task   | 用什么最小真实任务证明增量                    |
| 横切与交接要求 | 当期存储、权限、错误、日志及恢复要求          |
| 退出条件       | 必需正例、失败路径和可核验结果                |

处理原则：

- 已由前文定义的模块规则，本章保留当期启用范围及交接要求，不重复展开完整协议。
- 同一要求在阶段正文、横切表和依赖表中的表述保持一致。
- 保留每个阶段的具体目标与退出条件，不压缩成只有阶段名称的总览。
- 本章明确调用、状态及存储语义，不新增公共接口、数据库表或调度机制。

### 2.2 区分首次建立与继承增强

统一阶段正文及 §21.15–21.16：

| 阶段关系         | 澄清原则                                                                                             |
| ---------------- | ---------------------------------------------------------------------------------------------------- |
| P0 → P1         | P0 建输入与基础存储，不要求模型；任务输入引用不依赖虚构的 Job／Run／Session 记录                     |
| P1 → P2 → P3   | P1 固定受限工具证明原生 Loop；P2 接入正式工具治理；P3 增强事件、期限及预算控制，同一执行路径逐步完善 |
| P4 → P6 → P7   | P4 建会话、输入和完整历史存储；P6 验证历史使用、纠正与隔离；P7 启用经过验证的原生压缩                |
| P5／P6 → P8     | 前序使用明确的受控输入与事实版本，P8 才建立正式修订、步骤和人工业务交互，不提前复制完整 Workflow     |
| P8 → P12        | P8 已交付业务复核、修订及等待；P12 继承这些能力，增加完整界面、冻结动作、审批及外部提交              |
| P9 → P10 → P11 | 资源、可执行扩展和子 Agent 分别启用；前一阶段的资源或记录能力不表示后一阶段已经运行                  |
| P12 → P13       | P13 改变执行承载并完善发布运维，保留前序业务语义，通过 Host 环境重新验证受影响链路                   |

同时明确：

- “核心能力”列出的既有对象不一定是本阶段新建，应标明继承或增强。
- 后续阶段沿用同一模块，不按阶段重建实现。
- 权限、错误和清理从能力首次启用时就必须有效；P13 完善生产机制，不替前序阶段补交基本控制。

### 2.3 修正提前依赖和模糊完成条件

对现有具体表述作有限修正：

- **P4 扩展条目恢复：** 验证原生自定义条目的完整保存与恢复，不要求提前装载产品扩展；真实扩展产生条目的完整链路随 P10／P11验证。
- **P4 会话操作：** 查看历史、创建分支记录不自动启动 Run；需要继续执行时才核验新的执行身份。
- **P5／P6 事实纠正：** 明确使用前序受控输入版本，不把它称作已交付完整人工复核或正式 Revision。
- **P7 压缩：** 当期验证压缩请求的期限、预算与持久化；真实子 Agent 的压缩和共享预算随 P11 验证，不形成提前依赖。
- **P9／P10 版本变化：** 实现当期资源／扩展的更新、撤销及受控组合变更；完整安装、Host 和生产迁移治理仍在 P13。
- **P12 Revision：** 表述为继承 P8 的修订能力并连接冻结载荷与审批，不暗示重新建立一套修订机制。
- 各阶段中 Job／步骤归 `core/jobs`，Run／绑定归 `core/runtime`，Kernel 负责协调，避免交接表再次出现双重负责人。

### 2.4 明确 Driving Task 与阶段退出的关系

在章节引言及 §21.16 补充统一原则：

- Driving Task 是证明当期能力的最小真实任务，**一次成功运行不是全部退出条件**。
- 阶段通过同时需要：当期必需增量成立、适用失败路径有效、受影响前序能力未退化，以及所需真实接入与质量证据充分。
- 回归按变更影响范围选择；不要求每阶段机械重跑所有历史测试，也不能只验证新增 happy path。
- P0 验证真实产品输入与存储链路；P1 起按阶段验证真实模型能力，不提前要求完整企业业务成功。
- 功能测试可以随开发执行；真实 Agent 效果评测在相关功能可运行后开展。Case／Gold 可提前准备，但准备完成不代表产品运行通过。
- 结果绑定实际组合、输入版本及环境；沿用前序证据时说明适用范围，不把旧报告直接算作新阶段通过。

阶段方案再确定样本、通过阈值和具体测试步骤，主方案不填写未经验证的数值。

### 2.5 区分必需能力、可选模式与外部条件

补充一致的退出处理：

| 情况                                 | 阶段结论                                         |
| ------------------------------------ | ------------------------------------------------ |
| 当期必需能力未实现或未验证           | 保留缺口，不能宣布阶段完整通过                   |
| 已明确为可选、当前任务不需要的模式   | 保持关闭并说明范围，不计入已完成能力             |
| 必需 SDK／插件接入点无法成立         | 阻断依赖能力；不能用模拟结果或关闭该能力冒充通过 |
| 缺少真实模型、企业规则或获准测试环境 | 可报告已完成部分，不能代替缺失的真实验证         |
| 前序相关能力出现回归                 | 修复并验证后再完成依赖该能力的阶段交接           |

具体落实：

- P7 至少验证满足当期任务的原生压缩模式；未验证的其他模式不开放。
- P10 必须有实际扩展装载、使用及控制证据，不能以全部停用退出。
- P11 必须完成单个前台只读子任务的真实闭环；有限并行、后台、活动调整及续聊按后续任务增量启用。
- 原生预算、存储及清理边界在首次启用相关模式时验证；P13 再验证 Host 形态，不能将前序必需接入全部推迟到 P13。

### 2.6 明确 P12、P13 内部里程碑与最终交付

保持现有阶段编号，在 §21.13–21.17 明确：

- P12-A 通用模拟、P12-B 企业契约模拟、P12-C 获准真实测试分别报告结果。
- 本地闭环通过不代表完整 P12 通过；缺少必需企业条件或真实测试证据时，保留未完成范围。
- P13 的 Host／安装／恢复工程验证，与 Test／Shadow／Canary／Production 的运行放行分别成立。
- 工程能力完成不自动授予生产写权限；未取得生产条件时可以报告工程验证结果，不能宣称已完成生产业务交付。
- 生产收益使用获准真实运行证据，不由模拟或只读 Shadow 推算。
- 这些是阶段内部交付节点，不新增 Harness 阶段，也不更改 P0–P13 顺序。
