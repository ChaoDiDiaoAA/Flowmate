
# 第 8 章事件驱动与时间控制的适度完善方案

## 1. 审查结论与修改定位

**第 8 章的主体设计已经完整，不需要重做。** 已定义事件关联与去重、持久序号、重连补发、超时、预算预留与结算，以及未知消耗的处理。

需要完善的是几处边界：

- “事件只能观察”过于绝对，应区分事件通知与受控状态变更。
- 实时进度和持久事件的序号、重放承诺没有充分区分。
- 多层期限如何共同生效、运行到期后如何清理，仍容易产生不同实现。
- 单工具超时被概括为“只读失败或外部 UNKNOWN”，未充分覆盖内部写和已受理命令。
- 预算正文中的释放条件比状态表宽泛，需要统一。

本次只补充职责、关键行为及阶段要求，具体事件类型、缓冲机制、计时实现和数值留到阶段方案。

## 2. 第 8 章的必要调整

### 2.1 明确事件通知与状态变更的关系

完善 §8.1，并同步 P3 的“事件只能观察”表述：

- Pi／插件产生原生执行事实，runtime-pi 负责关联和转换，core/evidence 负责产品持久事件及 Timeline。
- 事件可以触发所属模块进行核验或调用受控命令，但事件本身不授予执行权，也不能直接成为业务成功的依据。
- Run、输入、工具和业务对象仍由各自唯一负责人更新；普通 UI、日志和 Timeline 订阅者不能写业务状态。
- 不通过重放事件重新执行工具、派发提交或恢复旧授权，不引入事件溯源架构或通用消息总线。

### 2.2 区分实时进度、持久事件与订阅故障

在 §8.1 补充简短分类：

| 类别                   | 保存与恢复原则                                      |
| ---------------------- | --------------------------------------------------- |
| 实时流片段、可合并进度 | 可以合并；未持久内容不承诺完整重放，缺口明确标记    |
| 需要持久的运行事件     | 由 core/evidence 落库并分配产品序号，按持久游标补发 |
| 业务事实及关键审计     | 由所属受控事务保存，事件和日志不能替代其权威记录    |

同时明确：

- 持久 `sequence` 表示接收落库顺序，不是所有实时片段都天然具有持久序号，也不表示跨 Run 的全局因果顺序。
- 重复、乱序和迟到处理沿用现有源身份与对象关联，不按到达先后覆盖权威事实。
- 慢 UI、普通订阅者或诊断故障应隔离并报告，不无限阻塞执行，也不直接判 Run 失败。
- 必需事件或关键证据保存失败时，交给既有错误边界处置；不能假装已持久化。涉及数据库、授权或状态完整性时，停止受影响的新执行。
- 重连只补发已持久事件；历史和业务记录用于核对缺口，不伪造原生事件。

具体持久事件清单、缓冲上限及合并方式在 P3、P13 确定。

### 2.3 明确期限的共同约束与到期语义

完善 §8.2：

- 模型请求、工具调用和子执行同时受自身限制及所属执行剩余期限约束，适用限制中先到期者生效。
- READ 重试、模型重试及有界等待不自动重置或延长 Run 总期限。
- 长期人工等待属于持久业务等待，不占用活动 Run；后续新 Run 有新的执行期限，但不能重置原审批有效期或业务等待期限。
- 超时表示触发停止和核对，不等于实际执行已停止、清理已完成或外部动作未生效。
- Run 到期后阻止新的任务执行；必要停止、清理及在途结果核对按各自受控边界继续，不能借此继续原任务或获得无限额度。
- 单工具超时按第 6 章的 effect 和已知事实处理：读取失败、内部命令是否已提交、外部动作是否未知分别判断。

保留“持续时间使用单调时钟、持久时间使用 UTC”的路线；明确重启不比较不同进程的单调时钟值，也不自动重新授予完整期限。应用离线期间不承诺即时提醒，恢复及关键操作前重新检查到期事实。

### 2.4 统一预算范围、计量与释放条件

完善 §8.3，保留 §8.4 状态枚举及转换：

- Job 总预算由 core/runtime 统一管理；主子 Run、重试和压缩消耗按既有规则归入同一总额。
- 新 Run 或新绑定不自动重置 Job 已消耗及未知占用；运行限额与 Job 总额同时生效。
- 请求数、工具次数、Token、费用和时长是不同限制维度，各自明确计量范围，不将它们混成同一种扣减。
- 区分预留估计、实际用量和未知消耗；事后统计不能冒充请求前硬限制，插件汇总不与明细重复计费。
- 修正释放表述：已产生实际消耗的请求进入 settled，结算后退还未使用预留；released 用于已有依据确认未产生消耗的情况。实际停止本身不证明零消耗。
- 原生重试、自动压缩及子请求的预算接入仍是实测事项；不能验证控制边界时，沿用关闭相关模式或采用可证明保守限制的既定策略。

必要清理与外部核对沿用各自受控权限和有界策略，不复活旧 Run，也不作为绕过预算的通道。

## 4. 验收与细节边界

文档一致性检查及后续验证方向：

- 事件可触发受控核验，但普通订阅者不能推进业务状态。
- 实时进度不冒充持久事件，重连不重执行业务动作。
- UI 订阅故障与关键持久化失败按影响范围分别处理。
- 重试、等待、重绑和重启不自动延长期限或重置额度。
- 超时、实际停止、清理完成和外部结果分别取证。
- 已知消耗结算、零消耗释放、未知消耗保留占用，正文与状态表一致。

保持现有目录、23 张表、状态枚举和 P0–P13 顺序，不新增调度平台、消息中间件或计费系统。不生成产品代码，不修改已发布评测资产。

事件字段细化、队列与缓冲实现、具体计时方式、期限及预算数值、SDK 控制入口和测试步骤，仍由对应阶段方案确定。
