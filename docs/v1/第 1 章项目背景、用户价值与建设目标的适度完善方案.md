## 2. 必要调整

### 2.1 明确业务起点与建设目标

完善 §1.1、§1.3、§1.6：

- 产品终点保持为获准的 B2B 发票录入、权威结果核对及异常交接，不延伸到 ERP 回写、付款或入账。
- 区分已具备的数据条件、待确认的企业流程和预期收益；有样本不代表企业业务已验证。
- 保留与企业现有人工、API、RPA 或其他自动化方案比较的原则。

补充两类目标：

| 目标           | 成立依据                                                       |
| -------------- | -------------------------------------------------------------- |
| 工程建设与学习 | 按 P0–P13 逐步掌握并验证 Pi 接入及 Agent Harness 产品控制能力 |
| 业务价值       | 在获准真实业务范围内，证明人工投入、成本、时效或质量有所改善   |

工程能力通过不直接证明业务收益，也不以扩大业务范围解释收益不足。

### 2.2 集中说明 Agent、产品与人工职责

在 §1.4 增加简短职责表：

| 参与方            | 核心职责                                                                         |
| ----------------- | -------------------------------------------------------------------------------- |
| 主 Agent          | 理解材料、提出字段候选、选择获准工具取证、整理冲突与缺口、请求人工交互及动作意图 |
| 子 Agent          | 按需承担获准的只读辅助核查，提供建议或证据；不是每票必经步骤                     |
| Flowmate 产品能力 | 执行确定性规则和受控命令，管理业务事实、权限、步骤、审批、发送防重及结果核对     |
| 有资格人员        | 澄清和复核业务事实、批准具体冻结动作、处理需要人工承担责任的异常                 |

明确候选、匹配建议和模型文字不直接成为已接受事实；请求审批不等于批准。人工复核按适用规则发生，正式提交仍须有资格人员批准具体动作。

### 2.3 明确“只读工具”的来源及接入关系

将 §1.4 中相关表述改为：

> Agent 理解已有解析材料、提出字段候选，并按需调用 Flowmate 提供、通过 Pi SDK 注册接入的业务只读工具，读取获准证据或查询企业业务依据。

增加简短说明：

| 工具类别        | 来源与作用                                                                                               |
| --------------- | -------------------------------------------------------------------------------------------------------- |
| 业务只读工具    | Flowmate 实现，例如`read_parsed_document`、`read_evidence`，以及后续按需增加的供应商、订单等查询工具 |
| Pi 原生通用工具 | Pi 提供，按需接入产品控制后启用；不天然具备发票业务、资产用途或 Workspace 授权语义                       |

固定概念：

- **“只读”描述行为，“Pi 原生／产品实现／插件提供”描述来源。**
- 业务工具由产品定义和实现，经 `runtime-pi` 转换为 Pi 可调用工具。
- Pi 负责原生工具调用调度；产品负责调用准入、业务读取及记录。
- 只读不等于任意读取，仍受当前任务、资产范围和权限限制。

本章只说明来源及调用关系，不展开 ToolSpec、Handler 或 SDK 参数；具体契约继续由第 6 章定义。

### 2.4 修正工作变化的概览流程

将 §1.4 的线性文本链路调整为简洁流程图：

**合格解析与获准证据 → Agent 理解并调用业务工具取证 → 适用规则检查与事实接受 → 冻结动作 → 人工审批及最终准入 → 受控提交 → 权威结果核对 → 满足既定条件后完成 Job。**

保留必要分支：

- 缺失、歧义或冲突进入取证／人工复核，接受新事实后重新核验。
- 技术异常在发生位置进入受控停止或恢复。
- UNKNOWN 按原动作核对，不自动重发。
- 权威成功后仍检查既定完成条件，不将任何回执直接等同于 Job 完成。

关联与业务核查标明按适用条件执行。图只解释工作方式，不重复第 12、16 章的完整状态协议。

### 2.5 对齐阶段、技术归属与完成口径

完善 §1.2、§1.5–1.8：

- 将“按真实业务终态查看完成、拒绝、待人工和 UNKNOWN”改为按**业务状态和结果**查看，等待与 UNKNOWN 不称为终态。
- 明确 Pi 提供原生历史组织、使用和压缩语义，Flowmate 负责 SQLite 持久化；Subagent 来自第三方插件。

- 主子 Agent 是可用协作结构，不要求每次执行都创建子任务。
- 将含糊的“自动成功”改为有证据的业务成功，并分别记录人工参与；逐票审批不能计为无人处理。
- 单次业务完成、阶段能力通过和完整产品交付分别成立。

保留现有价值指标，不新增收益比例或 ROI 公式。收益比较采用相同任务和成本边界，外部解析在两种方案中均使用时保持一致口径，不将其收益归给本产品 Agent。
