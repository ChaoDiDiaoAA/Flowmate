
# 第 4 章 LLM Provider 与模型调用的适度完善方案

## 1. 修改定位

主方案只明确**技术路线、职责边界、关键行为和阶段交付要求**。具体 SDK 参数、配置示例、实例复用方式、超时数值及测试步骤，由后续阶段方案确定。

继续完全复用 Pi 原生 Provider、模型目录、鉴权和模型调用能力。Flowmate 不新增 Provider 实现、配置解析器或认证系统。

## 2. 主方案补充内容

保留第 4 章现有结构，补充以下五组原则。

| 补充位置                         | 主方案需要明确的内容                                                                                                                                                             |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **4.1 配置路线**           | 应用显式选择本次使用的 Pi 原生配置来源，CLI、桌面和 Host 保持一致；配置格式、认证解析和优先级由 Pi 负责。避免未经选择就继承开发机全局配置                                        |
| **4.1.1 模型选择**         | 模型引用能唯一定位 Provider 和 Model；使用获准模型，缺失或不可用时明确失败，不静默改用默认模型或其他服务。创建、恢复时均核对实际模型                                             |
| **4.2 运行装配与参数**     | ModelRuntime 由接入层装配和管理，不逐轮重建；配置变更不能悄悄影响活动执行。请求参数和能力判断沿用 Pi 原生机制，产品只固定任务所需约束并记录必要的生效信息                        |
| **4.2 认证变化与运行记录** | 区分同一身份下的正常认证刷新与账号、模型、服务目标等运行组合变化；前者由 Pi 处理，后者走产品既有变更控制。运行记录只保存必要的非秘密身份和依据，不重新解析整套 Provider 配置     |
| **4.3 失败与控制交接**     | Pi 报告原生调用结果并执行已启用的原生重试；Flowmate 按统一错误、Run 和预算契约处置。模型不可用、认证失败、超时、取消、流中断及重试耗尽不能被当作正常成功，也不能触发业务提交重放 |

同时调整两处表达：

- 将认证“固定优先级”的概括改为遵循锁定 Pi 版本的原生解析规则，避免主方案复制 SDK 内部行为。
- 明确原生默认值可以使用，但不能违背已固定的模型、任务能力及运行限制。

## 4. 验收与细节边界

文档验收检查：

- Pi 与 Flowmate 的职责一致，没有引入第二套 Provider、认证或重试实现。
- 模型选择、配置变化、失败处置及阶段承接无相互矛盾。
- 正常认证刷新不被笼统等同于更换业务运行组合。
- 评测覆盖配置一致、禁止静默回退、恢复核验和失败不误报成功。
- 保持现有目录、23 张表和 P0–P13 顺序。

**留到阶段方案确定：**精确 SDK 签名、配置路径及示例、ModelRuntime 实例复用方式、参数映射、超时和重试数值、非秘密记录字段及具体测试用例。本次不生成产品代码，不改动已发布评测资产。
