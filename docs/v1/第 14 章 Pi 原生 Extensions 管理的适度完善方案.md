
# 第 14 章 Pi 原生 Extensions 管理的适度完善方案

## 1. 审查结论与修改定位

**第 14 章的主体设计已经完整，不需要重做。** 已覆盖原生扩展接入、来源与版本、能力盘点、兼容验证、实例状态及清理失败。

需要澄清的是：

- 安装包、扩展入口、注册能力和运行实例之间的关系。
- “已安装、已批准、已装载、当前可调用”是不同事实。
- 工具、命令及不同 Hook 的产品控制入口不能一概而论。
- “禁用只撤销后续高风险动作”范围过窄。
- 停用、清理和原生热卸载能力容易混淆。
- P10“Flowmate 只控制来源、放行和诊断”遗漏了既定准入、绑定及清理职责。

Job、步骤、审批及提交仍属于第 12 章；本章负责可执行扩展的接入和治理。

本次只明确概念、职责、关键行为及阶段要求，具体 SDK 接口、Hook 清单和清理实现留到阶段方案。

## 2. 第 14 章的必要调整

### 2.1 区分安装包、扩展能力与运行实例

完善 §14.1，增加简短概念表：

| 概念         | 主方案定义                                                    |
| ------------ | ------------------------------------------------------------- |
| 包／来源     | 提供代码及依赖的分发来源；包内可能包含多个扩展入口或其他资源  |
| 扩展入口     | 通过 Pi 原生机制装载的可执行入口                              |
| 注册能力     | 扩展提供的工具、命令、Hook 及相关资源，分别核验用途和控制条件 |
| 运行实例     | 某次绑定实际装载的扩展实例，具有独立身份、状态和清理证据      |
| 产品启用配置 | 指定获准版本、绑定范围和能力集合，不代表实例已成功运行        |

明确：

- 原生 Extensions 指复用 Pi 的扩展机制，不意味着第三方包属于 Pi SDK 内置能力。
- 包已安装不等于允许装载，装载成功不等于所有注册能力均可使用。
- 产品清单固定所需入口和能力，不因安装一个包就默认启用包内全部内容。
- 管理视图中的加载状态来自实际实例观察，不在配置层另存一套可独立修改的运行状态。

沿用现有清单、RuntimeSnapshot、运行事件和绑定记录，不新增扩展表。

### 2.2 明确安装、装载与批准的先后

整理 §14.1 的管理流程：

**登记并核验来源 → 通过受控维护路径准备固定依赖 → 建立候选清单 → 在限定范围装载验证 → 获准绑定 → 实际运行。**

补充原则：

- 依赖准备和装载通过锁定版本支持的原生机制接入，不笼统承诺所有安装操作都是 SDK 方法。
- 不能以“只是安装或发现”为由执行未获准代码；来源及允许操作范围须先核验。
- 验证使用的扩展同样属于受信代码，限定测试范围不等于操作系统沙箱。
- 禁止从开发机全局目录或包内其他入口隐式增加能力。
- 模型不能通过普通工具自行安装、升级或修改扩展配置。

不增加包管理器或扩展市场；P10 先准备和验证当期固定扩展，P13 再验证安装交付环境。

### 2.3 分别定义工具、命令和 Hook 的控制接入

完善 §14.1–14.2：

| 能力类型                | 控制原则                                                                           |
| ----------------------- | ---------------------------------------------------------------------------------- |
| 扩展工具                | 沿第 6 章共享准入、最终参数检查、预算、取消及唯一调用记录；执行仍由插件负责        |
| 扩展命令                | 区分原生会话操作与产品业务操作；涉及业务事实、权限或审批时必须调用所属受控命令     |
| 输入／上下文等变换 Hook | 仅使用获准变换范围，保留实际来源和关联；不能改变产品固定目标、权限或业务事实       |
| 生命周期／观察 Hook     | 提供原生事实和诊断；不能凭回调直接推进业务状态或重放外部动作                       |
| UI 相关能力             | 按当前 CLI、桌面或 Host 承载能力验证；必要交互不可用时拒绝依赖能力，不伪造人工确认 |

统一要求：

- 固定实际启用的工具、命令和 Hook，而非允许任意 Hook。
- 顺序及变换结果通过真实 SDK 验证；工具最终准入不能被后续 Hook 修改绕过。
- 注册名称冲突明确拒绝，不依赖加载先后覆盖。
- 无法覆盖必要控制的能力保持未启用；不能以事后日志代替执行前核验。
- 扩展代码属于受信运行域，不把这些控制描述为对任意插件代码的沙箱。

不要求所有 Hook 都经过 Tool Gateway，也不为扩展再建一套权限系统。

### 2.4 明确停用、撤销与实际清理

调整 §14.2：

- **停止后续装载**：阻止指定范围的新绑定加载该扩展，不自动宣称当前实例已停止。
- **即时撤销**：阻断受影响实例的后续工具、命令及可执行 Hook 能力，不仅限于“高风险动作”；必要停止和清理仍通过受控路径完成。
- **实例清理**：确认实际执行停止、监听解除及相关资源释放，才可以进入 disposed。
- **升级／回退**：使用获准兼容组合建立新实例，不在活动实例内静默替换代码；同一 Job 的新 Run 不自动选择最新扩展。

同时明确：

- 不预先承诺 Pi 支持任意扩展独立热卸载。
- 如果锁定组合不能独立、安全地释放某扩展，则关闭并重建受影响绑定；清理影响范围由实际依赖决定，不能假称只影响一个插件。
- 旧实例未隔离前，不开放可能冲突的新执行。
- 已发送外部动作继续按原身份核对；停用扩展不取消外部事实。
- P13 才加入受控 Host 终止手段，不将 Host 作为 P10 的前置条件。

保留既有实例状态枚举和清理协议。

### 2.5 区分装配失败与运行中故障

完善 §14.2–14.3：

- 初始化或装配所必需的 Hook 失败时，按既有 loading → load_failed 处理，不进入 binding-ready，并清理部分资源。
- 实例 active 后的工具业务失败，先按工具和 Run 契约处理，不机械等同于整个扩展加载失败。
- 运行中必要 Hook 或控制接入失效时，停止受影响能力，按现有 disable_pending／cleanup_failed 路径处置，不把 active 实例倒退为 loading。
- 非必需观察或展示故障可以按既有错误边界隔离，但涉及授权、历史保存或执行完整性的故障不得静默忽略。
- 恢复依据是当前控制和实际资源状态；事件历史可用于展示与核对，不能通过重放事件重新装载或恢复旧执行权。

职责统一为：

- runtime-pi 报告实际实例行为和技术状态。
- core/runtime 接受影响绑定、停止及清理的事实。
- 持久事件沿既有 evidence 路径保存。
- core/configuration 管理获准组合及当前控制。

修正 P10“只控制来源、放行和诊断”的表述，明确 Flowmate 还负责已有共享准入、绑定协调和清理结果核验。

评测复用 MOD-33、RT-08、RTC-08 及现有工具、状态和版本场景，补充：

- 已安装、已批准、已装载、当前可调用分别取证。
- 包内未选择入口和未批准能力不会自动启用。
- 工具、命令、变换 Hook 和观察 Hook 分别验证控制边界。
- 停止后续装载与即时撤销有不同效果，配置停用不冒充实例释放。
- 装配失败、业务调用失败和必要 Hook 失效分别处置。
- 不支持独立卸载时，受控关闭绑定仍能正确隔离旧实例。
- 更新、回退及恢复不复活旧权限，不自动重放业务动作。

机制测试与真实 Agent 使用效果继续分别记录，不新增评测体系或提前制作具体 Case。
