
# 第 20 章工程目录与生成约束的适度完善方案

## 1. 审查结论与修改定位

**第 20 章的目录覆盖已经完整，不需要重新拆包或重画架构。** 已包含应用入口、产品控制、Pi 接入、领域实现、数据、日志、测试和独立评测，并规定了依赖方向与阶段启用顺序。

需要完善的主要是：

- 固定目录边界与阶段内部细化的关系。
- 同名或相近模块的职责区别。
- 运行文件目录与数据库权威存储之间的冲突。
- SDK 依赖限制与原生能力验证入口的关系。
- 部分阶段注释、当前状态和目录说明没有跟上前面章节。

本次只明确工程落点、依赖和生成原则；具体内部文件、构建配置及检查脚本由阶段方案确定。

## 2. 第 20 章的必要调整

### 2.1 区分目标目录、阶段生成与当前实际状态

完善 §20.1、§20.3、§20.6：

- 包名、主要职责目录、公共组装入口和依赖方向属于固定约束。
- 阶段方案可以在既定职责内细化内部文件，不需要主方案提前列出全部实现文件。
- 新增平行包、改变公共边界或迁移模块职责时，先同步主方案；不能通过内部细化绕过架构约束。
- 目录上的阶段标记表示最早启用时间，不代表整棵子树必须同时生成；当前功能所需依赖必须同步具备。
- 已生成目录、已实现能力、验证通过分别记录，不用空壳导出或占位命令代表完成。

修正“当前只保留设计文档”的表述：**目前尚未建立产品工程，但已有评测数据准备工具和资产。** 本轮不移动、删除或重写这些工具，也不把它们当作产品 Runtime 已实现的证据。

### 2.2 统一相近目录的职责

完善目录树注释及 §20.5，集中消除容易导致重复实现的表达：

| 工程落点                          | 明确职责                                   |
| --------------------------------- | ------------------------------------------ |
| `core/runtime`                  | 产品 Run、绑定、目标、预算、停止及清理     |
| `runtime-pi`                    | 接入 Pi 的实际执行与原生控制，报告执行事实 |
| `core/tools`                    | 工具登记、共享准入、调用记录及业务 Gateway |
| `runtime-pi/tools.ts`           | Pi 工具契约适配、原生工具接合和结果回送    |
| `employee-invoice/capabilities` | 发票业务能力及其 Handler 的领域实现        |
| `core/memory`                   | 原生历史的数据库保存、去重及完整性         |
| `runtime-pi/memory`             | 原生历史读取、恢复、压缩及存储端口接入     |
| `data/isolation`                | 受控资产读取和纯输入投影                   |
| `core/context`                  | 当前任务的信息选择、业务快照及来源关联     |

补充原则：

- 接入层的 `policy.ts` 只落实产品提供的限制及技术兼容条件，不形成第二套授权或业务策略。
- 候选的领域含义与处理规则属于发票模块；产品接受、持久化及事务沿既有受控端口完成。“由 core 接受”不表示把发票规则放进通用 Kernel。
- Context 构造不承担输入受理或实际投递职责。
- 界面可以合并展示复核、审批和接管，但写入仍分别调用所属业务命令，界面目录名称不改变领域归属。
- 保留各目录的详细职责说明，不因已有模块正文而删减为只有目录名称。

### 2.3 对齐运行目录与存储权威

调整 §20.2、§20.5：

- `runs/<runId>/` 保存既定文件型证据、大产物及受控导出，不再笼统描述为另一套完整消息、工具记录和事件库。
- 原生历史仍以 `sessions/memories` 为准；业务上下文正文归 `context_snapshots`；持久事件、工具调用及业务状态归对应数据库表。
- 文件证据通过 `artifacts` 等既有引用关联；导出和展示副本不能参与另一套独立恢复。
- `runtime/<runId>/` 只保存临时工作资源及获准资源投影，不能成为会话持久化目录。
- `reports/<candidateId>/` 明确指运行组合候选的验证报告，避免与发票候选身份混淆。
- 项目输入、产品运行数据、评测数据分别维护；目录隔离不能代替实际读取入口的权限和用途检查。

同步两处已有冲突：

- 子执行必须在**首个模型请求或任何工具执行前**完成可信绑定，不能仅要求“业务工具调用前”。
- 无法安全续接时，不自动从当前事实空建 Session；仍须满足业务允许、事实充分及旧资源已隔离的条件。

### 2.4 明确公共入口、SDK 依赖与验证边界

完善 §20.3–20.4：

- 产品中的 Pi SDK／插件实现依赖集中在 `runtime-pi`；其他产品模块通过公共契约接入，不引用其私有源码。
- 原生能力验证可以通过 `runtime-pi` 的公开验证入口运行实际 SDK／插件，沿用同一锁定依赖；不为测试建立另一套 Runtime 或独立依赖版本。
- `tests/support` 的“受控 Provider”明确为测试响应设施，不是产品新增的厂商 Provider。
- 功能测试归根 `tests/`；评测设施自身测试归 `agent-eval/tests/`；真实 Agent 效果由独立评测方案管理。
- CLI 与桌面复用公共组装和命令。公共文件被导入不自动启动资源，多入口不产生多个数据库控制者。
- P13 Host 经受控工具和存储端口连接控制侧；Host 装配说明同时体现持久化交接，不只描述工具代理。

保留 Bun、TypeScript、Electron 及现有包边界。根命令随对应能力提供真实可执行入口，不要求早期阶段提前建立桌面或 E2E 空命令。

### 2.5 同步阶段注释和目录维护规则

统一 §20.1、§20.3.1、§20.5、§20.6：

- P4 落地会话、输入及历史存储；P6 验证记忆使用；P7 才启用经过验证的原生压缩。
- P8 交付业务复核与等待能力，P12 增加完整界面及提交审批，避免把必需复核推迟到 P12。
- P10 包含共享控制、绑定和清理；P11 表述为“LLM 调用第三方插件 Agent 工具”，不再使用“原生委派”的简称。
- 同一 Job 新建 Run 不自动升级资源或扩展组合。
- 当前工程状态与命令登记以实际检查为准，不把历史说明长期当作当前事实。
- 修正 §20.5 的章节引用错误，合并重复的 `agent-eval/data/` 行并清理空表。
- 评测内部资产布局由评测总方案维护；主方案保留独立根、产品禁止读取及工程交接约束，避免两处重复定义发生漂移。

本轮不实际生成目录，也不调整现有数据路径。
