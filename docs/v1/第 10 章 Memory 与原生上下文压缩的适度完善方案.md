
# 第 10 章 Memory 与原生上下文压缩的适度完善方案

## 1. 审查结论与修改定位

**第 10 章的主体设计已经完整，存储与恢复协议也较充分，不需要重做。** 已明确 Pi 负责原生历史和压缩，Flowmate 负责 SQLite 持久化、接入控制及恢复核验。

需要澄清的是：

- “为当前任务选择信息”属于第 9 章；本章负责会话历史的保存、使用和原生压缩。
- 完整历史、模型当前使用的上下文、压缩摘要是不同对象。
- 压缩执行成功、保存成功和能够继续执行需要分别判断。
- “切换分支仅更新当前位置”表述过于绝对，可能遗漏原生操作产生的新条目。
- 压缩流程图尚未充分表现保存失败后的绑定失效，以及压缩后仍超限的情况。

本次只完善概念、关键行为和交接边界，不增加记忆引擎或细化 SDK 实现。

## 2. 第 10 章的必要调整

### 2.1 明确会话记忆、活动上下文和摘要的区别

在 §10.1–10.2 补充简短说明：

| 对象           | 职责与边界                                                                       |
| -------------- | -------------------------------------------------------------------------------- |
| 完整会话历史   | sessions/memories 保存完整原生条目、历史树及当前位置，用于恢复和追溯             |
| 当前模型上下文 | Pi 根据当前历史位置及原生机制组织，不等于把数据库全部条目送入模型                |
| 原生压缩摘要   | Pi 为后续上下文使用生成的历史记录，保存于 memories；不替代全部原始历史或业务事实 |

同时明确：

- 压缩主要解决后续模型上下文容量，不等于数据库清理、历史删除或敏感资料擦除。
- 摘要可能遗漏细节，不能承诺无损记忆；关键业务判断仍读取当前业务事实及必要证据。
- 用户纠正通过后续输入或业务修订表达，不直接覆盖旧历史条目。
- 当前只实现 Session 会话记忆，不增加跨任务长期记忆、偏好库、向量检索或自动经验提炼。

### 2.2 统一压缩启用与运行控制边界

完善 §10.2–10.3：

- P1–P6 不开放产品手动压缩或自动压缩；容量不足先减少业务输入、按需读取，仍不足则明确停止。
- P7 起按实际验证结果启用原生手动或自动压缩；两种入口遵守相同的绑定、权限、期限、取消及预算规则。
- 压缩与输入交付、历史位置切换及关闭等操作的交接复用 Pi 已验证机制，不能让相互冲突的历史变更无约束并行。
- 不另建压缩调度器，不由产品生成替代摘要。
- 压缩产生的用量计入既有预算；取消请求不等于压缩已停止，仍须核验实际状态。

精确触发条件、操作交接方式及 SDK 调用留到 P7 方案确定。

### 2.3 分开判断压缩完成、保存和继续资格

在 §10.3 明确三个事实：

1. **原生压缩完成：** 有实际 SDK 结果及原生条目依据。
2. **压缩结果已保存：** 新条目、当前位置及存储版本成功提交。
3. **允许继续执行：** 会话可用、上下文可容纳，且当前授权、期限和预算仍有效。

相应处理：

- 原生压缩成功但保存失败，按既有规则使绑定不可继续，阻断新执行并请求中止。
- 保存成功仍不等于后续任务一定可执行；压缩后仍超限或资格失效时不能继续。
- 压缩失败或取消后先核验实际 Session、已提交历史及容量；不能默认旧内存状态仍可安全使用。
- 压缩只改变历史使用方式，不自动生成新 ContextSnapshot；业务依据改变时才由第 9 章规则更新。
- “成功入库”“恢复成功”“模型正确使用记忆”分别验证，不能互相替代。

### 2.4 澄清历史变更与恢复语义

适度修正 §10.4，保留既有存储路线：

- 将“同一会话切换分支仅事务更新当前位置”改为：保存原生操作实际产生的变化；若仅位置改变，则只更新位置及版本；若同时产生原生摘要或其他条目，则一并保存。
- 所有变化仍由 Pi 产生，Flowmate 不自行重链历史或生成分支摘要。
- 保留原生会话身份、条目引用和当前历史位置；独立分支与源会话的边界沿用既有规则。
- 区分“恢复同一 Session 的已提交历史”与“依据当前业务事实创建新 Session”；后者不能宣称恢复了全部原对话。
- 权限撤销、历史损坏或不兼容时，继续沿用第 9、11 章的受控恢复，不靠压缩隐藏或清除问题。
- P4 的公开变更接入覆盖和 P13 的持久化 ACK 继续列为真实 SDK 验证事项，不把设计契约写成已经验证的能力。

不新增存储接口、表或历史副本。

### 2.5 同步压缩流程图

保留 §10.3 的总体结构，修正以下路径：

- 未启用压缩时，容量不足明确停止，不隐含手动压缩兜底。
- 已启用但未触发压缩，也须满足实际容量和执行资格才能继续。
- 压缩成功后先保存，再核验会话、容量和当前执行资格。
- 保存失败进入“绑定不可继续／阻断新执行／请求中止”，不能只标成可直接恢复的普通等待。
- 失败或取消后，只有实际状态、已提交历史及继续条件均成立才允许继续。
- 将“更新后续业务输入”明确为核验当前事实；只有业务依据变化才更新快照。

## 3. 阶段与评测同步

只修改主方案和 Agent 评测总方案，其他章节仅同步冲突表述。

| 阶段     | 承接重点                                               |
| -------- | ------------------------------------------------------ |
| P1–P3   | 最小内存会话与短上下文，不承诺持久恢复或启用压缩       |
| P4       | 原生条目、历史位置及变更完整保存，分支变化与恢复一致   |
| P6       | 多轮纠正、来源及隔离；保存正确与记忆使用效果分别验证   |
| P7       | 原生压缩、结果保存、容量复核、取消及失败后的继续资格   |
| P8–P9   | 业务事实与历史摘要分离，资源内容不成为独立记忆库       |
| P11      | 主子会话分别绑定、存储和压缩，共享预算但不共用可变历史 |
| P12–P13 | 授权与外部事实不被摘要覆盖，Host 持久化确认及故障恢复  |

评测复用现有 Memory、Compaction、Session、预算和恢复场景，重点覆盖连续压缩、保存失败、压缩后仍超限、分支变更及错误记忆纠正，不新增评测体系或具体 Case。

## 4. 验收与细节边界

文档验收检查：

- 业务信息选择、会话记忆与原生压缩职责清楚。
- 压缩不被描述为无损记忆、历史删除或权限恢复。
- 原生完成、保存成功和允许继续具有独立判据。
- 分支保存涵盖原生实际变化，不遗漏新条目。
- 正文、流程图、存储协议和评测要求一致。
- 保持现有目录、23 张表、状态枚举及 P0–P13 顺序。

本次不生成产品代码，不修改已发布评测资产。锁定 SDK 接入路线保持不变；精确方法签名、触发阈值、操作交接、故障注入及测试步骤，由对应阶段方案确定。
