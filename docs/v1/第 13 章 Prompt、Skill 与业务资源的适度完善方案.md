
# 第 13 章 Prompt、Skill 与业务资源的适度完善方案

## 1. 审查结论与修改定位

**第 13 章的核心边界已经明确，但资源分类和版本生效规则还需要适度补充。** 已定义 Pi 原生资源接入、获准／发现／实际使用集合、内容摘要、按需读取及权限边界，不需要重做。

主要歧义是：

- Prompt、Skill、SOP 和角色定义被放在一起，容易误解为都属于同一种 Pi 原生资源。
- “必需资源”没有直接区分必须可用与必须注入正文。
- Skill 引用的辅助资料、脚本和工具，其依赖边界还不够明确。
- “新运行使用新资源”容易被理解为同一 Job 的新 Run 自动使用最新版本。
- “资源已使用”可能混淆正文已交付和模型正确遵循。
- 资源缺失后的拒绝范围，以及更新、撤销和回退之间的区别需要集中说明。

Job、步骤、审批与提交仍由第 12 章负责；本章负责指导资源的内容、接入、选择及版本治理。

## 2. 第 13 章的必要调整

### 2.1 明确资源分类及接入方式

在章节开头增加简短分类表：

| 类型                   | 定义与接入边界                                                                              |
| ---------------------- | ------------------------------------------------------------------------------------------- |
| 基础／角色 Prompt      | 定义任务角色、行为指导和输出要求，通过适用的 Pi 原生装配入口接入                            |
| 任务模板               | 提供可复用的任务表达；当前任务事实仍由 Context 构造，不把模板当成完整业务上下文             |
| Skill                  | 使用 Pi 支持的原生技能格式与发现、按需读取机制；提供指导，不等于新增工具或可执行 Workflow   |
| SOP／参考资料          | 产品维护的流程说明和辅助材料，可作为 Skill 依赖或业务输入资源，不一律描述为 Pi 原生资源类型 |
| 子角色定义             | 服务于后续第三方 Subagent 插件；具体适配归 P11，不标为 Pi 内置子 Agent 能力                 |
| Workflow／Policy／Tool | 可执行业务规则、授权及工具能力，仍由对应模块实现，资源文本只能说明和引用                    |

明确基础 Prompt 装配、模板展开和 Skill 按需读取不是同一个操作，不要求全部经由同一种 ResourceLoader 行为实现。

具体格式、入口和参数以锁定 SDK／插件版本的阶段验证为准。

### 2.2 明确必需资源、按需读取与使用证据

完善 §13.1：

- **必需资源可用**表示当前能力依赖的资源存在、版本匹配且可以通过获准入口取得，不表示全部正文必须预先注入。
- 基础指令按装配要求提供；按需 Skill 可以先被发现，在实际需要时读取正文。
- 如果某项任务明确要求使用特定 SOP／Skill，其适用要求属于固定任务契约；不能仅凭“已经发现”认定要求满足。
- 显式 Skill 请求仍检查名称、适用范围和当前资格；正文交付不意味着另建 Skill 执行实例或自动完成其中全部步骤。
- 获准集合、已发现集合和实际注入／读取集合继续分别记录。

评测区分三个事实：

1. 资源通过装配核验。
2. 对应内容已实际交付或读取。
3. 模型正确理解并遵循适用指导。

前两项是接入证据，不能代替第三项的真实 Agent 效果评测。

### 2.3 补齐资源依赖和可执行能力边界

适度补充依赖原则：

- Skill 引用的必要模板、参考文件等资源纳入同一获准范围和版本核验，不能只固定入口文件而忽略影响行为的依赖内容。
- 依赖工具或扩展时，只引用已经获准且在当前阶段启用的能力，不因资源加载而自动安装、注册或授权。
- 资源中的命令或脚本说明不直接执行；确需执行时，仍通过已启用工具及其准入规则。
- SOP 文本与可执行 Workflow／Policy 必须保持一致；发现已知冲突时阻断受影响能力，不能让模型自行裁决哪个版本有效。
- 产品不增加包管理器、依赖解析平台或 Skill 执行引擎。

具体依赖声明格式、文件边界和工具映射留到 P9，扩展及子角色依赖随 P10／P11 增量落实。

### 2.4 明确更新、撤销、回退与运行绑定

补充版本生效规则，并同步 P9 的“新运行使用新资源”表述：

- 修改 `resources/` 作者文件不直接改变已固定的运行组合；发布所引用的内容及依赖须可按原版本取得和核验。
- 新 Job 可以显式选择获准的新组合；**同一 Job 创建新 Run，不自动改用最新资源**。
- 既有 Job 更换资源组合走已有显式迁移流程；活动执行不静默热替换，历史 RuntimeSnapshot 不改写。
- 普通更新与立即撤销分开：更新不自动终止仍获准的旧组合；撤销则阻断受影响的新使用及执行，不能以旧快照为继续依据。
- 回退是重新选择仍获准且兼容的旧组合，不回滚业务事实、会话历史或外部动作，也不恢复已撤销权限。
- 换资源版本不等于清除 Session 中已存在的旧资源内容。续接时按既有恢复及迁移规则核验；无法安全续接时停止，或在业务允许的条件下创建新 Session。

沿用现有清单、文件、运行快照和控制记录，不新增资源数据库或历史清洗机制。

### 2.5 明确失败影响范围及职责交接

将“明确拒绝对应候选”的笼统表述细化为：

| 情况                                         | 处理原则                                                       |
| -------------------------------------------- | -------------------------------------------------------------- |
| 基础或当前能力必需资源缺失、不兼容、摘要不符 | 阻断依赖它的装配或执行                                         |
| 可选资源未选用且不是当前能力依赖             | 不声称已使用，也不因此否定无关能力                             |
| 实际请求读取的可选资源失败                   | 明确报告本次失败；按固定任务要求决定是否可继续，不能静默换版本 |
| 未批准资源、名称冲突或范围越界               | 拒绝相应装配／读取，不按加载顺序覆盖                           |
| 已加载资源后续被撤销                         | 按现有权限和执行控制停止受影响使用，不以重新加载或压缩恢复资格 |

补充简短交接关系：

**configuration 固定获准组合 → runtime-pi 核验并接入原生资源机制 → Context 选择必要业务输入 → 记录实际交付／读取证据。**

资源管理不受理用户输入、不调度模型轮次，也不直接推进 Job。若正文已由原生入口提供，Context 不重复拼接。

评测复用现有 MOD-06、RT-07、RTC-07 和相关版本场景，补充：

- 必需资源可用与正文按需读取分别验证。
- 正文及必要依赖版本一致，脚本说明不能绕过工具准入。
- 新 Run 不自动升级既有 Job 的资源组合。
- 更新、撤销和回退具有不同效果，旧 Session 内容不会被误报为已清除。
- 装配成功、实际读取和正确遵循分别记录。
- 可选资源失败不扩大成无关能力失败，也不静默替换版本。

## 4. 验收与细节边界

文档验收检查：

- 各类资源的性质、负责人及接入路线明确。
- 必需、可选、已发现和实际使用不混淆。
- 资源依赖不隐含安装能力或执行授权。
- 版本生效与 Job／Run／Session 的既定绑定规则一致。
- 正文、目录、阶段和评测要求一致。

保持现有目录、23 张表及 P0–P13 顺序，不新增资源平台、记忆系统或 Skill 执行引擎。

本次只调整文档，不生成产品代码，不修改已发布评测资产。精确 SDK 类型、模板格式、依赖声明、加载路径、迁移操作及测试步骤，由对应阶段方案确定。
