
# 第 16 章发票员工完整业务方案的适度完善方案

## 1. 审查结论与修改定位

**第 16 章的主要业务范围已经完整，不需要重做。** 已包含字段抽取、规范化、必要关联、适用业务核查、人工复核、目标提交和权威结果确认。

需要完善的主要是：

- 已有解析、模型候选、已接受修订和目标字段之间的关系。
- 流程图容易让人理解为每张票都必须执行全部关联和核查。
- 规则不通过、资料不足和接口故障被统一画成人工纠错。
- “提交确认或明确策略授权”与第 12 章的正式审批契约不一致。
- API 与浏览器路径的选择、失败交接及完成判据不够明确。

本章描述发票业务如何使用既有 Harness，不重复定义第 12 章的状态机和提交协议。具体字段、企业规则、接口和测试步骤留到阶段方案。

## 2. 第 16 章的必要调整

### 2.1 明确输入、候选、修订与目标载荷

完善 §16.1–16.2，增加简短说明：

| 对象         | 业务含义                                                                     |
| ------------ | ---------------------------------------------------------------------------- |
| 已有解析输入 | 外部工具产生、经接入校验的文档内容，不代表字段已经正确或业务审核通过         |
| 抽取候选     | 模型根据获准输入与证据产生的预测，保留原始结果及来源                         |
| 已接受修订   | 经既定规则和受控命令接受的当前业务字段，人工修改保留修订记录                 |
| 目标载荷     | 根据当前有效修订、目标映射和必要关联构造的提交内容，冻结后用于审批和发送核验 |

同时明确：

- 原票用于获准取证、复核和附件，不在 Flowmate 内重新建设解析功能。
- 规范化不能静默改写票面事实；模型预测、人工修正和计算结果分别保留依据。
- 目标供应商／订单 ID 来自合法关联，不作为模型从票面直接猜出的字段。
- 提供方标签与评测 Gold 不进入业务抽取输入。
- 保持一份输入明确对应一张发票的范围；已有多页解析可用，不增加自动拆票、合票。

### 2.2 明确检查适用性及异常分流

完善 §16.2–16.3：

- 字段关联解决“目标字段应填写哪个对象”；业务核查解决“当前任务要求的业务条件是否满足”，二者分别判断。
- 供应商／订单查询按目标字段或适用核查需要启用，不要求每票执行全部查询。
- 收货、合同、价格、余额／数量等既定核查继续保留，不扩大为付款、入账或企业财务审批。
- 适用条件及阻断规则由领域规则确定，不能由模型临时决定跳过。
- 未实现、未执行、查询失败或依据缺失都不能标成“不适用”或“通过”。

补充异常处理方向：

| 情况                     | 处理原则                                                                   |
| ------------------------ | -------------------------------------------------------------------------- |
| 字段缺失、歧义或证据冲突 | 获准取证或请求人工澄清，接受新事实后重新校验                               |
| 明确业务规则不满足       | 保留不通过依据，按规则修正或进入既有业务处置；人工点击确认不能直接改成通过 |
| 主数据缺失、多候选或过期 | 补充有效依据或人工选择，接受前仍核验范围和有效性                           |
| 接口不可用或查询异常     | 按技术错误与有界恢复处理，不伪装成“无匹配”或业务拒绝                     |
| 疑似重复发票             | 核对已有业务身份及结果，不仅凭相似文本认定重复，也不直接继续发送           |

说明输入文件去重、业务重复识别和提交动作防重是不同职责；发现既有成功或 UNKNOWN 时，沿用原业务记录及提交核对规则，不通过新建 Job 绕过。

### 2.3 统一复核、审批与完成判据

修正 §16.1 的“提交确认或明确策略授权”：

- 改为**有资格操作者批准具体冻结动作，再进行最终发送准入**。
- Workspace／发布策略决定允许范围，不替代 `approvals` 中的具体提交许可。
- 人工复核确认业务事实，提交审批授权具体动作，二者不能互相代替。
- 依据变化、审批拒绝或失效沿用第 12 章处理，不在本章增加第二套审批路径。

区分三个结果：

| 结果         | 判据                                                       |
| ------------ | ---------------------------------------------------------- |
| 可申请提交   | 当前字段、适用核查及必要复核满足要求，可以冻结预览         |
| 提交动作成功 | 已取得与原逻辑动作对应的权威成功证据                       |
| Job 完成     | 权威提交成功，且既定 Workflow 的适用必需事实与完成核验齐备 |

权威成功后仍缺必需核验时，保留成功事实并进入核对，不再次发送。截图或诊断失败不自动推翻权威成功；不借完成核验新增 ERP 回写、付款或入账责任。

### 2.4 明确 API 与浏览器接入边界

完善 §16.3：

- 按获准目标的实际能力确定 API 或浏览器路径，保持同一业务端口、冻结依据及提交协议。
- 正式 API 可用时优先使用；本地模拟仍保留既定真实浏览器验证。
- 浏览器发送前核验页面内容与冻结载荷；API 路径核验实际请求内容与冻结载荷，不要求不存在的页面回读。
- API 失败不能自动切浏览器重新提交；是否可能生效先按原动作核对。
- 保存草稿、上传附件等操作是否产生外部副作用，由目标契约明确，不能因为未点击“最终提交”就默认属于只读操作；实际写入遵守既有受控入口。
- MFA／验证码和未知页面沿用人工接管及恢复核验，不允许人与自动执行同时操作同一页面。

具体目标动作、控件、权威结果形式及路径切换条件由 P12 确定，不新增浏览器平台或提交机制。

### 2.5 修正最终业务流程图

保留 §16.1 的总体链路，调整以下表达：

- 关联与核查标明“按适用条件执行”，不画成每票必须完成全部查询。
- 输入不合格交外部补充；业务缺口、规则不通过和技术故障分别进入对应处理。
- 人工修改后重新核验受影响的字段、关联和业务依据。
- 冻结动作后经过正式审批及最终准入，再执行提交。
- UNKNOWN 进入有界查询／人工核对，不暗示无限轮询或自动重发。
- 权威成功先保存，再判断 Job 完成条件；缺口进入核对。
- 保留“外部权威拒绝且未生效 → 原 Job rejected → 用户决定重办时新建关联 Job”的既定路径。

图示只表达业务交接，不重画第 12 章全部状态转换。

### 2.6 明确模拟与真实业务的交付区别

完善 §16.4：

- P12-A 通用模拟证明本地完整闭环，不代表企业字段与全部业务核查已经验证。
- P12-B 对齐获准企业字段、适用规则和只读业务依据。
- P12-C 使用获准真实测试系统核验实际目标契约及结果。
- 三类环境分别记录业务结果和未覆盖项，模拟回执不能冒充真实平台回执。
- 缺少企业规则、必要主数据或真实测试条件时，明确保留对应缺口，不能把检查标为不适用或宣称完整 P12 通过。

模拟系统继续独立产生可查询结果，不调用产品 Kernel 替产品完成业务判断。
