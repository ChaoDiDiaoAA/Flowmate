
# 第 18 章数据库和文件存储的适度完善方案

## 1. 审查结论与修改定位

**第 18 章的主体设计已经完整，现有 23 张表能够覆盖已确定的功能，不需要重新拆表。** 已包含模块归属、主要字段、约束、事务、ER 图、迁移、恢复及独立日志。

需要完善的主要是：

- 目标数据结构与分阶段实际结构的区别。
- 结构化正文、文件引用及原生 JSON 的约束表达。
- 数据库提交、执行完成和外部效果的边界。
- 备份恢复、迁移与当前执行资格的关系。
- 少量图示、负责人和提交联动表述与前面章节不一致。

本次只完善主方案原则及交接，不继续展开 SQL、驱动参数或逐字段实现。

## 2. 第 18 章的必要调整

### 2.1 明确目标结构与分阶段启用

完善 §18.1、§18.2.16：

- 23 张表是最终目标结构，各阶段只建立当期实际需要的表、字段和约束。
- 尚未启用的 Session、步骤、上下文或审批不能用虚构记录满足未来关联。
- 当期功能依赖的表及约束必须先具备，不能以“后续再完善”为由长期关闭已需要的完整性检查。
- 后续增加约束时验证已有数据，缺少历史事实不能猜补。
- 本章主要字段是设计契约，具体类型、可空条件、索引和迁移 SQL 在相应阶段固定。

集中明确存储职责：

| 模块             | 职责                                               |
| ---------------- | -------------------------------------------------- |
| core/storage     | 连接、事务基础、迁移及受控文件元数据               |
| 各领域模块       | 所属表的业务语义、状态和受控读写                   |
| Kernel           | 协调必要的跨模块授权和事务                         |
| runtime-pi／Host | 经受控端口报告或提交原生事实，不独立拥有业务数据库 |

“共享数据库”不表示所有模块可以直接改写所有表。控制侧管理数据库写入，Renderer、Pi 和 Host 不建立第二套持久事实。

### 2.2 统一正文、引用与版本的表达

完善 §18.1.3、§18.2.14、§18.2.17：

| 内容                                   | 权威存储                        |
| -------------------------------------- | ------------------------------- |
| 产品状态、身份及业务记录               | 所属数据库表                    |
| 原生会话头、条目和压缩内容             | sessions／memories              |
| 业务上下文快照正文                     | context_snapshots               |
| 原票、附件、配置清单、评估快照及大证据 | 受控文件，由 artifacts 定位     |
| 诊断日志                               | logs 下 JSONL，沿用独立日志方案 |

补充原则：

- `json/ref`、`args_hash/ref` 等是主方案简写；阶段契约必须明确实际载体及引用类型，读取时不能靠猜测。
- 对允许正文或文件引用的业务结果，明确哪一份是权威内容；展示副本、摘要和导出不能成为另一份可独立修改的事实。
- 产品 JSON 使用版本化 Schema；Pi 原生内容保留原生格式，以锁定原生版本及既有接入契约核验，不强行插入产品 `schemaVersion`。
- 内容摘要用于完整性和幂等核验，不替代主体权限、业务身份或当前有效性。
- 外键、文件引用、原生条目引用和受控逻辑引用分别核验，不能把 JSON 内任意字符串当数据库外键。
- 内容版本、状态并发版本、历史存储版本和任务代次各按原用途使用，不合并为一个通用版本号。

保留已有存储选择，不新增 BLOB 方案、消息表、压缩表或通用引用服务。

### 2.3 明确事务、提交确认与失败处理

完善 §18.3，并统一各存储段落：

- 数据库事务只覆盖本地事实及引用，不覆盖模型执行、文件写入或外部网络动作。
- 事务内完成必要核验与写入，不等待模型生成、人工回答或远端请求。
- 文件先完整保存和校验，再通过领域事务发布引用；事务失败留下的文件不能被当作业务已经接受。
- 事务成功后再发布对应成功通知；通知或响应丢失不证明事务未提交。
- 调用方无法确认提交结果时，通过原请求身份及持久事实核对，不盲目重复业务操作或清理可能已被引用的文件。
- 数据库冲突或暂时不可写时，沿统一错误与幂等契约处理；存储重试不能连带重放工具、模型请求或外部提交。
- 历史保存失败沿用绑定失效规则；关键业务事实或审计保存失败不得继续依赖未提交状态。

P13 Host 持久化 ACK 只表示控制侧对应存储提交已确认，不表示 Run、Job 或外部动作已经成功。ACK 接入继续保留为真实 SDK／Host 验证事项。

不新增事务协调器、持久化队列或通用重试系统。

### 2.4 完善备份、恢复、迁移与清理

完善 §18.2.16、§18.4：

**备份**

- 备份固定一致性数据库快照及其所需文件版本、清单和摘要。
- 不能以复制一个正在使用的数据库主文件代替既定一致性备份。
- 位于项目来源根等位置的必要业务资产，也须纳入可恢复范围或有已验证的恢复来源。
- 不把可重建临时目录、可选展示投影或诊断日志当作业务恢复的权威依据。

**恢复**

- 先隔离旧控制者与执行资源，核验应用／Schema、数据库、文件引用和摘要，再决定可恢复范围。
- 数据恢复成功不等于允许重新执行；当前撤回、权限、审批和未决外部动作仍须核验。
- 从较早备份恢复时，备份之后可能已经发生的外部动作不能被视为“从未执行”。无法确认期间事实时，保留缺口并阻断受影响的新发送。
- 缺失必需文件时报告受影响对象，不能用日志、旧导出或模型文本补造权威事实。

**迁移与清理**

- 迁移失败不启动依赖新结构的业务；保留原数据及可恢复依据。
- 应用或数据库回退不撤销外部已发生事实，也不恢复已撤销许可。
- 删除前核验保留要求、有效引用和恢复依赖，不能仅凭“当前指针不再指向它”就删除历史文件。
- 清理临时目录、诊断日志和业务证据分别处理，不设置跨域级联清除。

具体备份方式、迁移顺序、保留期限及故障恢复操作留到对应阶段。

### 2.5 同步图示与既有业务契约

修正 §18.2.18–18.2.19 及相关文字：

- 核心关联图明确是数据关联与交接概览，不代表直接调用路径或每阶段都必须执行全部节点。
- Session 节点体现元数据、原生头和当前位置，不再仅概括为“索引”。
- Context 到 Pi 的路径标明经过受控交付；候选到修订经过领域接受。
- 权威回执更新动作、步骤及 Job 时仍按完成判据核验，不画成任何回执都直接完成 Job。
- ER 图的可选关联、当前审批选择关系与正文约束一致；同一审批不能被多个不同动作选用。
- 索引示例统一使用实际表名，避免 `runs/tools/actions` 等简写被误当成另一些表。
- 将“依据变化取消尚未发送动作”限定为全部历史尝试均无可能生效的不明事实；存在旧 UNKNOWN 时继续核对，沿用第 12 章。
- 评测中 Session 元数据归 core/sessions、Run／绑定归 core/runtime、历史提交归 core/memory，消除重复负责人。

不增加关系或状态体系，不重写已确定的提交协议。
