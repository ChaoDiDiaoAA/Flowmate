
# 第 2 章总体架构与 Pi／Flowmate 职责的适度完善方案

## 1. 审查结论与修改定位

**第 2 章的架构覆盖和主要职责已经完整，不需要重新拆包或调整技术路线。** 已说明 SDK 嵌入、产品控制、三类工具、Workspace、权限及 P13 Host 承载。

需要完善的主要是：

- 架构图省略 `core/runtime` 和输入交付职责，容易被理解为 Context 直接驱动 Pi。
- 图中的 Job／Workflow／授权与恢复合成一个节点，容易模糊 Kernel 和领域模块的责任。
- “Runtime”在契约表中同时指产品运行模块和 SDK 接入层。
- Host 交接只概括 Runtime／Gateway，遗漏既有存储端口与提交确认。
- 总览中的完整契约容易被理解为前期必须提供全部对象。
- 少量权限、动作创建和工具职责表述需要与后文统一。

本次保留 §2.1–2.6，明确架构层次、调用方向和交接边界；具体接口字段、SDK 方法和进程通信实现留到阶段方案。

## 2. 必要调整

### 2.1 让总体架构图直接表达模块分工

完善 §2.1，在图前增加简短架构说明：

| 层次               | 职责                                                 |
| ------------------ | ---------------------------------------------------- |
| Application／入口  | 接收可信操作，调用产品命令和查询                     |
| 产品控制与领域模块 | 管理业务事实、执行资格、会话输入、审批和恢复         |
| `runtime-pi`     | 装配并调用 Pi，接入工具、事件、历史及控制端口        |
| Pi SDK／第三方插件 | 执行原生模型与工具循环，提供对应历史、资源及委派能力 |
| 数据与外部接入     | 保存产品事实和文件，读取业务依据，执行获准外部动作   |

调整现有架构图，以模块分组表达以下主线：

**Application／Kernel 协调 → jobs 确定业务目标 → runtime 管理 Run／绑定 → runtime-pi 接入 Pi → Pi 执行原生 Loop。**

同时补齐：

- sessions 管理输入受理与投递归属，Context 提供业务输入选择；实际交付经过执行资格核验，由 runtime-pi 完成。
- Workspace 表示归属和权限边界，不画成独立执行服务。
- Kernel 协调授权和事务；业务事实、Run、输入及动作仍由各自模块负责。
- 保留业务工具、Pi 原生工具和插件工具三条路径，共享准入和记录，不强制使用同一种 Handler。
- 保留 LLM 调用第三方 `Agent` 工具的唯一委派入口；子执行在首次模型请求或工具执行前完成可信绑定。
- 事件返回经过接入关联及产品证据模块，不以普通事件订阅直接推进业务状态。
- 外部提交经过具体动作审批和最终准入，由 submissions 管理发送及核对。

图继续表达目标架构，节点随阶段启用；不是每次任务都经过全部节点，也不代表独立服务或进程。工具内部协议仍由第 6 章详述。

### 2.2 统一 Runtime、Kernel 与领域模块名称

完善 §2.2–2.4：

| 名称                        | 统一含义                                                   |
| --------------------------- | ---------------------------------------------------------- |
| `core/runtime`            | 产品 Run、执行绑定、目标核验、预算、停止和清理             |
| Runtime 端口                | 产品控制调用实际 Agent 执行的公共契约                      |
| `runtime-pi`              | Runtime 端口的 Pi 接入实现                                 |
| Pi ModelRuntime／Agent Loop | SDK 内的模型与原生执行能力，不等同于产品 Run 管理          |
| Kernel                      | 组织受控命令、授权及跨模块事务，不另设领域状态负责人       |
| 发票 Workflow               | 提供领域规则、适用步骤和完成判据，由所属模块接受并保存事实 |

修正总览中的两处表达：

- 将“Kernel 创建持久意图”明确为：Kernel 协调受控命令，由 submissions 管理冻结动作及后续发送事实。
- 将 Handler、领域能力和 Adapter 区分为业务实现及其依赖，不把所有 Adapter 都概括成直接注册给模型的工具。

保留既有模块责任表，只补齐理解总图所需的 context、memory、evidence 和 submissions 交接，不复制全部目录说明。

### 2.3 补齐最小契约中的交付和存储边界

整理 §2.4 的交接表，明确每处“Runtime”所指对象：

- 产品运行模块经 Runtime 端口启动、控制和释放实际 Pi 执行；runtime-pi 报告原生事实，产品模块判定 Run 结果。
- sessions 管理输入身份及消费／处理关联，Context 构造业务输入；接入层报告实际交付证据，不能凭快照存在认定模型已收到。
- 工具调用通过共享控制端口取得执行资格，结果按原调用身份回送。
- 原生历史变更经既有存储端口提交至 `core/memory`；数据库仍是会话历史的唯一持久化来源。
- 实时进度与持久事件分别处理，不将所有流片段都描述为已分配持久序号。

沿用既有接口，不新增服务或消息类型。集中注明：

- 契约表是目标能力概述，各阶段只要求已启用对象。
- P4 前不虚构持久 Session／Memory，P5 前不补造 ContextSnapshot，后期审批和发布记录同样按阶段建立。
- 请求受理、原生执行结束、持久化成功、Run 成功和 Job 完成分别成立。
- 持久动作可在发起 Run 合法结束后，由受控产品主体继续审批、派发及核对，不复用旧 Run 的 Scope。

### 2.4 对齐 SDK 嵌入与 Host 承载路线

完善 §2.1、§2.3、§2.4：

- 保留 P1–P12 嵌入 Pi SDK、P13 将主子 Session 和插件移入 Host 的路线。
- P13 的交接同时包含运行控制、工具代理、历史持久化及事件关联；控制侧继续拥有 Kernel 和业务数据库。
- Host 的持久化 ACK 只确认对应数据库提交，不代表 Run、Job 或外部动作成功。
- Host IPC 属于产品承载边界，不等于采用 Pi CLI RPC，也不意味着每个子 Session 是独立进程。
- CLI 与桌面复用公共组装和命令，多入口不产生多个数据库控制者。
- 保留 TypeScript、Bun、Electron 的现有选择；各承载环境按阶段实测，兼容失败按第 24 章处理，不静默更换已固定路线。
- 尚待验证的原生 Hook、预算、存储和清理接点继续标为阶段核验事项。

不新增 Node 后端服务、Plugin Runtime 或另一套 Agent 引擎。

### 2.5 澄清 Workspace 与权限的概括性表达

保留 §2.5–2.6 的范围、状态及权限矩阵，仅纠正容易误读的文字：

- 请求可以携带目标 Workspace 或对象引用，但引用不构成可信归属或授权；由产品核验，不将“不能自行签发”误写为接口不能接收对象 ID。
- Scope 表达本次获准执行范围，实际操作仍核验当前撤销、状态和对象归属，固定快照不是永久通行证。
- “权限不足是业务拒绝”明确为**当前操作的授权拒绝**，不自动将整个 Job 置为 `rejected`。
- Workspace 暂停及权限撤销阻断相关新操作，不冒充在途执行已停止或资源已释放。
- 主子工具共用产品权限规则；扩展代码属于受信运行域，工具准入不被描述为操作系统沙箱。
