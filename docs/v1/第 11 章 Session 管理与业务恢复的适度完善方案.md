
# 第 11 章 Session 管理与业务恢复的适度完善方案

## 1. 审查结论与修改定位

**第 11 章的主体设计已经完整，不需要重做。** 已覆盖会话归属、多轮交互、输入投递、绑定、归档、恢复及状态转换。

需要完善的是几处操作语义和流程表达：

- 查看历史、恢复原生会话、继续 Agent 执行和恢复业务步骤，尚未集中区分。
- “替换／分支必须创建新 Run”容易被理解为只读查看或创建分支记录也必须启动执行。
- 恢复正文和流程图没有同样明确地表现旧执行隔离及受控新建会话的条件。
- “串行交给 Pi”可能被误实现为等待整轮结束后才允许 steer／followUp。
- 流程图中的迟到回执可能被误读为会自动触发新 Run。

“为当前任务选择信息”仍属于第 9 章；本章负责会话操作、输入续接和业务恢复交接。

## 2. 第 11 章的必要调整

### 2.1 区分四类操作

在 §11.1–11.2 补充简短概念表：

| 操作            | 含义与边界                                                            |
| --------------- | --------------------------------------------------------------------- |
| 查看历史        | 按权限查询数据库及展示投影，不自动启动模型或创建活动 Run              |
| 恢复原生会话    | 从已提交历史重建 Pi 会话及当前位置，只证明历史可恢复                  |
| 继续 Agent 执行 | 当前资格核验通过后，使用有效 Run／绑定执行；旧 Run 已结束时创建新 Run |
| 恢复业务步骤    | core/jobs 根据当前事实和恢复规则决定下一步，不由历史最后一条消息决定  |

明确：打开历史页面、重新打开归档记录和技术恢复成功，都不自动代表业务继续执行。

保留 sessions、memories、agent_runs 和业务表的现有职责。

### 2.2 澄清替换、分支与执行身份

调整 §11.1、§11.4：

- 一个 Run 绑定的 Session 身份不变；**转到另一个 Session 执行**时，须结束旧绑定并创建新 Run。
- 单纯查看分支或获准创建独立分支记录，不因此自动启动 Agent。
- 同一 Session 内切换历史位置，沿用原生历史变更及保存协议；涉及活动执行时先经过受控状态检查，不能在执行中随意改变其依据。
- 分支、恢复或切换界面不继承或扩大业务写权限，也不自动生成新生产 Job。
- 后续普通输入可以通过新 Run 续接同一 Session；独立业务任务仍按既有规则新建 Job 与 Session。
- Job 代次及业务恢复决定归 core/jobs，经 Kernel 协调；Run／绑定归 core/runtime，避免将 Kernel 的事务协调描述为另一套状态负责人。

不新增分支调度器或会话操作类型。

### 2.3 完善恢复顺序与失败分支

整理 §11.2，并与 §11.3 保持一致：

1. 核验可信主体、Workspace／Job／Session 归属及当前放行状态。
2. 阻断旧执行准入，核对旧主子执行、工具和相关资源；未排除旧执行继续操作同一资源前，不开放新执行。
3. 读取当前业务事实、等待事项及未决动作；UNKNOWN 由现有核对通道处理，不通过恢复模型重新提交。
4. 由 core/jobs 判断是否需要继续 Agent 执行、允许从哪个步骤继续，以及是否允许从业务事实新建 Session。
5. 需要执行时建立新 Run 和绑定，恢复获准历史或受控新建会话，重新核验模型、资源、权限及当前输入依据。
6. 装配与必要持久化成功、绑定 ready 且业务继续条件满足后，才开放执行。

保留以下失败边界：

- 历史不可恢复不自动落入“空建新 Session 并继续”；只有业务规则允许且必要事实充分时才能新建，否则报告缺口并停止。
- 新建会话不能声称恢复了全部历史，也不能绕过旧资源未停止、未决输入或 UNKNOWN。
- 部分装配失败清理已创建资源，不留下半可用绑定。
- 仅查看历史或核对外部动作不要求创建 Agent Run；各阶段只核验已经启用的能力。

具体资源隔离、事务划分和恢复接口留到阶段方案。

### 2.4 澄清多轮输入与原生队列的关系

完善 §11.4、§11.6，保留现有状态表：

- “串行交付”指同一 Session 的输入操作有受控顺序和明确归属，不表示必须等待整轮 prompt 完成后才能提交获准 steer／followUp。
- 执行中的追加和调整使用已验证的 Pi 原生入口及队列语义，Flowmate 不另建模型轮次调度器。
- 输入受理、进入原生队列、实际消费和处理完成分别判断；不因排队成功就认定已消费。
- 普通方向调整仍受原目标约束；业务事实或权限变化先走所属命令，必要时终止旧执行并新建 Run。
- 未消费输入只有在停止旧投递、证明未消费并重新核验后才能移交；已消费或投递不明的输入不自动重投。
- Run 正常收尾与并发新输入继续沿用既有准入关闭规则，不重新打开终态 Run。

### 2.5 修正恢复与人工交接图示

更新 §11.3、§11.7 的冲突表达：

- 在开放新执行前明确旧资源隔离条件。
- 历史不可用路径增加“业务是否允许新建”的判断，拒绝时进入停止／报告缺口。
- 迟到权威回执按原动作保存并核对业务状态；**回执到达本身不自动创建或启动 Agent Run**，后续执行仍经受控命令及准入。
- 人工回复先经过所属交互／输入命令处理，再判断是否需要新 Run。
- 将“完成已受理输入，停止并清理”标明为产品与接入层的交接过程，不表示 Pi 提供一个统一产品收尾接口。
- 保留历史恢复和从业务事实新建两种路径，不将所有人工续接都画成必然复用原 Session。

## 3. 阶段与评测同步

只修改主方案和 Agent 评测总方案，其他章节仅纠正冲突表述。

| 阶段   | 承接重点                                                    |
| ------ | ----------------------------------------------------------- |
| P1–P3 | 最小内存 Session 与 Run／绑定职责，不承诺持久恢复           |
| P4     | 查看与执行分离、多轮队列、跨 Run 续接、替换／分支及恢复失败 |
| P6–P7 | 历史恢复与正确使用分开，位置切换和压缩不绕过绑定控制        |
| P8     | 业务恢复决定、人工交接及受控新建 Session                    |
| P11    | 旧主子执行隔离、取消清理及新根执行不继承旧子任务执行权      |
| P12    | 历史页面、人工命令和 UNKNOWN 核对不自动启动或重复提交       |
| P13    | Host 失联、部分装配失败、未决输入及资源隔离后的恢复         |

评测复用现有 Session、steer／followUp、恢复和动作场景，不新增评测体系或具体 Case。

## 4. 验收与细节边界

文档验收检查：

- 查看、历史恢复、Agent 续接和业务恢复具有不同完成条件。
- 只读操作不自动启动 Run，转到另一 Session 执行不复用旧绑定。
- 旧资源未隔离时不开放冲突执行。
- 历史损坏不触发未经业务允许的新建与续跑。
- steer／followUp 不被“串行”表述阻塞到整轮结束。
- 迟到回执和人工回复不绕过当前恢复资格。
- 正文、流程图、状态表及评测一致。

保持现有目录、23 张表、状态枚举及 P0–P13 顺序。不生成产品代码，不修改已发布评测资产。精确 SDK 调用、队列优先级、资源隔离实现、事务及竞态测试步骤，由对应阶段方案确定。
