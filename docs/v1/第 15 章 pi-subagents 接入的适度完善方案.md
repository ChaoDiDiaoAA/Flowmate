
# 第 15 章 pi-subagents 接入的适度完善方案

## 1. 审查结论与修改定位

**第 15 章的主体设计已经完整，不需要重做。** 已明确第三方插件接入、LLM 唯一委派入口、父子身份、只读权限、预算、取消清理、数据库存储及委派状态。

需要完善的主要是：

- Agent 工具调用、委派、子 Run 和子 Session 的关系。
- “首次子执行前绑定”与“首个业务调用前绑定”的要求不一致。
- 插件结果返回、子执行结束、清理完成和父 Run 完成尚未集中区分。
- 活动子任务调整、结束后续聊、历史恢复容易混为一谈。
- 后台模式是否允许脱离父 Run，以及子失败如何影响主流程，需要明确。
- 预算释放表述需要与第 8 章统一。

本次只补充职责、关键行为及阶段交接，不增加调度器或细化插件实现。

## 2. 第 15 章的必要调整

### 2.1 明确调用、委派、执行与历史的关系

在 §15.1 增加简短概念表：

| 对象           | 定义与边界                                                       |
| -------------- | ---------------------------------------------------------------- |
| Agent 工具调用 | 主 LLM 发出的真实插件调用，是创建委派的唯一入口                  |
| Delegation     | 产品对本次委派请求、准入、结果及清理的关联记录                   |
| Child Run      | 一次获准子执行的产品记录；拒绝发生在准入前时不虚构子 Run         |
| Child Session  | Pi 原生子会话及其持久历史，可以在获准续聊时由后续子 Run 继续使用 |
| 插件 agentId   | 插件实际执行身份，通过真实证据关联，不替代产品 Run／Session 身份 |

补充：

- 首版一个 Agent 调用对应一个前台只读子任务；未来启用多子模式时，沿用已有槽位与关联规则。
- 主 LLM 在获准角色范围内提出具体核查要求，产品核验范围、依据及执行资格，不自行生成另一套任务调度。
- 委派不是每张发票的强制步骤；P11 验证真实委派能力，产品运行按任务需要使用。
- P11 的 Driving Task 将“调用原生 Agent”统一为“调用第三方插件 Agent 工具”，避免误认为 SDK 内置 Subagent。

### 2.2 统一创建与首次执行前的可信绑定

完善 §15.4–15.5，统一为：

**真实 Agent 调用 → 委派准入及子 Run／预算登记 → 插件创建实际子 Session → 身份、存储、工具及 Scope 绑定完成 → 开放子执行。**

明确：

- “pending 子 Run”只是待绑定描述，实际 Run 状态仍为 queued。
- 完整绑定必须在首个子模型请求或工具执行前成立，不能等到首个业务工具调用才补齐。
- 子 Session 不默认继承父工具、全部历史或权限；只装配当前角色获准能力和所需资料。
- 无法在首次执行前建立边界的模式保持关闭；必要兼容补丁仍限于已有装配、关联及存储接入范围。
- 产品可以登记、核验、取消和清理，但不能绕过真实 Agent 调用主动创建子任务。

补充“只读”的含义：子 Agent 不修改共享业务事实、不提交外部动作，也不取得审批权；产品保存其历史、运行记录和结果证据不属于子 Agent 获得业务写权限。

### 2.3 区分结果回送、执行完成与业务采纳

完善 §15.3、§15.6：

| 事实             | 表示什么                                                               |
| ---------------- | ---------------------------------------------------------------------- |
| 插件工具返回     | 插件已经回送结果或状态，不自动证明子目标完成、资源释放                 |
| 子 Run 完成      | 满足该次子执行的目标和运行结束条件                                     |
| 委派 finished    | 按既有状态契约完成结果登记及必要清理；结果可以是成功、失败、取消或拒绝 |
| 主流程采纳子结果 | 当前来源、修订、范围和业务规则核验通过                                 |
| 父 Run／Job 完成 | 分别满足产品运行目标和业务完成判据，不能由单个子结果代替               |

补充结果处理：

- 子输出仍是建议或证据，主 Agent 汇总不等于产品已接受业务事实。
- 截断、冲突、部分失败和缺失来源须明确保留，不能包装为完整成功。
- 子任务失败不必然导致父 Run 失败；主流程可以在当前目标、权限和预算内继续处理或合法交接，但不能把缺失的必需结果当作已满足。
- 新委派仍须由主 LLM 再次调用 Agent 工具，经当前准入处理；适配器不自动补发失败任务。
- 结果回送丢失或状态不明时按原身份核对，不因界面缺少结果而重新执行。
- 旧修订或父执行失效后的迟到建议按既有规则归档，不覆盖当前事实或恢复旧执行权。

### 2.4 明确前台、后台、调整与续聊的边界

完善 §15.2–15.4、§15.6：

- 首版继续保持一个前台只读子任务、深度 1、总子并发 1；未启用模式保持关闭。
- 后续有限并行、后台及续聊按具体任务逐项启用，不作为首版必须一次实现的能力。
- 前台表示主调用等待插件返回；未来后台模式只表示父执行可以继续处理，不意味着子任务成为脱离父 Run 的独立后台作业。
- 父 Run 正常成功或确认取消前，须核对已准入子执行和必要清理；故障导致父 Run 失败时，仍保留未清理子执行的回收责任并阻断冲突执行。

区分三类操作：

| 操作               | 身份与行为                                                             |
| ------------------ | ---------------------------------------------------------------------- |
| 调整仍活动的子任务 | 使用已启用、已验证的原生入口及当前身份，不扩大原任务范围，不创建新委派 |
| 已结束子任务的续聊 | 新的 LLM Agent 调用创建新委派／子 Run，可复用符合条件的持久子 Session  |
| 查看或恢复子历史   | 查询或恢复已提交内容，不自动创建、启动或续跑子任务                     |

结果读取和 steer 不得成为隐式创建入口；产品发起的取消、回收与状态核对也不属于新增委派。

### 2.5 统一取消、资源释放与预算核对

调整 §15.3–15.4：

- 取消受理、实际模型／工具停止、资源清理完成分别记录。
- 执行槽位释放与费用结算分别判断，不能因费用尚未明确而伪造资源仍在执行，也不能因资源停止就清零费用。
- 已知消耗按第 8 章 settled 结算，并退还未用预留。
- released 仅用于有依据确认未产生消耗且满足停止条件的情况。
- 未知用量保留占用，主子请求、重试及压缩继续归入既有 Job 预算，不与插件汇总重复记账。
- 新父 Run、子续聊或新绑定不自动重置 Job 消耗及未知占用。
- 取消与结果同时发生时保留实际结果及已提交证据，不能仅凭取消请求覆盖已有事实。

保留当前应用进程／Host 的分阶段回收路线；Child Session 不被描述为可以独立终止的进程。

### 2.6 同步时序图与数据库恢复说明

更新 §15.1.1 时序图，补齐：

- 插件创建前的产品准入、子 Run 及预算登记。
- 实际子身份取得后的存储与可信绑定。
- 绑定完成后才进入子模型／工具循环。
- 插件结果回送与产品终态、清理核验分别表达。

完善 §15.5：

- 子历史恢复只证明已提交内容可恢复；继续执行仍须满足当前任务、模型、资源、权限及绑定条件。
- 原生目录为空时的数据库恢复验证，不等于允许插件自动恢复执行。
- 续聊须使用新子 Run 和有效绑定，不复活旧委派或旧 Scope。
- 历史不可恢复不静默退回文件路径或空建会话；新建会话仍受既有业务恢复规则约束。
- 当前插件文件分支、最早绑定入口和存储工厂覆盖继续作为锁定版本验证事项，不写成已接通能力。

不新增子任务表、会话副本或存储接口。

评测复用 MOD-34、RT-17、RTC-17 及现有联合场景，补充：

- 首个子模型请求前绑定成立，而不只是首个业务工具前。
- 真实调用、委派、子 Run、子 Session 和插件身份关联正确。
- 插件返回、子完成、委派清理、父完成分别验证。
- 子失败、部分结果和迟到结果不会被误算为业务成功。
- 活动调整、结束后续聊和历史恢复具有不同执行语义。
- 后台子任务不因父 Run 结束而获得独立执行资格。
- 资源槽位、已知消耗和未知占用分别核对，恢复不重置额度。

机制测试、真实主子模型行为和业务效果继续分别记录；不以子任务数量增加独立样本数，也不提前制作具体 Case。
