
# 第 12 章产品执行控制的适度完善方案

## 1. 审查结论与修改定位

**第 12 章的主体设计已经完整，不需要重做。** 已覆盖业务状态、步骤追踪、人工复核、提交审批、动作防重、权威结果、UNKNOWN 核对和检查点恢复。

需要完善的主要是跨对象交接：

- Kernel、领域 Workflow 和各模块的状态负责人表述尚不完全统一。
- 审批拒绝、过期或撤销后，Job、Approval 和 Action 的处理没有充分对应。
- 动作申请、实际发送与结果核对，和发起它的 Agent Run 之间的生命周期关系需要明确。
- “权威提交成功”与“Job 完成”之间还需要核验什么，容易被无限扩大。
- 步骤恢复图容易让人理解为每次恢复都必须启动 Agent。

本次只补充职责、关键行为和阶段要求；具体命令参数、事务实现、目标接口及并发测试步骤留到阶段方案。

## 2. 第 12 章的必要调整

### 2.1 统一业务决定与状态写入职责

完善 §12.1、§12.4、§12.5：

| 模块                      | 统一职责                                   |
| ------------------------- | ------------------------------------------ |
| employee-invoice/workflow | 定义发票步骤、适用条件、业务转换和完成判据 |
| Kernel                    | 组织授权、版本检查及跨模块事务协调         |
| core/jobs/steps           | 管理 Job、步骤尝试、业务代次和恢复位置     |
| core/reviews              | 管理业务澄清、复核及接管交互               |
| core/approvals            | 管理具体冻结动作的审批决定与有效性         |
| core/submissions          | 管理动作、发送尝试、回执及结果核对         |
| core/runtime              | 管理 Run、绑定、执行资格、停止和清理       |

将“core/jobs 的 Kernel”“Kernel 在 core/jobs/steps 内创建尝试”等容易混淆目录与职责的表达统一。

领域规则提供决定，所属模块执行受控更新，Kernel 协调必要事务；不增加统一状态管理服务，也不改变 Pi 原生 Loop。

### 2.2 补齐审批与 Job／Action 的联动

完善 §12.1.1、§12.2.4、§12.3.2，以现有状态明确以下处理：

| 情况                                             | 处理原则                                                                                                      |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| 人工拒绝当前提交审批                             | Approval 保留 rejected；无可能生效的尝试时取消当前 Action，Job 返回 reviewing，由用户决定修正或结束业务       |
| 许可过期、撤销或主体资格失效，但冻结业务依据未变 | 阻断发送，Job 返回 reviewing；符合现有条件的 Action 可保留 awaiting_confirmation，重新核验后申请新的 Approval |
| 载荷、目标或冻结业务依据改变                     | 无在途不明事实时取消旧 Action；Job 返回 reviewing，新依据须重新冻结动作和申请审批                             |
| Action 自身到期                                  | 保留 expired 终态；再次处理须经复核创建新 Action，不延长旧动作冒充原许可                                      |
| 存在可能已生效的尝试                             | 保留 sending／unknown 及核对责任；不能因审批失效而回到可重新提交的复核路径                                    |
| 外部权威拒绝且确认未生效                         | 按既有规则终结原 Job 为 rejected；后续修正通过新关联 Job 处理                                                 |

补充两项交接规则：

- reviewing 重新进入 awaiting_approval 时，核验当前依据；符合复用条件的冻结 Action 可以申请新审批，已经取消、到期或依据变化的动作不能复用。
- **拒绝一次审批不自动等于拒绝整个 Job。** 正式业务拒绝和人工结案仍走各自命令。

保留现有枚举，统一转换表的触发条件、联动说明和图示，不新增审批流程。提交确认不默认引入金额审批；既有运行放行范围和限额保持。

### 2.3 明确持久动作与 Agent Run 的关系

完善 §12.3–12.3.1：

- Agent 工具申请动作成功，只证明动作及审批事项已持久受理。
- 发起 Run 可以在满足既定交接目标后结束；后续人工审批、产品派发和结果核对不要求该 Run 持续存活。
- 派发器使用受控产品主体，按照当前 Job、Action、审批及控制事实取得本次发送资格，不沿用已结束 Run 的 Scope 或绑定。
- Run 正常结束不会自动取消已受理动作，也不会自动批准发送。
- 用户取消执行、撤销审批、停止业务和人工结案仍是不同命令，分别影响其负责对象。
- 只有后续业务确实需要模型处理时，才经 Runtime 创建新的获准执行。

保持提交模块的唯一外部写入口；不增加后台 Agent 或新的调度平台。

### 2.4 明确提交成功与业务完成的范围

完善 §12.1、§12.3、§12.5：

| 事实             | 完成判据                                                   |
| ---------------- | ---------------------------------------------------------- |
| 请求提交步骤完成 | 冻结动作及相关请求已持久受理                               |
| 提交动作成功     | 获得与原逻辑动作对应的权威成功证据                         |
| Job 完成         | 权威提交成功，且当前 Workflow 规定的适用必需步骤及事实齐备 |

同时明确：

- 必需核验范围由既定 Workflow 和任务依据确定，不能在成功后由模型或界面临时追加。
- 提交前必须满足的校验，不能留到提交后补做。
- 提交后的完成核验主要确认目标业务对象、提交结果及本地事实记录一致；不新增 ERP 回写、付款或入账流程。
- 已成功动作若仍缺必要核验，Job 保持 reconciling 并明确缺口；不得再次发送。
- 截图或诊断失败按证据要求判断影响，不抹除已有权威成功。只有确属必需证据缺口时才影响 Job 完成。

保留现有业务核查范围，不把“完整完成”扩展成额外业务责任。

### 2.5 澄清步骤恢复与执行方式

完善 §12.5.1–12.5.5：

- 业务阶段表示位置，StepAttempt 表示一次具体尝试，二者不要求一对一。
- 固定步骤清单按领域适用条件启用，不要求每张发票机械执行全部匹配和人工步骤。
- 等待对象满足后，先由所属命令接受事实，再判断步骤是否已经完成、继续等待或需要执行。
- 人工或确定性产品命令可以直接完成适用步骤，不必额外启动模型。
- 需要 Agent 时才经 Session／Runtime 恢复及准入；检查点不授予执行权。
- 新代次建立新尝试，但仍有效的人工等待对象可以受控关联，不重复发起同一问题或审批。
- 已终结尝试不重开；迟到结果按原身份保存，由当前业务规则决定是否可采纳。

将协作引用中的笼统 `humanActionId` 改为适用的 `interactionId`、`approvalId` 或既有请求身份，不增加新的身份体系。

### 2.6 同步图示与查询语义

保留现有图的组织方式，修正：

- Job 图明确审批拒绝、许可失效与业务正式拒绝的区别。
- Action 图与正文区分许可失效、冻结依据变化和在途未知。
- 步骤恢复图先判断等待、事实接受及执行者类型；仅需要模型时进入 Runtime／Session。
- 状态查询分别展示 Job、步骤、审批、动作、尝试及未决事项，不用一个“失败”或“完成”覆盖所有对象。
- 迟到回执可核定原动作，但不自动启动新 Agent、重开旧步骤或改变人工结案统计。

- 审批拒绝不误终结整个 Job，正式拒绝不被重新打开。
- 许可失效、依据变化和外部 UNKNOWN 分别处理。
- 发起 Run 结束后，合法审批和派发可继续；失效 Scope 不能被复用。
- Action 成功不冒充 Job 完成，缺证据不触发重发。
- 等待结果可通过业务命令处理，不强制创建 Agent Run。
- 跨对象事务失败不留下部分批准、可提交或完成事实。

机制测试、真实 Agent 行为及业务结果继续分别记录，不新增评测体系或具体 Case。
