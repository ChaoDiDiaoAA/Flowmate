
# 第 9 章上下文工程的适度完善方案

## 1. 审查结论与修改定位

**第 9 章的主体设计已经完整，不需要重做。** 已明确产品选择业务资料、Pi 组织原生历史与请求，以及快照存储、按需取证、权限检查和实际请求关联。

需要澄清的是：

- “输出本次 Run 的 ContextSnapshot”容易被理解为一个 Run 只有一份快照。
- “按优先级装入”混合了信息选择顺序、可信程度与业务事实效力。
- Context 与原生历史、Prompt／Skill 的装配边界需要更直观。
- 资料缺失、证据冲突、容量不足和权限撤销应分别处理。
- 流程图从快照存储直接连到 Pi，省略了既有交付核验。

本次只明确职责、选择原则和关键行为；不增加检索平台、长期记忆或新的上下文引擎。

## 2. 第 9 章的必要调整

### 2.1 明确上下文组成及责任边界

在 §9.1 补充简短分类：

| 信息类型           | 来源及处理原则                                                                     |
| ------------------ | ---------------------------------------------------------------------------------- |
| 当前任务上下文     | 产品固定的目标、约束、步骤、有效修订及选用资料，由 core/context 选择               |
| 会话上下文         | 当前 Session 的原生历史及摘要，由 Pi 解释和组织，产品不另建历史拼接逻辑            |
| 工具上下文         | 实际工具结果、状态和错误经 Pi 原生历史回送；被产品采纳为新业务依据时再更新业务快照 |
| Prompt／Skill      | 使用同一获准资源清单，通过既定原生入口装配；Context 不重复注入相同正文             |
| 用户长期记忆与日志 | 当前不新增长期用户记忆；日志不是默认上下文源，不自动注入其他会话或任务材料         |

明确 Context Builder 只负责选择和构造业务输入；输入受理、实际交付及原生请求组织沿用第 7 章职责。

### 2.2 区分选择顺序、可信程度与事实效力

调整“按优先级装入”的表述：

- 该顺序表示任务信息的组织与选择原则，不承诺直接对应 Provider 消息角色或最终请求的物理排列。
- 系统约束、角色指导、用户要求、当前业务事实和取证资料分别组织；自然语言内容不能改变产品权限。
- 当前已接受业务事实用于判断业务状态；历史陈述、模型预测、工具返回和原始资料保留各自来源，不因进入上下文就自动成为已确认事实。
- 新证据与当前事实冲突时，标明冲突并按业务规则复核，不按“最后出现”或“模型更相信哪条”覆盖修订。
- 仅选择完成当前步骤所需且获准的材料，保留已有来源、版本和有效时点，不默认扩大读取范围。

具体 Prompt 排列、角色映射和片段选择方式由阶段方案确定。

### 2.3 统一快照、原生历史与实际请求的关系

调整章节引言及 §9.2.1：

- ContextSnapshot 表示**一次明确的业务输入选择及其依据**；同一 Run 可以产生多份快照，多次模型请求也可以复用同一快照。
- 普通消息、工具结果和原生历史增长不自动生成新快照；业务目标、已接受事实或选用依据改变时，按既有规则追加快照。
- 快照保存所选事实、输入投影及来源引用，不复制完整 Session 历史，也不等于最终 Provider 请求。
- 原生压缩由 Pi 执行，压缩条目进入 memories；压缩本身不要求新建业务快照。
- 快照证明当时选择了哪些业务信息；实际交付及请求关联由接入证据证明，不能仅凭快照存在就声称模型已经收到或正确使用。
- 当前 Run 的最新快照指针只表示当前选择，不能改写旧请求、工具调用及候选的实际依据。

保留现有 `context_snapshots`、请求关联和不可变存储契约，不增加模型请求表。

### 2.4 分别处理不足、冲突、容量和失效

完善 §9.2：

| 情况                 | 主方案处理原则                                                                                   |
| -------------------- | ------------------------------------------------------------------------------------------------ |
| 资料不足             | 在当前权限与预算内按需取证；仍不足则明确缺失或请求人工，不猜补业务事实                           |
| 证据冲突             | 保留冲突来源，交业务规则或人工处理，不把冲突当成单纯缺少资料                                     |
| 上下文过大           | 优先减少无关或重复内容，限制单次读取，使用有来源的片段及引用；不得静默截断关键约束后声称信息完整 |
| 历史过长             | P7 起使用已启用的 Pi 原生压缩；压缩失败或仍超限时按既有规则停止或进入受控恢复                    |
| 资料、修订或权限失效 | 阻断受影响执行，重新核验后构造有效输入；新快照不能恢复旧授权                                     |

容量控制需考虑原生历史、工具定义、资源内容和响应空间，不能只看业务快照大小。具体额度、估算方式和压缩阈值留到阶段方案。

另明确：权限撤销不会自动删除已进入原生历史的资料。不能声称“换一份快照就已清除旧内容”；受影响会话能否继续使用，须经过受控恢复与访问核验，不自行删改原生历史。

### 2.5 修正上下文流程图的交付边界

保留 §9.3 主流程，补齐：

**选择资料 → 来源／范围／时效检查 → 保存快照 → sessions／runtime-pi 核验并交付 → Pi 组织实际模型请求。**

同时表达：

- Prompt／Skill 引用同一资源清单，已由原生入口装入的正文不重复拼接。
- 普通工具结果进入原生历史；被产品采纳为业务依据时，才按既有规则更新快照。
- 权限或依据失效时先阻断受影响执行，不能仅沿“重新构造快照”路径直接继续。

不把图扩展成新的调度流程，也不在主方案规定具体 SDK 调用。

## 4. 验收与细节边界

文档验收检查：

- Context、原生历史、工具结果和资源装配职责清楚。
- 信息选择顺序不冒充权限层级或事实效力。
- 一个 Run 可有多快照，历史增长不导致逐轮复制快照。
- 缺失、冲突、容量不足和权限失效有不同处理方向。
- 流程图包含交付核验，快照存在不冒充模型已使用。
- 保持现有目录、23 张表及 P0–P13 顺序。
