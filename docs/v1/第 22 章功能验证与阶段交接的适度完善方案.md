
# 第 22 章功能验证与阶段交接的适度完善方案

## 1. 审查结论与修改定位

**第 22 章的基本框架完整，不需要重做。** 已覆盖开发验证、独立评测交接和最终产品验收，并明确不能用 Mock、静态页面或空报告代替实际证据。

需要完善的主要是：

- 确定性测试、真实 SDK 接入验证、真实模型效果与业务结果的证明边界。
- 交接给评测侧的“固定候选”具体指什么，以及如何接收评测反馈。
- 必需检查失败、证据不足与可选能力未启用的不同处理。
- 最终产品验收清单与阶段退出条件的关系。
- 少量概括性表达容易与前面模块契约冲突。

本章负责“如何验证、如何交接、如何判断完成”；功能建设顺序仍由第 21 章定义。具体用例、阈值、命令和报告格式留到阶段方案。

## 2. 第 22 章的必要调整

### 2.1 明确不同验证方式能够证明什么

完善 §22.1，增加简短对照：

| 验证方式               | 证明范围                                                 |
| ---------------------- | -------------------------------------------------------- |
| 确定性功能测试         | 规则、状态、权限、事务、幂等和错误处理是否符合契约       |
| 实际 SDK／插件接入验证 | 真实原生执行、工具回送、事件、历史及控制接点是否正确接合 |
| 真实模型验证           | 模型是否正确选择工具、使用信息、遵循约束及完成当期任务   |
| 实际业务链路验证       | 在对应目标环境中，业务事实、审批、提交及权威结果是否成立 |

补充原则：

- 受控模型响应可以用于验证真实 Pi／插件机制，但不能证明真实模型效果。
- 使用真实模型也不能代替权限、幂等及故障边界的确定性验证。
- 模拟系统只证明模拟范围；企业模拟、真实测试及生产结果分别报告。
- 功能测试随开发运行，不要求全部模块完成后才测试；真实 Agent 效果评测在相关能力可运行后执行。
- 普通测试默认离线，Live 执行仍须满足当前身份、数据、环境、允许动作和预算条件。

修正“Mock 不能代替真实模型工具循环”的笼统表述，避免误将“实际 Pi Loop＋受控响应”的机制测试判为无效。

### 2.2 让功能证据清单对应已启用模块

完善 §22.1 的验证面表：

- SDK 接合覆盖实际模型身份、原生 Loop、工具回送和控制；恢复、压缩、扩展及主子协作随阶段启用。
- 明确列出 Session／Memory／Context 的证据：输入消费、历史及位置恢复、当前业务依据、实际交付关联和压缩保存分别验证。
- 工具控制按三类工具的实际执行路径检查；审批和外部发送仅在对应阶段启用。
- 业务状态覆盖复核、审批失效、UNKNOWN 与迟到事实，不能用消息或 Run 终态代替业务结论。
- 界面与 Host 验证按 P12／P13 开展，前序 CLI 通过不代表后续承载环境通过。

说明该表是**最终验证范围索引**，各阶段只承担当期已启用部分，不成为提前实现所有模块的清单。

回归沿用第 21 章：覆盖受影响前序能力和关键约束，不机械重跑所有历史检查，也不能只验证新增正常路径。

### 2.3 补齐产品与独立评测的双向交接

完善 §22.2：

**产品向评测侧提供：**

- 固定的执行组合及依赖摘要；这里的“候选”指运行组合候选，不是发票字段候选。
- 已启用能力、限制、输入输出契约、获准环境及动作。
- 当期实际存在的运行、取消、恢复和证据查询入口。
- 隔离初态、资源归属、停止／清理责任及适用功能报告。
- 实际运行身份、装载事实及证据引用，使结果能够关联到被测组合。

P0 只交接真实基础能力，不虚构尚未实现的 Runtime 入口；后续接口随对应能力提供。

**评测侧向产品返回：**

- 绑定实际组合、输入、环境和评测资产版本的质量结论。
- 已覆盖范围、限制、失败归因、证据缺口和需要产品修复的事项。
- 修复后的适用回归结果及前序证据可继承范围。

同时明确：

- 评测可以在获准测试范围内调用产品受控命令，不直接改业务数据库或重写 Runtime。
- 取消测试时，评测侧停止派发并请求取消所属执行；实际停止和清理由产品负责，不能把取消受理当作已清理。
- 对正常生产业务的观察沿用只读关联边界，停止观察不等于取消业务任务。
- 已有功能报告满足版本、范围及证据条件时可以复用；证据失效或覆盖不足时补验证，不要求质量侧复制全部功能测试。
- 首次试评不要求候选先拥有自己的通过结论，但必须具备当期必要的执行资格和控制条件。

修正“按本章 P0–P13”指向第 21 章，避免阶段依据不明确。

### 2.4 区分验证结论与完成资格

在 §22.2–22.3 补充统一处理：

| 情况                                   | 处理原则                                                 |
| -------------------------------------- | -------------------------------------------------------- |
| 必需功能失败或相关回归失败             | 由所属模块修复并验证，不能签署依赖该能力的阶段完成       |
| 缺环境、未执行、证据不足或评测设施异常 | 保留缺口，不直接当作产品通过，也不无依据归为模型能力失败 |
| 已明确为可选且未启用                   | 记录限制，不计入已完成能力                               |
| 功能和质量要求满足                     | 作为阶段退出或产品验收的依据，仍按既定责任核验           |
| 取得生产放行或具体动作许可             | 由发布治理及业务授权分别决定，测试成绩不能直接授予权限   |

保留以下边界：

- 阶段完成由阶段负责人依据第 21 章判断，质量侧不直接更新产品业务状态。
- 候选存在、功能测试通过、质量结论通过、阶段完成、生产放行和动作批准是不同事实。
- 修复或变更后按实际影响范围重新验证；历史结果保留，不能通过改报告摘要或资产答案制造通过。
- 本章不新增评分体系、阶段状态表或审批流程。

### 2.5 澄清最终产品验收清单

保留 §22.3 的 PC-01–PC-06，不新增验收编号：

- 六项是最终交付的能力维度，不要求每阶段全部满足。
- 每项按对应阶段逐步积累证据，最终结论检查证据对当前交付组合及范围是否仍适用。
- PC-03 区分工具登记／准入、Skill 发现／按需读取、Extension 装载／停用／清理，不用同一组操作暗示三者具有相同生命周期。
- PC-04 将笼统的“旧结果拒绝”改为：失效执行建议不能推进当前任务；迟到权威回执仍按原动作核对，不能一律丢弃。
- P12 三类测试环境与 P13 工程／生产证据分别成立；未取得真实条件时报告已完成部分和缺口，不能签署完整生产交付。
- 最终验收保持固定发票员工及既定范围，不增加第二业务任务、通用员工平台或额外财务流程。
