
# 第 19 章员工、能力版本与产品操作的适度完善方案

## 1. 审查结论与修改定位

**第 19 章的主体设计已经完整，不需要重做。** 已定义固定员工、不可变运行组合、实际装载快照、发布控制、迁移回退及产品入口。

需要完善的主要是：

- 员工版本、组合候选、生产放行和实际运行快照之间的关系。
- “未获准清单只允许 Test”容易被理解为测试可以绕过基础授权。
- 初始化快照与后续按需资源使用的区别。
- 迁移时直接创建新 Session 的表述缺少既定业务条件。
- 产品入口中的“暂停、恢复、回退”尚未直接说明操作对象及效果。

本次只明确概念、职责和关键行为，不增加员工管理平台、发布系统或复杂配置页面。

## 2. 第 19 章的必要调整

### 2.1 区分员工、组合、放行与运行事实

完善章节引言及 §19.1，增加简短对照：

| 概念                        | 定义与边界                                                          |
| --------------------------- | ------------------------------------------------------------------- |
| employeeKey                 | 固定发票员工的稳定产品身份，不代表某次执行或已获准版本              |
| 员工语义版本                | 人可识别的版本说明，不能单独定位全部实际依赖                        |
| ExecutionManifest／组合候选 | 固定模型、工具、资源、实现及环境约束的不可变组合，以引用和摘要定位  |
| 发布控制                    | 对具体组合、环境及范围的验证与放行状态，不修改组合正文              |
| RuntimeSnapshot             | 某次绑定经过核验的实际装载事实，不等于发布许可或整个 Run 的最终记录 |
| invoiceCandidateId          | 发票字段预测身份，与运行组合候选无关                                |

明确：

- 同一员工可以有多个历史组合；当前不增加通用员工创建功能。
- 文件保存成功、组合可装载、验证通过、正式放行和实际执行是不同事实。
- 创建新 Run 不自动选择最新组合；历史 Run 保留原组合及装载证据。
- 产品接口继续使用既有 manifestRef/hash、executionMode 和控制引用，不新增版本身份体系。

### 2.2 澄清 Test、环境变化与发布资格

完善 §19.1、§19.1.1：

- 将“未获准清单只允许 Test”改为：**尚未取得对应生产放行的候选，可以在已获准测试范围内验证。**
- Test 仍须满足可信主体、来源与依赖、输入范围、工具权限和预算要求，不能运行未获准扩展或访问任意目标。
- 候选不需要先通过自身评测才能开始测试；但已有撤销、停写和安全限制仍有效。
- Test／Shadow／Canary／Production 表示运行及放行范围，不等于物理目标环境。标记 Test 不能把生产目标变成测试目标。
- 目标、实现或部署组合改变时，按既有规则形成新固定组合；测试环境的旧报告不自动证明新目标已通过。
- 前序证据仅在组合、范围和验证内容适用时引用，明确继承范围与尚待验证部分，不能改报告摘要冒充同一候选结果。
- Shadow 保持只读，生产写入仍须当前范围放行和逐动作审批。

保留现有发布状态及 P13 放行阶梯，不新增第二套发布流程。

### 2.3 明确 RuntimeSnapshot 与后续使用证据

完善 §19.1：

- RuntimeSnapshot 固定初始化时已核验的模型、工具、资源发现／装载、扩展及绑定事实。
- 获准集合、已发现集合和实际注入／读取集合仍按第 13 章区分；可选 Skill 不要求初始化时全部读取正文。
- 后续按需资源读取、上下文选择及工具调用，通过既有事件和对应记录关联，不反复改写初始化快照。
- 快照中的初始 Context 引用不代表整个 Run 只使用这一份上下文，也不能替代后续实际请求关联。
- binding-ready 由运行模块依据装载核验结果管理；core/configuration 核对组合，runtime-pi 报告实际装载，不产生第二个绑定状态负责人。
- 装配或必要持久化失败时，不发布可执行绑定，按既有规则处理部分资源和清理。

继续复用 Pi 的模型、资源及扩展机制，不把快照管理写成新的 Runtime。

### 2.4 统一更新、暂停、撤销、回退与迁移

完善 §19.1–19.1.1：

| 操作         | 处理原则                                                                     |
| ------------ | ---------------------------------------------------------------------------- |
| 发布新组合   | 增加可选择版本，不自动替换活动 Run 或既有 Job                                |
| 暂停放行     | 阻断受影响的新准入；已有执行按当前控制及停止规则处理，不宣称资源已释放       |
| 撤销资格     | 沿用现有不可复活规则，不能换 controlId 或旧快照绕过                          |
| 回退组合     | 选择仍获准且兼容的旧组合，不回滚业务事实、Session 历史或外部动作             |
| 迁移既有 Job | 停止并隔离旧执行，核对未决动作，经受控命令更新组合和代次，再重新取得执行资格 |

补充：

- 暂停／撤销影响当前适用的工具、资源及执行准入，不仅检查新 Run 启动；必要停止、清理和在途结果核对仍可通过受控路径完成。
- 完成停止请求不等于旧执行已经隔离。冲突资源未隔离前，不开放新执行。
- 迁移的组合决定归 configuration，业务代次与恢复决定归 jobs，Run／绑定归 runtime，Kernel 协调必要事务。
- 将“没有历史兼容证明时创建新 Session”改为：只有业务规则允许、必要事实充分且旧资源已隔离时才能受控新建；否则报告缺口并停止。
- 新 Session 不得宣称恢复了全部历史，换资源或模型也不表示旧历史内容已被清除。
- UNKNOWN 继续按原目标核对，不能借迁移或回退获得新发送许可。

不修改现有状态枚举，不增加迁移调度器。

### 2.5 明确产品操作的对象和效果

完善 §19.2，在现有入口表后补充操作语义：

| 操作                         | 主方案边界                                                                     |
| ---------------------------- | ------------------------------------------------------------------------------ |
| 查看任务、历史、证据和执行树 | 受控查询，不自动启动模型、恢复任务或重新投递输入                               |
| 启动／继续                   | 按当前业务事实与执行资格决定是否创建新 Run，不复活终态 Run                     |
| 暂停                         | 明确受影响对象和范围，阻断相应新执行并按需请求停止；不承诺冻结任意模型请求现场 |
| 取消执行                     | 使用 Run 的取消契约，分别展示请求受理、实际停止及清理结果                      |
| 停止业务、人工结案、撤销审批 | 分别调用所属业务命令，不能由“取消”按钮互相代替                               |
| 接管／恢复                   | 按浏览器所有权及业务恢复规则核验，不以界面切换代表执行权转移                   |
| 配置、放行和回退             | 通过受控维护命令操作，不直接编辑运行状态或数据库                               |

同时明确：

- 工作台展示 Job、Run、绑定、审批、动作及未决事项的各自状态，不用一个“完成／失败”覆盖全部对象。
- 可用操作来自既有权限与状态规则，按钮可用不替代执行时核验。
- CLI 与桌面复用同一 Application／Kernel 命令和控制实例；多入口不能各自取得独立执行权。
- 入口表的 P12／P13 表示完整产品界面的交付阶段；前序阶段可通过必要 CLI 操作验证当期能力。
- 保持固定发票员工、配置文件／CLI 和必要维护入口，不增加复杂管理页面或第二业务领域演示。
