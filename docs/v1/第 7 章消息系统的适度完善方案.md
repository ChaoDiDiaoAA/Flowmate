
# 第 7 章消息系统的适度完善方案

## 1. 审查结论与修改定位

**第 7 章的主要边界已经明确，但传递职责、消息身份和异常影响仍有几处歧义。**

已有设计正确区分了原生历史、业务事实和运行观测，也明确不另建 messages 表。需要调整的是：

- “业务输入由 Context Builder 提交”容易把上下文构造与输入投递混为一谈。
- “原 messageId 与 bindingId 去重”未区分流式消息身份和持久历史身份，跨绑定恢复可能被误实现为重复消息。
- “消息传递异常只改变运行状态”过于笼统，界面断流不应直接等同于 Run 失败。
- 消息结束、输入处理完成和业务完成需要在本章直接区分。

本次完善职责与关键行为，具体 SDK 事件映射、投影字段和重连算法留到阶段方案。

## 2. 第 7 章的必要调整

### 2.1 明确输入组织与投递职责

修正 §7.2 的“由 Context Builder 提交”，补充简短职责说明：

| 模块                | 消息链路职责                                        |
| ------------------- | --------------------------------------------------- |
| Application／Kernel | 建立可信入口，区分普通输入与人工业务命令            |
| core/sessions       | 用户输入受理、投递归属及消费／处理结果登记          |
| core/context        | 构造当前有效业务输入投影；P5 起提供 ContextSnapshot |
| core/runtime        | 核验本次执行资格，协调执行与收尾                    |
| runtime-pi          | 将获准输入交付 Pi，关联原生消息及实际消费证据       |
| Pi                  | 组织原生消息、工具结果和后续模型请求                |

人工修订、复核或审批先走所属业务命令；需要通知模型时再形成输入投影，不能把人工命令全部当作普通聊天转发。

本章概括调用方向，输入投递状态继续由第 11 章定义。

### 2.2 补齐输入、历史与展示的存储边界

调整 §7.1：

- 将 `session_inputs` 明确列为输入受理与投递记录，区别于 Pi 实际会话历史。
- `sessions/memories` 保存原生历史及当前位置；业务事实仍由业务表负责。
- 消息视图是受控投影，不成为新的权威历史或业务事实来源。
- 实时内容可以在持久化前展示，但不能据此宣称已保存；恢复以最后成功提交的历史为准。
- 原生内容块按用途投影，工具结果和附件保留受控引用，不把所有消息一律降为纯文本。具体支持形式随阶段确定。

不新增消息表、正文副本库或独立消息存储服务。

### 2.3 区分流式消息身份与持久历史身份

完善 §7.2 的聚合、配对和恢复规则：

- 实时片段在所属执行来源内聚合；工具请求与结果使用实际调用关联，不能从显示顺序猜测。
- 不假定所有原生事件天然具有可跨恢复使用的统一 messageId。必要映射由接入层依据真实事件和原生条目建立，具体方式在阶段方案验证。
- 历史展示以 Session 内已持久原生条目的身份为依据；新 binding 不应让同一历史消息重复出现。
- bindingId、Run 和代次用于标识执行来源，不作为历史消息的唯一身份。
- 当前对话按所选历史位置／分支展示，不把所有分支条目按保存顺序拼成一条对话。
- 主子消息保留来源；子结果通过插件实际回送进入主会话，展示层不能自行拼接历史或伪造结果。

保持现有历史树和事件关联设计，不增加新的消息身份表。

### 2.4 区分消息完成、输入处理和业务完成

补充三个层次：

| 事实          | 表示什么                                           |
| ------------- | -------------------------------------------------- |
| 消息流结束    | 当前消息的生成结束，不证明回答正确或任务完成       |
| 输入处理完成  | 已消费输入具有可核验的处理结果，由既有输入契约登记 |
| Run／Job 完成 | 分别满足产品执行目标和业务完成条件，由所属模块判断 |

同时明确：

- UI 中的 failed／aborted／incomplete 属于消息或展示状态，不能直接覆盖 Run、工具或 Job 状态。
- 多条输入可以共同关联一个结果，一条回答不能自动代表所有排队输入都已处理。
- 模型文字中的“已批准”“已提交”“已完成”不能生成业务事实；状态展示读取对应业务记录。

### 2.5 按故障位置处理消息异常

替换“消息传递异常只改变运行状态”的笼统表述：

- **展示或订阅断流：** 标记连接或消息不完整，按既有事件和历史恢复；不能仅因此判定 Run 失败或自动重发输入。
- **输入交付不明：** 由 `session_inputs` 的投递协议核对，禁止盲目重投。
- **原生执行异常：** 交由统一错误边界及 Run 契约处理。
- **历史保存失败：** 沿用既有停止绑定和最后提交状态恢复规则。
- **工具回送或外部结果不明：** 按原工具、命令及动作身份核对，不因界面缺消息而重复业务动作。

保留现有脱敏、访问控制及隐藏思维链边界；不修改原生条目结构来迎合展示需求。

## 3. 阶段与评测同步

只修改主方案和 Agent 评测总方案，其他章节仅纠正冲突表述。

| 阶段 | 承接重点                                                 |
| ---- | -------------------------------------------------------- |
| P1   | 最小输入、原生消息与工具回送关联                         |
| P3   | 流式聚合、消息投影及展示异常与运行结果分离               |
| P4   | 输入受理／消费／处理关联，持久历史恢复、分支及跨绑定去重 |
| P5   | Context 构造与输入交付职责分离                           |
| P8   | 人工命令先接受业务事实，再通知模型                       |
| P11  | 主子来源、工具关联及真实子结果回送                       |
| P12  | 桌面分别展示消息、输入处理和业务状态                     |
| P13  | Host 断流、重连、历史保存失败及恢复核对                  |

评测复用既有消息、Session、事件、工具和恢复覆盖，不新增评测体系或具体 Case。

## 4. 验收与细节边界

文档验收检查：

- Context Builder 不再被描述为输入受理或投递负责人。
- 输入记录、原生历史、展示投影和业务事实的权威来源明确。
- 跨绑定恢复不重复展示同一历史，分支及主子来源不混淆。
- 消息流结束不冒充输入处理、Run 或 Job 完成。
- 界面断流不直接判运行失败，消息缺失不触发重复输入或业务写。
- 保持现有目录、23 张表、状态枚举及 P0–P13 顺序。

本次只调整文档，不生成产品代码或修改已发布评测资产。精确消息类型、SDK 事件字段、标识映射、片段合并、分页和重连实现，由对应阶段方案确定。
