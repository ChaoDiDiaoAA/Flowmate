
# 第 23 章生产发布与持续运维的适度完善方案

## 1. 审查结论与修改定位

**第 23 章的主要范围已经完整，不需要重做。** 已覆盖生产观察、逐步放量、停写、安装迁移、回退、备份、凭证和维护责任。

需要完善的主要是：

- 运行组合变化与日常业务输入变化的区别。
- 停写、实际停止、资源清理及恢复放行的关系。
- 上线流程中“小任务验证”的授权前提。
- 技术故障转人工、备份恢复和凭证变化的处理边界。
- 运维操作的负责人及应用离线期间的能力承诺。

本章负责发布和持续运行的交接，不重复定义第 19 章发布状态或第 12 章提交协议。具体操作步骤、阈值和维护周期由 P13 方案确定。

## 2. 第 23 章的必要调整

### 2.1 对齐生产放行与运行组合

完善 §23.1：

- 沿用第 21 章的 Test／Shadow／Canary／Production 阶梯，以及第 19 章的发布控制，不另建生产状态体系。
- Shadow 使用获准生产资料进行只读运行，形成的候选、预计载荷或预览属于本地结果，不代表已创建外部草稿、上传附件或取得发送许可。
- 将“变更产生新候选”限定为模型、资源、实现、目标或部署等运行组合变化；正常新增发票和业务事实变化按输入、修订及快照规则处理，不要求每张票重新发布员工。
- Canary 的范围放行与逐动作审批分别成立；质量成绩、观察时间或安装成功不能自动扩大权限。
- Production 持续受批准组合、范围及当前停写控制约束，新版本和扩量分别核验。

保留已有白名单和额度治理，不增加财务审批责任。

### 2.2 明确停写、核对与恢复的顺序

完善 §23.1–23.3：

| 操作               | 主方案边界                                                           |
| ------------------ | -------------------------------------------------------------------- |
| 停止新准入／停新写 | 阻断受影响范围的新操作，不表示在途执行已停止                         |
| 停止执行与清理     | 请求取消后核验实际停止、绑定及资源释放                               |
| 在途结果核对       | 按原动作身份通过受控通道继续，UNKNOWN 不自动改成失败或未执行         |
| 恢复运行／写入     | 故障及资源条件满足后重新核验当前资格，不恢复旧 Run、Scope 或失效审批 |

补充：

- 停写范围依据既有错误影响范围和运行控制确定；单个查询异常不自动扩展为整个实例故障，共享存储、授权或执行完整性故障按实际影响阻断。
- 严重错录、重复有效提交、未授权写入和关键审计缺失继续执行既定立即停新写规则。
- 通知失败不妨碍本地停止措施，也不能把“通知已发送”当作停写已生效。
- 恢复必须同时核验故障处置、相关回归、旧执行隔离、未决动作及当前发布／权限；不能仅删除暂停标记。
- 发布放行不能覆盖仍有效的 Kill Switch、撤销或其他限制；恢复不自动重放旧输入、委派或未知提交。

### 2.3 澄清安装、迁移与回退流程

完善 §23.2，保留既有总体顺序，补齐关键前提：

**固定获准组合 → 停止受影响的新准入并核对在途 → 确认旧控制者及冲突资源隔离 → 一致性备份与迁移验证 → 安装／迁移 → 保持写禁用并检查 → 获准的小范围验证 → 核对结果 → 恢复批准范围。**

明确：

- “获准小任务”若涉及真实写入，须先取得对应范围放行和具体冻结动作审批，不能因属于部署验证而绕过授权。
- 安装、只读检查、真实业务验证及恢复流量分别取证；安装成功不代表业务已可用。
- 来源或主数据异常时可以暂停、补充依据或交人工处理，但人工操作不能把缺失规则直接标为通过，也不能绕过发送准入。
- 数据库迁移或必要兼容检查失败时，不启动依赖新结构的业务。
- 回退只能选择仍获准且兼容的组合；不能回滚外部交易、复活撤销许可或利用旧备份重发业务。
- 历史不兼容时沿用受控恢复规则，不自动空建 Session 继续执行。

具体升级命令、迁移顺序及目标成功证据留到 P13。

### 2.4 完善持续检查、备份和凭证边界

完善 §23.3：

**持续检查**

- 现有日常／每周／每月表作为维护节奏，具体频率、阈值和责任人在生产前固定。
- 自动检查只在已部署且实际运行的承载环境中生效；应用离线期间不承诺即时监控或通知。
- 启动、恢复及关键操作前重新核验到期、额度、依赖和当前控制，不因漏过一次定时检查而默认仍有效。
- 诊断日志用于定位，业务状态、审计和权威结果仍读取各自记录；检查或告警本身不产生恢复许可。

**备份恢复**

- 沿用第 18 章的一致性数据库与必要文件联合恢复范围，保留独立备份位置及实际恢复演练。
- 将“来源撤回策略在恢复后重新生效”明确为：**开放新使用或写入前核验当前撤回、权限和审批**，不能在恢复窗口暂时沿用旧资格。
- 从较早备份恢复时，核对备份之后可能发生的外部动作；无法确认的范围阻断新发送，不将记录缺失解释为未执行。
- 备份成功、数据恢复成功和业务允许恢复分别判断。

**凭证变化**

- 区分同一身份下 Pi 负责的正常认证刷新，与受控的凭证切换、账号或服务目标变化。
- 模型认证继续沿用 Pi 原生机制；业务凭证通过所属 Adapter 的受控配置接入，不另建认证系统。
- 凭证切换核验在途影响及实际生效结果；涉及运行组合变化时走既有变更控制，不静默影响活动执行。
- 台账只保存非秘密引用及核验信息，凭证可用不等于具有业务提交资格。

### 2.5 明确负责人和交付范围

在 §23.3–23.4 补充简短职责表：

| 负责人／模块             | 职责                                             |
| ------------------------ | ------------------------------------------------ |
| `core/configuration`   | 发布组合、范围及当前放行控制                     |
| `core/operations`      | 受控维护、健康检查、备份恢复和运维协调           |
| `core/runtime`         | 执行停止、绑定及资源清理事实                     |
| `core/submissions`     | 在途动作、UNKNOWN 和权威结果核对                 |
| 发布、维护及业务授权主体 | 按各自资格决定放行、维护及具体动作批准           |
| 独立质量工作             | 提供适用验证、归因和质量结论，不直接授予生产权限 |

同时明确：

- 一个操作者可以具备多种已登记资格，但维护身份不自动获得业务批准权。
- 响应责任和可响应时间在生产前固定，不额外建设运维平台或值班系统。
- 最终交付物须对应实际交付组合和已验证范围；安装说明、备份工具及恢复手册不能仅有未执行模板。
- 工程完成与完整生产交付分别报告；缺必需真实条件时保留缺口。
- 卸载或清理不默认删除业务数据库、历史和证据，沿用既有保留及受控维护规则。
