
# 第 5 章 Agent Loop 与业务 Workflow 的适度完善方案

## 1. 审查结论与修改定位

**第 5 章的主体设计已经完整，不需要重做。** 已明确复用 Pi Loop，并定义产品目标、Run／绑定状态、候选接受、人工交接及取消清理。

需要完善的是少量概念和表达：

- “Agent Loop 管一次推理和工具交互”容易被理解为只调用一次模型。
- 时序图省略 Runtime 接入层，容易误解为 Kernel 直接调用 Pi、直接拥有 Run 状态。
- “结束信号→完成队列→关闭绑定”的图示容易被理解为 Pi 提供一个统一的产品收尾操作。
- 候选接受与 Run 成功的相互条件，需要避免形成循环解释。

本次只明确职责、关键行为和交接顺序，具体 SDK 调用、队列处理和事务实现留到阶段方案。

## 2. 第 5 章的必要调整

### 5.1 明确 Loop、Run、Session 和 Workflow 的关系

补充一张简短概念表：

| 概念          | 主方案定义                                                                                    |
| ------------- | --------------------------------------------------------------------------------------------- |
| Pi Agent Loop | 原生模型—工具执行机制，一次执行可以包含多次模型请求和工具调用                                |
| Run           | Flowmate 对一次获准执行的产品记录，固定目标、执行资格和完成条件；不等于一次模型请求或一条回答 |
| Session       | 承载原生对话历史，可被后续 Run 续接；Run 结束不等于删除 Session 历史                          |
| Job／Workflow | 管理业务步骤、事实、人工等待及最终业务结果；一个 Job 可以经历多个 Run                         |

同时说明：一个有效业务代次可以包含获准的主子 Run，“单一有效代次”不等于禁止子 Agent 协作。

### 5.1.1 修正时序图的职责表达

图中明确表现以下调用关系：

**Application／Kernel 接受任务 → core/runtime 管理 Run → runtime-pi 接入 Pi → Pi 执行原生 Loop。**

返回时分别表达：

- runtime-pi 报告原生执行事实。
- core/runtime 核验产品运行结果并管理 Run 终态。
- Kernel 协调业务结果接受，core/jobs 按 Workflow 判断业务下一步。

保留 Kernel 的事务协调职责，不将其画成另一套 Run 状态负责人。将“原生 Agent 委派”统一表述为第三方插件提供的 Agent 工具委派。

### 5.2 明确产品控制对原生循环的影响

补充原则，不增加新的状态：

- 工具拒绝或可恢复错误先作为结果交回 Pi；单次工具失败不必然等于整个 Run 失败。
- 是否继续仍受当前目标、权限、预算和终止条件约束，不能无限尝试。
- 业务暂停、取消和依据失效由产品撤销相应执行资格，并通过原生控制入口请求停止；不承诺能够冻结和恢复任意模型请求现场。
- 取消请求、实际停止和资源清理继续分别记录，沿用现有状态契约。

### 5.3 澄清候选接受与成功判定

统一三个事实：

1. **候选已保存**：只证明产生了可追溯的预测。
2. **业务结果已接受**：通过当前领域规则、版本和权限核验。
3. **Run 已成功结束**：满足本次目标、输入处理及停止清理要求。

修正“满足成功条件才能接受候选”的表述：先核验候选及自动接受资格，再由受控结果处理协调业务接受与 Run 终态，避免要求“Run 已成功”后才能接受、又要求“接受后”才能成功。

保留现有边界：P2 只保存候选，P8 才实现完整修订接受；失败 Run 的候选可以由获准人工另行复核，不恢复旧执行权。

### 5.4–5.5 澄清收尾和续接

保留现有状态表，仅统一正文与图示：

- 原生结束事件只是产品核验的触发信号。
- 正常收尾先关闭本次输入准入，核对已归入该 Run 的输入，再确认结果、停止与必要清理。
- 上述是产品交接原则，不表示 Pi 提供“完成产品队列并关闭 Run”的单一接口。
- 原生正常结束但目标未满足时，不能判成功；只有目标允许且持久交接成立时，才能以合法交接结束。
- 后续输入使用新 Run 续接 Session；长期人工等待保留业务等待对象，不占用活动 Run。

## 3. 阶段与评测同步

| 阶段     | 承接重点                                                      |
| -------- | ------------------------------------------------------------- |
| P1       | 原生 Loop 与产品 Run 的区别；正常结束、目标满足和失败分别判断 |
| P2–P3   | 工具错误回送、受限继续、预算和停止控制                        |
| P4       | 多轮输入、Run 收尾与 Session 跨 Run 续接                      |
| P8       | 候选接受、业务步骤及合法人工交接                              |
| P11      | 同一业务代次内的主子 Run 职责与结束关系                       |
| P12–P13 | 外部动作不随 Run 取消而回滚，故障恢复不重放未知动作           |

同步评测总方案已有 Loop、Run、状态及交接覆盖，不新增评测体系或展开具体测试步骤。重点覆盖：

- 多次模型调用仍属于原生 Loop。
- 工具拒绝不被机械等同于 Run 失败。
- 原生结束不冒充目标完成或业务成功。
- 候选保存、接受和 Run 成功可以分别核验。
- 长期人工交接、新 Run 续接及主子协作不混淆执行身份。
