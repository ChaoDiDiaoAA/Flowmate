## 1. 审核结论

上一轮“保留要求已全部迁移”的判断不成立。新方案保留了不少 Pi Runtime 复用、Kernel、Gateway、人工协同和审计行为，但把“基于 Pi SDK 二次开发、交付可复用数字员工平台”的产品目标，压缩成了“打通一条发票业务链并保留扩展边界”。这影响项目终点和验收，不能靠补上 Pi 名称或 SDK 能力表解决。

原方案明确：**L1 使用 Pi SDK，L2–L6 是我们自己的核心产品；07B2B 发票录入是第一个 Digital Employee Template。** 首版只运行一个员工，不代表产品模型可以写死成 InvoiceAgent。新方案必须同时承接平台基础和首个业务模板，再分阶段实现。

对照依据：

- 原 V1.2 第 3 章（来源文件已删除）：六层架构、十大核心产品、Runtime 复用、阶段矩阵和六类资产。
- 原总目标方案（来源文件已删除）：单人实施、第一版范围及业务交付约束。
- [新完整方案](../../spec/00_Flowmate完整方案.md)：重点核查第 2、3、6、10–13、16 和 20 节。

这里比较文档要求，不验证旧稿对某个 Pi SDK 版本的 API 描述是否仍然准确；具体 SDK 能力仍需锁定版本后核实。

## 2. 六层架构必须作为产品范围恢复

| 层 | 原方案要求 | 新方案承接情况 / 修订要求 |
|---|---|---|
| L1 Pi SDK | 复用模型、Agent Loop、Session、工具运行和资源机制 | 第 16.1 节已较完整保留；继续避免重写 Runtime |
| L2 Runtime Control Plane | 自研运行控制、Job/Run/Session 映射、命令事件、预算、健康与恢复 | 主要行为存在；需要作为平台交付资产明确验收，不能仅表述为 SDK 包装 |
| L3 Capability / Tool / Skill | 企业工具、能力、SOP 及其管理 | Gateway 较完整；Registry、按员工解析能力组合及管理操作不足 |
| L4 Digital Employee Kernel | 通用 Job、Workflow、Policy、Approval、Audit | 发票控制行为充分；公共 Kernel 与发票工作流定义的边界不足 |
| L5 员工管理与运营 | Template、Prompt、Version、Eval | 被压成配置与报告；需要恢复操作者能完成的管理和运营闭环 |
| L6 产品体验 | Task Center、Cockpit、Review、Takeover | 发票体验大体保留；缺公共任务外壳与领域视图的扩展边界 |

原文定位：V1.2 第 167 行起（§3.1）；六类自研资产位于第 1472 行起（§3.17）。平台自研控制面与薄 Pi Runtime Host 不是同一个范围。

## 3. 十大核心产品逐项对照

“保留”按可执行行为判断；表中“修订要求”是下一版必须补齐的设计责任，具体接口和界面另在阶段设计落实。

| 原核心产品及原文位置 | 新方案位置 | 判定 | 修订要求 |
|---|---|---|---|
| Digital Employee Definition，§3.3，第 808 行 | §2.2、§8、§16.2 | 配置字段保留，通用性约束遗漏 | 员工模板是可注册、可版本化并绑定 Workflow/Policy/Tools/Skills 的产品对象。发票逻辑归首个模板，公共模型不得写死 InvoiceAgent |
| Agent Runtime Control Plane，§3.4，第 867 行 | §6、§8、§16.1–16.2 | 主要行为保留 | 将统一接口、事件、预算、健康、恢复明确列为平台产物；验证 Pi 升级或 Host 更换不要求重写 UI/Kernel |
| Task Center，§3.5，第 958 行 | §3、§8、§16.2–16.3 | 发票任务行为保留，复用目标弱化 | 明确公共 Job/Run 与发票领域载荷分离，同一任务中心和详情外壳按任务类型加载领域视图 |
| Digital Employee Kernel，§3.6，第 996 行 | §6、§8–9、§16.3 | 控制行为保留，最终配置化不完整 | Kernel 执行注册且固定版本的 Workflow/Policy；发票状态与业务规则属于工作流定义。配置化不要求图形设计器，不允许随意改动在途任务语义 |
| Enterprise Tool / Capability，§3.7，第 1070 行 | §16.3 | Gateway 保留，Registry 管理不足 | 定义工具名称/版本、注册记录、发布/禁用状态、员工权限绑定及每次 Run 的工具集合解析。静态函数表不能代替最终管理能力 |
| Skill / SOP，§3.8，第 1167 行及 §3.2.7–3.2.8 | §16.1–16.4 | 绑定和版本原则保留，管理模型不足 | 明确 Skill Registry、Metadata、版本、发布和评估；SOP 规定查询顺序、业务依据与转人工原则，不能覆盖确定性规则和权限。通过受控 ResourceLoader 装载，改 SOP 不改 Pi Runtime |
| Human-in-the-loop，§3.9，第 1190 行 | §3、§7–9、§16.3、§17 | 主要完整并补强 | 复核、审批、接管、恢复保留；明确它们是公共任务能力，发票视图提供具体业务字段 |
| Agent Cockpit，§3.10，第 1226 行 | §3、§16.2–16.3、§17 | 首个模板体验基本完整 | 原图、字段、校验、Timeline、工具、浏览器证据与人工入口均在；补公共驾驶舱与领域组件的边界 |
| Audit / Replay / Observability，§3.11，第 1245 行 | §9、§16.2–16.4、§17 | 主要保留 | 把追踪、回放、版本、成本和失败分析作为 Agent Ops 平台产物验收，不能只验发票日志 |
| Version / Eval，§3.12，第 1283 行 | §3、§12、§16.4 | 机制保留，最终运营闭环不完整 | 明确选择候选员工版本和固定评估集、运行评估、比较基线、定位失败、放行/停用/回退及追溯。可渐进采用 CLI 和最小界面，但最终必须可操作 |

另有明确遗漏：**平台负责业务 Context 构造策略**（原 V1.2 §3.13，第 1332 行）。新稿“ResourceLoader 装载上下文”不能代替这一责任。需定义如何从当前 Workflow 阶段、已确认修订、匹配/校验事实、授权状态、允许工具和预算生成运行输入，并记录来源及版本。恢复时从业务事实重建，任务之间隔离；不能把历史 Session 当作权威业务状态。

## 4. 六类自研资产要有独立验收

旧 §3.17 指定的资产必须进入新总方案的阶段矩阵、最终交付清单和验收条件，不能只散落在技术章节。

| 资产 | 下一版需明确的验收行为 |
|---|---|
| Digital Employee Kernel | 公共 Job/Run、Workflow/Policy 执行与发票领域逻辑分离；审批、幂等、恢复由公共业务控制维护 |
| Agent Runtime Control Plane | 稳定接口隔离 Pi 类型与 Session 细节；命令、事件、预算、故障隔离和恢复有契约证据 |
| Enterprise Tool Platform | 可注册、版本解析、按员工授权和停用；所有实际工具经过同一 Gateway |
| Human Collaboration | 同一任务机制支持复核、审批、接管、恢复，变更与授权均能追溯 |
| Enterprise Adapter Platform | 明确 Adapter Registry、环境/Provider 绑定、版本和替换契约；替换实现不重写领域核心 |
| Agent Ops | 按员工与发布版本评估、比较、追踪失败、发布、停用和回退，历史 Run 的版本组合可还原 |

平台边界可以通过接口依赖检查、注册与替换试验及契约验证证明；不因此自动增加第二个真实业务员工。现有新稿 §12.2 的发票业务、生产安全和运维验收继续保留，但不能独自代表整个平台已交付。

## 5. 必须显式处理的范围与阶段差异

1. 原总目标 §4.2 将“一个员工、一条流程、一个运行实例”等写为**第一版约束**；新稿 §2.2 曾将其提升为整个项目的边界。首个生产场景可以保持单机、单 Agent、一个模板，但不能据此删除平台通用模型和运营能力。
2. 原 V1.2 §3.14 的阶段矩阵包含 Tool Registry 版本化、Workflow 配置化、Adapter Registry、Eval Center 和正式员工版本管理。新 P0–P6 主要沿业务依赖成熟度拆分，需要补齐与之并行的平台交付和退出条件。
3. 原矩阵最终 Adapter Registry 标为“多平台”，新稿曾排除多 B2B。应区分“支持替换/注册不同 Adapter 的平台能力”与“本次实际交付多个真实 B2B 集成”。前者需要保留；后者是旧文之间的范围差异，不能静默判为已淘汰或已批准。
4. 原矩阵在真实 B2B 阶段指定 Server，后期 Server/Worker；新稿采用按故障隔离需求验证薄 Host。需要记录部署演进的理由与验收要求，不能因不建 Worker Pool 就取消 Runtime Control Plane。
5. 当前用户已确认的调整继续有效：复用 `D:\paper\Invoice`、原文或已有解析双入口、首版真实字段抽取、本地模拟完整闭环。它们改变数据起点和首版实现顺序，没有取消 Pi 二次开发平台。

后续修订顺序为：恢复平台产品定位及六层责任 → 补齐十大产品及六类资产的契约与操作行为 → 与完整发票业务链合并 → 给 P0–P6 同时配置平台和业务验收 → 逐项核对保留/调整/延后依据。当前先保留两套文档，不继续删除。
