## 1. 目标与已确认范围

Flowmate 首版在基于 Pi SDK 二次开发的最小平台上，运行首个 07B2B 发票员工，完成包含真实字段抽取的本地模拟录入闭环。平台基础与发票主线同时参与首版，完整平台运营和生产业务分阶段交付。

用户已经确认：

| 决策 | 当前结论 |
|---|---|
| 首版验收终点 | 完整本地模拟提交闭环，包含复核、审批、模拟提交及结果确认 |
| 产品输入 | 兼容原始文档与已有解析结果，当前优先复用已有解析结果 |
| 字段抽取 | 首版包含真实字段抽取；模型生成独立业务字段，标注仅供评估 |
| 文档位置 | 新方案统一放在 `docs/spec`；本轮先恢复旧方案核对 Pi SDK 二次开发内容，迁移尚未完成，保留新旧文档 |

首版验收主线：

```text
原始文档 → 文档解析 ─┐
                    ├→ 真实字段抽取 → 标准化与规则校验
已有解析结果 ────────┘
→ 必要的人工复核 → 待提交预览 → 人工审批
→ 本地模拟提交 → 查询并确认结果 → 完成任务与审计记录
```

首版必须实际调用模型完成字段抽取。直接读取数据集标签跑通流程仅是内部测试方式，不作为首版完成的证明。真实 07B2B 生产写入不属于本次首版验收终点。

## 2. 数据来源与接入

数据来源为 `D:\paper\Invoice`，目前主要样本位于 `voxel51` 子目录。直接复用现有原始文件与解析结果，不再把新建网络采集、重跑全部 OCR 或搭建 Obsidian 工作台作为首版前置任务。

| 数据层 | 现有文件 | 职责 |
|---|---|---|
| 原始文档 | `original.jpg` | 提供原文、复核依据和文档输入 |
| 解析结果 | `content.json`、`content.md`、`pages.json` | 提供文字、表格和版面信息，作为字段抽取输入 |
| 解析与来源元数据 | `parse.json`、`record.json`、`snapshot.json`、`receipt.json` | 关联样本、版本、文件和摘要 |
| 参考标注 | `annotation.json`、`fields.json` | 用于独立评估；与模型输入隔离 |

数据接入先筛出完整子集，检查配对、实际路径和 hash，再冻结运行清单。原图、派生结果、参考标注与系统预测分别关联，原始文件保持不变。数据目录仍在增量处理，评估使用固定清单，不能一边跑一边改变样本集合。

原始文档与已有解析结果通过不同入口进入相同的字段抽取流程。新原图的支持格式和 Parser 接入方式尚未确定，不能以“已关联旧解析结果”冒充对任意新文件的解析支持。

详细数据数量、质量问题与历史方案审查见[数据审查记录](02_现有数据与路线审查.md)。其中数量属于审查时点快照，不是当前数据总量承诺。

## 3. 字段抽取与评估边界

字段抽取读取文档内容，输出候选业务字段，并尽可能关联原文片段、页码或版面位置。模型不得通过文件工具或上下文读取 `fields.json`、`annotation.json` 及含参考答案的其他材料。

规则层负责类型、金额精度、日期、必填项及业务一致性检查。缺失值、零值、解释歧义和冲突分别保留；不猜币种、不将缺失金额填零，不静默修改票面总额以使计算通过。

字段规范化、必填清单和票头/明细关系将在模拟目标表单定位确定后细化。当前英文 invoice 数据不能直接按中国增值税票全字段口径验收。

评估器独立读取参考标注，并与系统预测比较。标注缺失或歧义的字段单列，经过复核才能作为确定答案使用。字段正确率、整票通过情况、复核率、成本和耗时分别记录，附样本数和分母口径；阈值尚未确定。

## 4. 业务控制原则与待细化设计

以下控制原则受完整方案第 7–9、16–17 节约束，具体阶段契约和异常行为在后续设计中细化：

- 业务任务与 Agent 会话分离；持久化任务、字段修订、审批和提交结果，不能仅靠会话记忆恢复进度。
- 复核修正字段，审批授权具体提交动作。建议审批绑定任务、目标、字段版本和载荷摘要，内容变化后重新校验并重新审批。
- 提交前保存意图和业务关联键；响应超时后先查询结果，不能因没有收到回执而盲目重提。
- 本地模拟系统能够按关联键确认结果，并覆盖成功、拒绝、超时、已提交但回执丢失等场景。
- 重复点击、重试和应用重启不能产生重复有效提交。未知提交结果保持可见并进入核对或人工处理。
- 展示原文、预测、修正、规则结果、待提交内容和执行记录；缺失数据或异常原因可追踪。

首版有人工审批，不将其结果包装成“无人工介入”的 STP；先统计抽取质量、自动准备率、复核率和批准后执行成功率。

## 5. 技术方向

完整方案规定的技术方向为 TypeScript、Electron、React、Pi SDK、SQLite、Zod；具体版本在 P0 验证并锁定。

Pi 负责 Agent 会话、模型调用、工具执行机制和运行事件；Flowmate 自研员工定义、公共 Job/Run、Runtime 控制面、Workflow/Policy、能力注册与 Gateway、人工协同和 Audit/Eval。Pi Host 保持薄适配，平台产品层按总方案第 6、7、16 节建设；“薄”只约束 SDK 包装层，不缩小平台范围。

保持单机、单 Agent、单条发票处理主线。首版至少有任务列表、任务详情/Timeline、复核及审批入口。EmployeeVersion、Workflow、Tool/Skill/Adapter 可从固定配置登记，但启动必须经过统一依赖解析、能力授权与 Release 绑定；公共模型不得写死 InvoiceAgent。完整管理界面逐步增加，Skill 市场和多 Agent 编排不作为首版前置。

## 6. P1 内部工作划分建议

全项目 P0–P6 阶段由完整方案定义。本文仅描述 P1 内部工作，不另设一套全项目阶段编号。P0 已提供数据与最小工程基线，P1 在其基础上实现首版。

| 里程碑 | 主要工作 | 交付检查点 |
|---|---|---|
| 接入基线 | 使用 P0 样本与 Parser 验证结果，明确首版模拟表单及字段契约 | 输入、标注和输出分离；文件引用可解析，范围明确 |
| 最小平台 | 注册员工/工作流/工具与资源，持久化公共 Job/Run，构造 Context，接入 Runtime 与 Gateway | 发票 Schema 与公共状态/运行引擎分离；版本固定；规范事件与工具授权实际生效 |
| 真实字段抽取 | 读取已有解析结果，实际调用模型生成字段，执行规范化与规则检查 | 预测结果可追踪到原文，可独立评估，缺失和歧义可见 |
| 模拟提交闭环 | 接入任务界面、人工复核、预览、审批、本地模拟目标与结果确认 | 一张票从文档处理到模拟录入完成；修改、拒绝、超时和重复场景行为明确 |
| 首版验证 | 集成约定的原始文档入口；验证恢复和标签隔离；运行冻结数据集 | 已确认的两类输入及完整主线经过验证；报告失败案例与已知限制 |

可在内部使用已给定字段测试模拟提交，但不能跳过真实抽取和原始文档接入验收。后续依照总方案进入 P2 目标业务契约、P3 全链真实测试、P4 Shadow、P5 Canary 和 P6 生产交付。供应商/订单/验真和 ERP 回写始终属于完整项目目标，P1 是否精细模拟只影响阶段工作量。

## 7. 首版验收框架

首版至少需要验证：

1. 对明确支持的原始文档和已有解析结果，两类输入都能进入处理流程。
2. 实际调用模型抽取业务字段，模型路径无法读取参考标注。
3. 字段缺失、歧义和规则冲突可以复核，修正前后有记录。
4. 预览、审批与实际提交内容一致，未经批准的提交被拒绝。
5. 本地模拟提交结果可核对，重复操作、超时和重启不会造成盲目重提。
6. 固定数据集上的结果可复现地统计，抽取质量与流程执行结果分别报告，并达到 P1 阶段设计事先固定的质量门槛；不能以每票人工重填代替抽取达标。
7. 员工/能力注册与版本解析真实参与闭环，Job/Run/Session 可关联，Pi 类型不进入公共领域与 UI；重建会话不丢业务事实。
8. 业务 Context、工具集合和运行版本可追溯，旧 Run/旧修订输出不能覆盖新人工结果；原生工具/资源不能绕过 Gateway 或访问参考答案。

支持格式、具体字段、金额容差、异常矩阵和质量阈值仍需确认，因此当前不能据此宣布首版已具备可执行的完整验收规范。
